# 04: Workflow scripts from headless sessions

Ticket: `.scratch/harness/issues/04-workflow-from-headless.md`. Brief: Sections 3.1 (item 2) and 5.4 (`absorb.js`, `panel.js`, `verify.js`). CLI verified: `claude --version` = 2.1.268, Linux, 128 cores (`nproc`). Smoke test date: 2026-09-11.

## Answer

1. **Yes, usable headless.** A `claude -p` session runs a saved `.claude/workflows/<name>.js` through the Workflow tool with no dialog. `-p` never shows the workflow approval prompt; the call goes through ordinary permission evaluation instead (docs, "Approve the plan before it runs"). Smoke test run 3 completed a two-agent workflow in one turn, 1.4 s wall, both agents returned schema-validated objects.
2. **Opt-in required: a permission allow rule for `Workflow`, and in practice `Skill` too.** Under `--permission-mode dontAsk` with nothing else, the Workflow call is denied (run 1). With `--allowedTools Workflow` only, the model first calls `Skill("hello")` because a saved workflow is exposed as the slash command `/hello`; that call was denied and the model gave up without calling Workflow (run 2). With `--allowedTools Workflow Skill` the Skill call expands to "Invoke: Workflow({ name: 'hello' })", the Workflow call runs, and the run completes (run 3). No settings flag was needed on this Max account (`enableWorkflows` defaults on by plan; Pro must toggle it in `/config`). The `ultracode` keyword is irrelevant here: the docs state it is ignored in a `-p` prompt. Alternatives the docs list: `--permission-mode auto` (classifier), `bypassPermissions`, a `PreToolUse` hook returning allow, or `--permission-prompt-tool`. Narrower rules exist: `Workflow(<name>)` approves one saved workflow by name (docs); `Skill(<name>)` is the analogous Skill rule shape (unverified in this test).
3. **Concurrency cap on this box: 16.** The binary computes `Math.min(16, Math.max(2, os.availableParallelism() - 2))`; with 128 cores that is 16 (an unlimited cgroup assumed; `availableParallelism()` honors CPU affinity). Excess `agent()` calls queue. Lifetime cap 1000 agents per run; 4096 items per `parallel()`/`pipeline()` call. This cap is separate from the Agent tool's `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` limit.
4. **Workflow agents are subagents for hooks and permissions, but not for the `-p` result's `subagent_stats`.** They run through the same agent loop with `agentType: "workflow-subagent"` (on-disk `agent-<id>.meta.json`) and `spawnedByWorkflowRunId` set; the stop-hook path in the binary emits `SubagentStop` whenever an `agentId` is present, with `agent_type` as the matcher input, so a `SubagentStop` matcher must accept `workflow-subagent` (or the custom `agentType` name). Not exercised with a live hook in this test: marked inferred from binary. Their tool calls use the session's permission rules and mode (docs), so under `dontAsk` every tool an agent needs must be on the allowlist. The `-p` JSON result reported `subagent_stats.spawned: 0` for the two workflow agents, so a conductor cannot count them there; use the `<usage>` block of the task notification or the run file instead.
5. **`agentType` works with `--agents` definitions, and workflow agents can use project skills.** `agent(prompt, {agentType})` resolves from the same registry as the Agent tool, so an inline `--agents` definition (prompt, model, tools, `maxTurns`, `skills`) is valid; with `schema` the custom system prompt gets a StructuredOutput instruction appended (workflow-authoring reference). The default `workflow-subagent` transcript shows a `skill_listing` attachment containing this project's skills plus the `session_context` and `deferred_tools_delta` attachments, so skills are reachable through the Skill tool; preloading needs the `skills` field of the agent definition (sub-agents docs). Not tested end to end with a custom `agentType` (3-launch cap): marked unverified.
6. **On-disk files (verified):** under `~/.claude/projects/<cwd-slug>/<session-id>/`:
   - `workflows/wf_<runId>.json`: the whole run in one JSON: `runId`, `taskId`, `script`, `scriptPath`, `result` (the script's return value), `agentCount`, `logs`, `status`, `durationMs`, `defaultModel`, `workflowProgress` (per agent: label, phase, model, state, tokens, toolCalls, durationMs, resultPreview), `totalTokens`. This is the file a conductor should read.
   - `workflows/scripts/<name>-wf_<runId>.js`: the persisted script.
   - `subagents/workflows/wf_<runId>/journal.jsonl`: `launched`, then per agent `started` and `result` lines keyed by a prompt hash, each `result` carrying the full return value.
   - `subagents/workflows/wf_<runId>/agent-<id>.jsonl` and `agent-<id>.meta.json`: full per-agent transcript and `{agentType, description, workflowPhase, spawnDepth, requestShape, requestNonInteractive}`.
   - Also `/tmp/claude-<uid>/<cwd-slug>/<session-id>/tasks/<taskId>.output` (same content as the run file minus the script) and the session transcript `<session-id>.jsonl` (tool_use, tool_result, task notification).
7. **Resume by `runId` is same-session only.** The tool schema says "Same-session only"; the docs add that `claude --resume <session-id>` can replay a run's cached results, a fresh session cannot (it gets `nothing to resume`), and a completed agent's result is replayed only if its (prompt, opts) are unchanged. For the harness this means a conductor never resumes a workflow across processes; it re-runs or resumes with `claude -p --resume <session-id>`.
8. **Fallback recommendation for the absorb phase: none needed as a fallback; use Workflow inside one `-p` session as the primary path**, launched with `--permission-mode dontAsk --allowedTools "Workflow(absorb) Skill(absorb) Read ..."` (or `--permission-mode auto`), and read `workflows/wf_*.json` after exit. Keep conductor-level fan-out (N `claude -p` readers, one chunk each) as the fallback when isolation or per-chunk model/effort control matters more than cost: it gives independent permissions, worktrees, and crash isolation, but pays a full session startup and system prompt per chunk and moves the coverage bookkeeping into the conductor. The Agent tool fan-out inside one session is the weakest option: model-driven scheduling, results land in the parent context, and no journal.

### Q5: fallback for the absorb phase

- Cost model (S2, S8): each workflow agent is a full subagent (about 19.5k tokens of fixed prefix here, shared through prompt caching within a fan-out; "Two agents that run with the same model, effort level, agent type, tools, output schema, and working directory build the same tools-and-system-prompt prefix"). A separate `claude -p` per chunk adds a session startup (hooks, CLAUDE.md, skills, MCP) and its own uncached prefix (about 90k cache-read tokens in the main session of run 1), so it is roughly 4 to 5 times the fixed cost per chunk on this configuration, and cannot share the 5 minute subagent cache.
- Isolation: Workflow agents share the session's permission mode and rules and its cwd (worktree isolation available per agent, S1: 200 to 500 ms plus disk). Conductor fan-out gives per-reader `--agents`, `--allowedTools`, `--worktree`, `--effort`, `--json-schema`, and crash isolation, at the price of the conductor owning the coverage audit and no journal.
- Agent tool fan-out inside one session: model-driven scheduling, results consume parent context, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` cap, no run file. Only worth it for a handful of chunks.
- Recommendation: primary path is Workflow in one `-p` session (`absorb.js` with `pipeline()` over chunks, obligation lists as schema output), reading `workflows/wf_*.json` after exit; fallback is conductor fan-out when a chunk needs a different model, tool set, or worktree than its siblings, or when the run must survive a session crash mid-way (a workflow cannot be resumed from a fresh process).
