## The detached job runner (ticket 17, criterion 1, prototype 27)

The real `wayline.resources.JobRunner` stands in for the prototype's throwaway script, as the
criterion asks. It ran on 2026-09-12 on this workstation (Ubuntu, systemd 255, Python 3.12.3, one
RTX 3090, 128 cores) from the harness worktree `.claude/worktrees/ticket-17-job-runner`, over a
project laid out by `wayline init` in a temporary `WAYLINE_HOME`. The pinned GPU job, a GPU OOM, a
host OOM, two cancellations, and the same GPU OOM again through the `setsid` fallback. Every job
file was written by `wayline job add` from a JSON spec on stdin, the way an experimenter's session
writes one.

It ran twice: at 17:46 UTC, and again at 18:08 after a review pass changed the launch path (it now
unloads a finished unit of the same id before relaunching it, and a cancellation is sticky in the
job file). Every reading below was the same in both runs; the sections marked **second run** are
the cases the review added.

**torch is not installed on this machine**, so the prototype's "allocate a tensor on CUDA if torch
is available" went through the CUDA driver with `ctypes`: `cuInit`, `cuCtxCreate`, `cuMemAlloc`.
That is a real device allocation, it needs nothing installed, and its failure path returns the
driver's own `CUDA_ERROR_OUT_OF_MEMORY`, which is one of the eight signatures of the OOM rule. The
`nvidia-smi` loop the prototype offers as the fallback is still there and runs when there is no
driver at all. The probe:

```python
cuda = ctypes.CDLL("libcuda.so.1")
cuda.cuInit(0)
cuda.cuDeviceGet(ctypes.byref(device), 0)
cuda.cuCtxCreate_v2(ctypes.byref(context), 0, device)
code = cuda.cuMemAlloc_v2(ctypes.byref(pointer), ctypes.c_size_t(int(gib * 1024 ** 3)))
if code != 0:
    cuda.cuGetErrorName(code, ctypes.byref(text))       # -> CUDA_ERROR_OUT_OF_MEMORY
    print("cuMemAlloc of %.1f GiB failed: %s" % (gib, text.value.decode()))
    sys.exit(1)
```


The launch line the `systemd_run` backend then ran, which is the line of Implementation Decisions 6
with nothing added and nothing left out:

```
systemd-run --user --unit=wayline-job-pinned --slice=wayline-jobs --remain-after-exit \
  --expand-environment=no -p CPUAffinity=8-15 -p MemoryMax=4294967296 -p MemorySwapMax=0 \
  -p TimeoutStopSec=30 -p RuntimeMaxSec=60 -p WorkingDirectory=<project> \
  -p StandardOutput=append:<project>/results/logs/pinned.log \
  -p StandardError=append:<project>/results/logs/pinned.log \
  -E CUDA_VISIBLE_DEVICES=0 -E PYTHONUNBUFFERED=1 \
  /usr/bin/python3 <tmp>/gpu_probe.py --gib 2 --hold 3
```

**Eight cores, but 8 to 15 and not 0 to 7.** The prototype asks for "GPU 0 and eight cores"; the
reservation of Implementation Decisions 6 owns cores 0 to 7 for the owner's interactive session,
so a job may never be pinned there. The log proves the pinning took, from inside the unit:

```

Name:	python3
Cpus_allowed_list:	8-15
device 0: NVIDIA GeForce RTX 3090
allocated 2.0 GiB on the device
nvidia-smi: 0, 2394, 2
nvidia-smi: 0, 2394, 0
nvidia-smi: 0, 2394, 0
freed; done
```

The poll while it ran, and after it exited:

```
$ systemctl --user show wayline-job-pinned.service -p LoadState,ActiveState,SubState,Result,ExecMainCode,ExecMainStatus
Result=success
ExecMainCode=1
ExecMainStatus=0
LoadState=loaded
ActiveState=active
SubState=exited
```

`show` returns the properties in its own order, not the order the `-p` list asks for, so the
decode reads fields by name and never by position. Decoded: `exited`, exit code 0. The job file's
attempt, which is where the exit code and the duration live:

```json
{"n": 1, "started_at": "2026-09-12T17:46:38.965Z", "ended_at": "2026-09-12T17:46:43.083Z",
 "result": "success", "exit_code": 0, "oom": null, "overrides": {}}
```

Duration is the difference of the two timestamps (4.1 s here); the job schema has no field for it
and does not need one. `cleanup` then unloaded the unit:

```
Result=success   ExecMainCode=0   ExecMainStatus=0
LoadState=not-found   ActiveState=inactive   SubState=dead
```

That reading is exactly why `LoadState=not-found` never implies success: an unloaded unit says
`Result=success` whatever it did. The decode calls it `gone`.

### 3b. The ladder's relaunch (second run)

Implementation Decisions 6 retries a job under a smaller footprint by relaunching the same job id,
and `--remain-after-exit` keeps the finished unit loaded until something unloads it, so
`systemd-run` would refuse the name. The host OOM job launched three times in a row, the third
without any cleanup in between:

```
attempt 2: oom_host (result=oom-kill)   attempts now 2
launching it a third time without a cleanup first, as a retry would:
attempt 3: oom_host   attempts now 3
```

A job that is still running is another matter, and is refused rather than doubled:

```
refused: job busy is already running as wayline-job-busy.service; poll or kill it before relaunching
after the kill: poll killed, job file killed
```

### 4. Two cancellations

A sleeper launched, polled `running`, then `kill(handle, hard=True)`:

```
$ systemctl --user kill --signal=SIGKILL wayline-job-cancelled.service
after kill: killed (result=signal exit_code=9)
Result=signal   ExecMainCode=2   ExecMainStatus=9
LoadState=loaded   ActiveState=failed   SubState=failed
job file status: killed
```

`Result=signal` with 9 and no `oom-kill` is a cancellation and not an OOM, which is the row of the
table that separates a job somebody stopped from a job the machine stopped.

**A graceful stop reads nothing like a cancellation (second run).** `systemctl --user stop` on a
transient unit blocks until the unit is gone and unloads it, so the very next poll reads the
unloaded unit:

```
right after stop: poll gone, job file killed
once it is gone: poll gone (result=success), job file killed
Result=success   ExecMainCode=0   ExecMainStatus=0
LoadState=not-found   ActiveState=inactive   SubState=dead
```

The job file keeps `killed` because the runner writes it at the kill and never lets a later poll
overwrite it. Without that the status would have become `gone` here, and `exited` on a unit that
stayed loaded: a cancellation is a fact about the harness, not a reading, and every backend reads
it as something else.

### 5. The `setsid` fallback

The same GPU OOM job through the fallback backend, which is what a box with no reachable user
manager gets:

```
setsid nohup env CUDA_VISIBLE_DEVICES=0 PYTHONUNBUFFERED=1 taskset -c 8-15 \
  sh -c '/usr/bin/python3 <tmp>/gpu_probe.py --gib 25 --hold 1; echo $? > <logs>/fallback.exit'
launched fallback as pid 1469248
state: oom_gpu   result=exit-code exit_code=1 reason=the log carries 'CUDA_ERROR_OUT_OF_MEMORY'
exit file: 1   pid file: 1469248
after cleanup: exit file removed
```

Pinning held inside the fallback too (`Cpus_allowed_list: 8-15`, from `taskset`). Two divergences
from research-notes 05 A5, both deliberate:

- The `.exit` and `.pid` files live beside the log, not in the jobs directory. The jobs directory
  is under `research/`, which only the ledger writes (Implementation Decisions 2); the log's
  directory is the one place a job already writes into.
- The note's `&` and `$!` are the backend's own `Popen`: started without a new session the child
  is not a process group leader, so `setsid` execs in place and its pid is the group leader's,
  which is what `kill -- -<pid>` needs and what the pid file records.

What it cannot see is unchanged: no `MemoryMax`, so no `Result=oom-kill`, so a host OOM arrives as
`failed`; and a job with neither an exit file nor a live pid reads `gone`, never `exited`.

**A cancelled fallback job (second run).** `setsid` execs in place, so the process group leader is
a direct child of whatever launched the job, and after a SIGKILL it keeps answering
`kill(pid, 0)` until someone waits on it. A dead job would then poll `running` forever and a
`wait` would never return, so the poll treats a zombie as gone:

```
launched pid 1825609; poll says running
after kill -KILL -- -1825609: poll gone (reason no exit file and no live pid; read the job file and the log)
the pid is state gone in /proc, and the exit file is absent
job file status: killed
```

The pid was already reaped here rather than left a zombie, because `subprocess` reaps the children
of `Popen` objects nobody kept whenever another subprocess starts, and this check ran one. The
zombie window is real all the same, so the suite forks a child of its own and asserts that a
zombie pid is not a running job.

### 6. `RuntimeMaxSec`, the spec's own addition to the launch line

Implementation Decisions 6 adds `RuntimeMaxSec` from the ticket's `wallclock_minutes` so a runaway
job frees its slot; research-notes 05 never tested it. A job that sleeps ten minutes with one
minute of wallclock:

```
launched wayline-job-runaway.service with RuntimeMaxSec=60
after 60 s: failed   result=timeout exit_code=15 reason=wallclock
Result=timeout   ExecMainCode=2   ExecMainStatus=15
LoadState=loaded   ActiveState=failed   SubState=failed
job file: status failed   attempt {..., "result": "timeout", "exit_code": 15, "oom": null}
```

Stopped at 60 s to the second, and `Result=timeout` decodes to `failed` with the reason
`wallclock`, as the spec says. The unit test's synthetic timeout reading is this one.

### The first run failed, and why (20:27 UTC)

The experimenter did everything but leave its touch set clean, and the conductor refused the
branch, which is the refusal working:

```
acceptance (worktree): pass
ticket 1 failed: the worker left 1 path(s) uncommitted in its worktree (sweep/_smoke/); the conductor integrates the branch, not the working tree (next: resume)
```

What the stream showed, and what changed because of it:

- `mkdir -p /tmp/smoke` and every `rm` were denied (neither is on any role's allowed tools), so the
  session smoke-tested into `sweep/_smoke/` and could not remove it.
- `wayline job add <<'EOF' ... EOF` was denied: the permission rule `Bash(wayline job add*)` does
  not admit a heredoc. The session wrote the spec into `sweep/_smoke/jobspec.json` and ran
  `wayline job add < sweep/_smoke/jobspec.json`, which was allowed.
- The three job files it wrote stayed `pending` after the ticket failed. That was a defect: a failed
  attempt's jobs now are cancelled (`job_cancelled`) when its outcome is carried.

The protocol (`prompts/roles/experimenter.md`) now has the spec written as a committed file in the
touch set and passed by path (`wayline job add sweep/jobs.json`), and smoke output written under the
git-ignored `results/smoke/`.
