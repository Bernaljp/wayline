## The dashboard's transport (ticket 11, criterion 2, prototype 36)

`wayline serve --port 8799` ran on 2026-09-12 on Python 3.12.3, Linux 6.8.0-117-generic, from the
harness worktree `.claude/worktrees/ticket-11-dashboard`, over a copy of `fixtures/ledger/`
registered in a temporary `WAYLINE_HOME`. The real dashboard stands in for the throwaway server of
the prototype ticket, as the criterion asks.

What it printed:

```

  ssh -o ServerAliveInterval=30 -o ExitOnForwardFailure=yes -N -L 8799:127.0.0.1:8799 KW61315
  proj             /home/bernaljp/.claude/jobs/006a546c/tmp/proj  (active)
  read-only in this milestone; ctrl-c stops the server
```

`~/.wayline/dashboard.json` afterwards, mode 0600: `{"port": 8799, "bind": "127.0.0.1", "token":
"..."}`. The token is minted once and kept across restarts, so a URL bookmarked on the laptop keeps
working; bound to loopback the views do not ask for it.

Every endpoint, with curl (`%{http_code} %{size_download} %{time_total}`):

| Request | Status | Bytes | Wall clock |
|---|---|---|---|
| `/` | 200 | 1119 | 1.1 ms |
| `/app.js` | 200 | 12253 | 1.1 ms |
| `/vendor/marked.umd.js` | 200 | 44870 | 1.1 ms |
| `/api/projects` | 200 | 298 | 1.1 ms |
| `/api/projects/proj/overview` | 200 | 6584 | 256 ms |
| `/api/projects/proj/journal?since=0` | 200 | 6469 | 1.0 ms |
| `/api/projects/proj/overview` with `If-None-Match` | 304 | 0 | 0.8 ms |

The overview's 256 ms is all of it the GPU utilization sampling of Implementation Decisions 6: the
free-slot rule needs two consecutive `nvidia-smi` readings 0.2 s apart, so every overview waits for
the second one. It is a sleep in one handler thread, not CPU, and at a 5 s poll it is 5% of one
thread; if it ever matters through the tunnel, the fix is to memo the resources reading for the
views interval rather than to weaken the two-sample rule.

Server CPU under load, measured the way `research-notes/08-dashboard-transport.md` measured it
(`utime+stime` from `/proc/<pid>/stat` over the window, six curl clients at 2 s):

| Polled | Clients | Window | Server CPU | Threads mid-window |
|---|---|---|---|---|
| `journal?since=<offset>` | 6 | 20 s | 0.00 s (below the 10 ms clock tick) | 1 |
| `overview` | 6 | 21 s | 0.00 s | 1 |
| `/` (the page) | 6 | 20 s | 0.00 s | 1 |

Two things the notes predicted and this confirms. The thread count stays at 1 with pollers, because
polling holds no per-tab thread (the note measured one thread per open SSE stream, lingering up to
32 s after the tab closed). And keep-alive works: two requests on one curl invocation reported
`1 connects` then `0`, which is `protocol_version = "HTTP/1.1"` plus an accurate `Content-Length`
on every response.

The server-sent-events alternative behind `?transport=sse`, live:

```
$ curl -sN "http://127.0.0.1:8799/api/projects/proj/journal?transport=sse&since=0"
retry: 2000

id: 206
data: {"ts":"2026-09-11T11:00:00.000Z","event":"run_started",...}

id: 363
data: {"ts":"2026-09-11T11:00:01.000Z","event":"pacing",...}
```

Unchunked with `Connection: close`, `id:` set to the journal offset after the line it carries (the
per-line offsets the note's fix produced, not the offset at the end of the read), `retry: 2000`, and
a `select()` dead-client check that ends the thread within one tick of the client closing. A
`Last-Event-ID` resumes with the line after that offset, so the server keeps no per-client state.
`tests/test_dashboard.py` asserts all of this over real sockets.

The page itself was rendered by a real browser (the Playwright-cached Chromium 1228,
`--headless --dump-dom`, with an `<img>` against a server that sleeps 8 s to hold the load event
open so the DOM serializes after the polls have answered, the same trick the research note used).
Polling, from the dumped DOM: one tab (`proj`, marked active, `aria-current="true"`), the overview's
fourteen fields (phase, autonomy, radius, window, both utilizations, the goal at `auroc 0.812 of
0.9 (up)`, the cpu slot at `loadavg1 0.43 of 128, 120 cores free`, the ram slot, `gpu slots 0 free
of 1`, and the ticket counts), the frontier (2 rows), running (1), jobs (1: `j-0001` on
`wayline-job-j-0001.service`), the open decision (`#10 Which split is held out?`, `subgraph`, asks
the human), and 26 journal lines in the tail. With `?transport=sse`: the same 26 lines, the note
reading `streaming, at offset 5846`, and no console message at any level.

That render caught the one defect the HTTP tests could not see: the decisions table treated a
ticket's `blocking` as a list of ids, when the schema makes it the scope a decision pauses
(`subgraph` or `all`), so `join` threw and the panel sat at "loading" with nothing in the console
for the owner to act on. Both are fixed: the field is printed as the scope it is, and the render
now sits inside the same `try` as the fetch, so a future render bug shows itself in the panel.

**Still open: the owner's reactions through the tunnel.** Criterion 2 asks for latency, dropped
streams, CPU on the workstation, and behavior when the laptop sleeps and wakes, as seen from the
laptop through `ssh -o ServerAliveInterval=30 -N -L`. That needs the owner and the laptop; the
workstation side is recorded above, and the line to paste is the one `serve` prints. Polling stays
the default until those reactions say otherwise (OPEN-20). What to write down when it is run: the
observed tail latency, whether the logs view felt annoying, what happened to the polling client and
to the SSE stream across a sleep, and whether `ExitOnForwardFailure` made the dead tunnel obvious.
