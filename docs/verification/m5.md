## Ticket 40: `wayline report` on a run that ended (2026-09-13)

What the ticket asks to be seen live: "the report for a fixture run that ended passes the linter".
The run is `fixtures/projects/ended-run/` (rebuilt by its `make.py`), copied to a fresh directory
under `/tmp` for each attempt, with `WAYLINE_HOME` pointed at a scratch directory, and
`python3 bin/wayline report --project <copy>` run with the real launcher (Claude Code 2.1.270,
logged in on claude.ai). The script that ran it printed the command's output, then each session's
`system/init` model and tool list, its `result` turns, duration, and permission denials, and every
`rate_limit_event`.

### Attempt 1: the writer on fable was refused by the weekly usage limit

`wayline report` with the shipped policy (writer `fable xhigh`) exited 1 after 6 s:

```
wayline report: the writer's answer could not be used: the result carries no structured_output (subtype success); the worker stopped without returning it
```

The writer's stream (`research/sessions/writer/1/stream.jsonl`):

- `system/init`: model `claude-fable-5-1`, tools `Glob, Grep, Read, StructuredOutput` (the read-only
  launch held: no write tool, no Bash, none of the owner's host tools).
- `rate_limit_event`: `status: rejected`, `rateLimitType: seven_day_overage_included`,
  `overageStatus: rejected` (`org_level_disabled`), `unifiedWindows`: `five_hour` 0.16,
  `seven_day` 0.64, `seven_day_overage_included` 1.
- `result`: 1 turn, 702 ms, `subtype: success`, no `structured_output`, no denials.

So a window can refuse one model while the five-hour and seven-day utilizations the pacing reads
are far below its thresholds: fable's own weekly allowance was spent. The first cut of the report
read the refusal as an unusable answer and failed the render. That is fixed: a session whose envelope
carries a `rejected` rate-limit event and no answer raises `UsageLimited`, which is never resumed;
a refused writer becomes a note and the report renders without its prose, and a refused classifier
leaves the sentences it did not reach unclassified (`tests/test_report.py`, `UsageLimitTest`).

### Attempt 2a: `--no-draft`, the real classifier

Exit 0 after 13 s:

```
linter    pass: 5 claim sentence(s), 5 tagged
```

- Classifier session: model `claude-haiku-4-5-20251001`, tools `StructuredOutput` only, 2 turns,
  10.8 s, no denials, rate limit `allowed` (five-hour 0.17, seven-day 0.64).
- One batch; the five finding sentences (four findings, one of them two sentences long, the negative
  result among them) were all classified `claim`, and each ends with the tags built from the manifest.
- `lint_report` on the `REPORT.md` on disk (citations read back into tags, classes from the cache):
  passed, 5 claims, 5 tagged, no problems.

### Attempt 2b: the writer moved to opus, then an offline rebuild

Because fable was refused, the copy's `harness.json` carried `"policy": {"roles": {"writer":
{"model": "opus", "effort": "xhigh"}}}`, so the writer path ran on a real session. Exit 0 after 75 s:

```
linter    pass: 11 claim sentence(s), 11 tagged
```

- Writer session: model `claude-opus-5`, tools `Glob, Grep, Read, StructuredOutput`, 17 turns,
  56.7 s, no permission denials; two `rate_limit_event`s, both `allowed` (five-hour 0.17 then 0.18,
  seven-day 0.64). It returned one paragraph for the group `SPEC.md#c1-interaction-terms` and one on
  the negative results. Every number it wrote is one of the findings', and every claim sentence ends
  with tags copied from the evidence it was handed. It sometimes put a space between two tags, which
  the linter accepts.
- Classifier session: `claude-haiku-4-5-20251001`, 2 turns, 14.5 s. Of the 13 distinct prose
  sentences, 11 were classified `claim`, one `transition` ("This group covers the feature table, the
  baseline model, and the same setup with pairwise interaction terms added."), and one
  `method_description` ("The depth experiment trained a model twice as deep as the baseline, with no
  interaction terms, over three seeds.").
- `wayline report --offline` on the same copy: exit 0 in under a second, the session count stayed
  at 2 (nothing launched), and the linter passed again with 11 claims, 11 tagged, from the two caches.
- `lint_report` on the file on disk: passed, 11 claims, 11 tagged.

Not run live: `wayline report --verify`. On this run it would take one verdict per tagged claim (11 of
them, all under the minimum of ten plus the difficulty-5 claims), on opus and fable. The sampling
rule, the gate, the journaled verdicts, and the writing tickets are covered by the suite with the fake
launcher (`SamplingTest`, `VerifyTest`). The writer on fable, the model the policy names, is still to
be seen live once its weekly allowance resets.

## Ticket 41: the toy project fixture (2026-09-13)

What the ticket asks to be seen live: "the experiment ticket runs with fake jobs in the suite and
on the GPU live." The fake half is `tests/test_toy_project.py`'s `RetryLadderTest`; this is the GPU
half, on an NVIDIA GeForce RTX 3090 (24576 MiB), driver 535.309.01, torch 2.14.0+cu126 from
`~/.wayline/tools/venv` (`wayline tools install`).

Copied out first (`cp -r fixtures/projects/toy /tmp/toy`), then, exactly as the fixture's own
`README.md` gives it:

```
WAYLINE_HOME=/tmp/toy-home bin/wayline init /tmp/toy --email you@example.org
WAYLINE_HOME=/tmp/toy-home bin/wayline absorb --level 0 --project /tmp/toy --fixtures fixtures/fetch
```

```
references  3  (3 verified, 0 unresolved)
  verified   query-2022-interaction-terms-improve-tabular-classification crossref
  verified   split-2020-held-out-evaluation-protocol-small      crossref
  verified   repo-2024-tiny-code-repository-reproducible-toy    arxiv
```

All three references of `research/INTAKE.md` resolved with no network reached, from the
recordings `fixtures/projects/toy/make.py` wrote under `fixtures/fetch/`.

### The experiment, at the shipped batch size

```
PYTHONPATH=/tmp/toy/src ~/.wayline/tools/venv/bin/python -m toy.train --seed 1 \
    --out /tmp/toy/results/toy/seed-1/summary.json
```

Exit 0 in 5.8 s (`user 11.5s`, two CPU threads feeding the one GPU):

```
auroc: 0.8503
```

`summary.json`:

```json
{
  "auroc": 0.8502984862625299,
  "batch_size": 256,
  "dataloader_workers": 0,
  "device": "cuda",
  "seconds": 4.0,
  "seed": 1
}
```

Comfortably past `GOAL.json`'s target of 0.82, the way the baseline of Implementation Decisions 14
is meant to be: reachable without the run needing to get lucky.

### The oversized configuration: a real GPU OOM

```
PYTHONPATH=/tmp/toy/src ~/.wayline/tools/venv/bin/python -m toy.train --seed 1 --batch-size 90000 \
    --out /tmp/toy/results/toy/seed-1/summary.json
```

Exit 1, no `summary.json` written, and on stderr:

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 30.18 GiB. GPU 0 has a total
capacity of 23.69 GiB of which 23.35 GiB is free. Including non-PyTorch memory, this process has
254.00 MiB memory in use. Of the allocated memory 0 bytes is allocated by PyTorch, and 0 bytes is
reserved by PyTorch but unallocated.
```

Two of `resources.GPU_OOM_SIGNATURES` appear verbatim (`CUDA out of memory`,
`torch.OutOfMemoryError`), which is what the conductor's OOM rule reads out of a job's log tail to
tell a GPU OOM from a plain failure (Implementation Decisions 6). The allocation that failed is
`toy.train.ready_interactions`'s diagnostic gram matrix at `--batch-size 90000`: `90000**2 * 4`
bytes is 30.2 GiB, more than the card has.

### The ladder's own override, same seed

`research/jobs/<id>.json`'s `retry.gpu_oom` names `{"--batch-size": "256"}` for exactly this job
(Implementation Decisions 6, `fixtures/ledger/research/jobs/j-0001.json`'s shape). Run by hand:

```
PYTHONPATH=/tmp/toy/src ~/.wayline/tools/venv/bin/python -m toy.train --seed 1 --batch-size 256 \
    --out /tmp/toy/results/toy/seed-1/summary.json
```

Exit 0 in 5.7 s, `auroc: 0.8503` again -- the same seed is the same data, so the ladder's recovery
is not a second, different result, it is the first attempt's answer, one batch size smaller.

Not run live: the conductor stepping the ladder itself (launching the retried job, reading the
log, writing the next attempt without a person choosing the override by hand). That mechanism is
outside this ticket's touch set; what this run shows is that the fixture's job, the log the fake
half of the suite scripts, and the real card's OOM all agree with each other.

## Ticket 58: the design pass over the dashboard (2026-09-16)

What the ticket asks to be seen: every view rendered in a real browser, before and after, over the
fixture ledger and over a project during a run, with the screenshots and what changed recorded here,
and no render logging a console message at any level.

The renders are `images/58/`, one `before-` and one `after-` file per view, taken in the same
browser at the same width on the same ledgers. Nothing in the server changed, so "before" and
"after" differ only in `dashboard/index.html`, `dashboard/app.js`, and `dashboard/style.css`: each
pass ran with one set of those three files in place, the other set held aside.

### How the renders were taken

`wayline serve --port 8791` from this worktree over a scratch `WAYLINE_HOME`, with three fixture
projects registered (`fixtures/projects/five-tickets`, `decision-branch`, `ended-run`, each copied
out of the tree first) and, for the run, two further copies laid out by `project.init_project` and
driven by `WAYLINE_LAUNCHER=fake` over the fixture's own `fake-worker.json` with its delays raised to
30 s, so that a wave is still running while the page is read. `project.init_project` is called rather
than `wayline init` so that no user unit is installed for a render (`WAYLINE_UNITS=none` does the
same for a process and its children), and the conductor runs under `WAYLINE_UNPINNED=1`, since this
worktree is on a branch rather than on the tag the fixture pins.

The browser is the Chromium that Playwright ships (Chrome for Testing 149.0.7827.55), headless, at
1440 x 900 for the per-view renders and 1280 x 800 for the narrow one, driven by a script that
navigates, selects each project's tab, opens a ticket page from a graph node and a log tail from
that ticket, and records every `console` message, every page error, and every response of status 400
or worse.

### The empty cases, in words

Every table and every list now goes through one of two helpers in `app.js`, `tableOrNone` or
`listOrNone`, each of which takes the sentence to draw when there is nothing: "no worker is
running", "no job has been queued", "no decision is waiting for an answer", "no ticket is ready to
launch: every open ticket is waiting on another", "nothing has been decided on this project yet",
"no file was packed for this ticket", "no event has been journaled for this project yet", and so on.
`tests/test_dashboard.py` fails if a view builds a `<table>` any other way, so a header row with
nothing under it cannot come back by accident. Loading and error states are drawn the same way, in
the panel they belong to: each panel says which of its own reads is in flight, and a failed read
replaces that panel's content with the error rather than leaving it saying "loading".

### The console

Before: one message per load, at error level, `Failed to load resource: the server responded with a
status of 404`. It is `/favicon.ico`, which the dashboard did not serve; `curl` against the running
server answers 404 for it. After: zero messages at any level, over all three fixture ledgers, over a
project during a run, in the light theme and in the dark one, counting console messages, page
errors, and any response of status 400 or worse. The icon is now an inline `data:` URI in the page,
so the browser asks for no file and nothing is fetched from outside the workstation.

### What did not change

No file under `wayline/` was touched, so every endpoint answers as it did, what is read-only stays
read-only, and every action still carries the token. The graph is restyled from the stylesheet by
matching the fills `wayline.dag.svg` writes, so `graph.svg` answers byte for byte as before; a new
status in `dag.STATUS_COLOR` without a rule in the stylesheet is a failing test rather than a node in
the prototype's colors. Markdown still reaches the page only through
`DOMPurify.sanitize(marked.parse(md))`, and the two vendored files and their digests in `VENDOR.md`
are untouched. `python -m unittest` passes, 2424 tests.
