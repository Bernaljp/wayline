## Ticket 40: `wayline report` on a run that ended (2026-09-13)

What the ticket asks to be seen live: "the report for a fixture run that ended passes the linter".
The run is `fixtures/projects/ended-run/` (rebuilt by its `make.py`), copied to a fresh directory
under `/tmp` for each attempt, with `WAYLINE_HOME` pointed at a scratch directory, and
`python3 bin/wayline report --project <copy>` run with the real launcher (Claude Code 2.1.270,
logged in on claude.ai). The script that ran it printed the command's output, then each session's
`system/init` model and tool list, its `result` turns, duration, and permission denials, and every
`rate_limit_event`.

### Attempt 1: the writer on fable was refused by the weekly usage limit

`wayline report` with the shipped policy (writer `fable xhigh`) exited 1 after 6 s:

```
wayline report: the writer's answer could not be used: the result carries no structured_output (subtype success); the worker stopped without returning it
```

The writer's stream (`research/sessions/writer/1/stream.jsonl`):

- `system/init`: model `claude-fable-5-1`, tools `Glob, Grep, Read, StructuredOutput` (the read-only
  launch held: no write tool, no Bash, none of the owner's host tools).
- `rate_limit_event`: `status: rejected`, `rateLimitType: seven_day_overage_included`,
  `overageStatus: rejected` (`org_level_disabled`), `unifiedWindows`: `five_hour` 0.16,
  `seven_day` 0.64, `seven_day_overage_included` 1.
- `result`: 1 turn, 702 ms, `subtype: success`, no `structured_output`, no denials.

So a window can refuse one model while the five-hour and seven-day utilizations the pacing reads
are far below its thresholds: fable's own weekly allowance was spent. The first cut of the report
read the refusal as an unusable answer and failed the render. That is fixed: a session whose envelope
carries a `rejected` rate-limit event and no answer raises `UsageLimited`, which is never resumed;
a refused writer becomes a note and the report renders without its prose, and a refused classifier
leaves the sentences it did not reach unclassified (`tests/test_report.py`, `UsageLimitTest`).

### Attempt 2a: `--no-draft`, the real classifier

Exit 0 after 13 s:

```
linter    pass: 5 claim sentence(s), 5 tagged
```

- Classifier session: model `claude-haiku-4-5-20251001`, tools `StructuredOutput` only, 2 turns,
  10.8 s, no denials, rate limit `allowed` (five-hour 0.17, seven-day 0.64).
- One batch; the five finding sentences (four findings, one of them two sentences long, the negative
  result among them) were all classified `claim`, and each ends with the tags built from the manifest.
- `lint_report` on the `REPORT.md` on disk (citations read back into tags, classes from the cache):
  passed, 5 claims, 5 tagged, no problems.

### Attempt 2b: the writer moved to opus, then an offline rebuild

Because fable was refused, the copy's `harness.json` carried `"policy": {"roles": {"writer":
{"model": "opus", "effort": "xhigh"}}}`, so the writer path ran on a real session. Exit 0 after 75 s:

```
linter    pass: 11 claim sentence(s), 11 tagged
```

- Writer session: model `claude-opus-5`, tools `Glob, Grep, Read, StructuredOutput`, 17 turns,
  56.7 s, no permission denials; two `rate_limit_event`s, both `allowed` (five-hour 0.17 then 0.18,
  seven-day 0.64). It returned one paragraph for the group `SPEC.md#c1-interaction-terms` and one on
  the negative results. Every number it wrote is one of the findings', and every claim sentence ends
  with tags copied from the evidence it was handed. It sometimes put a space between two tags, which
  the linter accepts.
- Classifier session: `claude-haiku-4-5-20251001`, 2 turns, 14.5 s. Of the 13 distinct prose
  sentences, 11 were classified `claim`, one `transition` ("This group covers the feature table, the
  baseline model, and the same setup with pairwise interaction terms added."), and one

  interaction terms, over three seeds.").
- `wayline report --offline` on the same copy: exit 0 in under a second, the session count stayed

- `lint_report` on the file on disk: passed, 11 claims, 11 tagged.

Not run live: `wayline report --verify`. On this run it would take one verdict per tagged claim (11 of

### The oversized configuration: a real GPU OOM

```
PYTHONPATH=/tmp/toy/src ~/.wayline/tools/venv/bin/python -m toy.train --seed 1 --batch-size 90000 \
    --out /tmp/toy/results/toy/seed-1/summary.json
```

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 30.18 GiB. GPU 0 has a total

254.00 MiB memory in use. Of the allocated memory 0 bytes is allocated by PyTorch, and 0 bytes is
reserved by PyTorch but unallocated.
```

Two of `resources.GPU_OOM_SIGNATURES` appear verbatim (`CUDA out of memory`,

tell a GPU OOM from a plain failure (Implementation Decisions 6). The allocation that failed is
`toy.train.ready_interactions`'s diagnostic gram matrix at `--batch-size 90000`: `90000**2 * 4`
bytes is 30.2 GiB, more than the card has.

```

    --out /tmp/toy/results/toy/seed-1/summary.json
```

Exit 0 in 5.7 s, `auroc: 0.8503` again -- the same seed is the same data, so the ladder's recovery
is not a second, different result, it is the first attempt's answer, one batch size smaller.

Not run live: the conductor stepping the ladder itself (launching the retried job, reading the
log, writing the next attempt without a person choosing the override by hand). That mechanism is
outside this ticket's touch set; what this run shows is that the fixture's job, the log the fake
half of the suite scripts, and the real card's OOM all agree with each other.

### The empty cases, in words

Every table, and every list a view can draw empty, goes through one of two helpers in `app.js`,
`tableOrNone` or `listOrNone`. Each takes the sentence to draw when there is nothing: "no worker is
running", "no job has been queued", "nothing has been decided on this project yet", "no file was
packed for this ticket", "nothing under figures yet", and so on. `tests/test_dashboard.py` fails if a
view builds a `<table>` any other way, so a header row with nothing under it cannot come back by
accident. Two lists are built without the helpers and need no sentence, since neither is drawn when
empty: a ticket's problems, and a decision's evidence.

The rest say their own words:
- **The board.** An empty column reads "none", and a project with no tickets says the board fills
  once the first one is written.
- **The graph.** A project with no tickets says the graph is drawn once the first one is written.
- **The intake list** says "nothing has been sent from this page yet" until a file is dropped on it.
- **The journal tail** says "reading the journal" while its first read is out. Once a read has come
  back with nothing, it says "no event has been journaled for this project yet"
  ([render](images/58/after-journal-empty.png)).
- **Over `?transport=sse`**, where there is no end of backlog to wait for, the tail says "the stream
  is open; no event has arrived on it yet" ([render](images/58/after-journal-over-sse.png)).

Loading and error states are drawn the same way, in the panel they belong to. Each panel says which
of its own reads is in flight, and a failed read replaces the panel's content with the error.

Two panels are drawn from reads that are not their own, and say so:
- **The board** needs the tickets and the overview's frontier. It says it is reading them until both
  have come, and shows whichever read failed.
- **The controls** are filled from the decisions view, and carry a line of their own for its reading
  and its failure.

The note that says how an action went stays in the header where ticket 35 put it, since it belongs to
the action the owner took rather than to a panel's reading.

### Which ticket goes where, and who says so

The board works from the server's answers wherever the server has one:
- The frontier column is the overview's frontier: the conductor's own list, not a second guess at it.
- A decision ticket waiting on the owner sits under "needs you" because the decisions view says it
  waits on the owner.
- The other columns are the ticket's own status. A status the board has no column for still shows,
  under waiting.

The graph works the same way. The server lays it out, and the browser draws the same layout again as
circles:
- each node keeps its column and its row;
- each edge keeps its ends;
- the fill the server chose is carried onto the circle.

If the drawing cannot be read back, the server's own SVG stands. The circles are drawn only while the
graph can be seen, since a hidden drawing cannot be measured. Choosing the graph view, coming back
from a ticket, and unfolding the section all draw it again.

The answer form on a decision ticket's page is the decisions panel's own card and form, so there is
one way to answer, shown in two places:
- It is offered for exactly the tickets the decisions view lists as open, which are the ones the
  `answer` action applies to.
- A ticket waiting on the owner that is not a decision ticket has nothing to answer and gets no form.
- Both forms send one draft, and what is typed in one shows in the other as it is typed.
- Submitting from the ticket page sends the same `answer` action, with the token in its header.
