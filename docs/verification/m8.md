### What differed from the research notes

- **pandoc-crossref on conda-forge.** Research note 03 measured pandoc 3.11 from conda-forge alone. Asked for `pandoc pandoc-crossref` together, the solver picked pandoc 3.9.0.2, because conda-forge's pandoc-crossref 0.3.25 declares `pandoc >=3.8.2,<3.10` while its binary says "built with Pandoc v3.11", and the filter then warned on every run: "pandoc-crossref was compiled with pandoc 3.11 but is being run through 3.9.0.2. This is not supported. Strange things may (and likely will) happen silently." The install therefore pins `pandoc=3.11` and adds pandoc-crossref with `--no-deps`; the warning is gone. The entry of pandoc-crossref records `built_with`, and a mismatch would add a `note` to it.
- **Newer versions than measured.** uv is the harness's own 0.12.24, not the owner's 0.11.29 in `~/.local/bin`; docling resolved to 2.140.0 where the owner's venv holds 2.126.0.

## Moving a project's environment (ticket 83, M8 criterion 14, the environment's half)

Run on 2026-10-19 on the same workstation (SingularityCE 3.8.1 at `/opt/singularity-3.8.1/bin`, with its setuid starter; Docker present but refused to this account, `permission denied while trying to connect to the docker API`) from the worktree of ticket 83, against a scratch project (`/tmp/wl83/proj`) and a scratch tools home (`WAYLINE_HOME=/tmp/wl83/home`), so the owner's tools home was never written. Times are wall clock from `date +%s.%N`, measured once each.

The scratch tools home got the harness's uv 0.12.24 and micromamba 2.9.0 (`wayline tools install uv`, 6.1 s; `wayline tools install micromamba`, 3.5 s) and R, a project's tool, after a yes (`wayline tools install r --yes`: R 4.5.3 with renv from conda-forge into `envs/r`, its explicit export kept as `locks/r.txt`, 41 s). The project had one ticket naming `software: [r]` and one locked Python package (`wayline tools package python six==1.17.0`, 2.3 s: `code/requirements.lock` holds `six==1.17.0`).

**The container, built without root.**

```sh
wayline switch --environment container --project /tmp/wl83/proj
```

It ran, in order:

1. `singularity build --sandbox .wayline/env.sandbox docker://debian:bookworm-slim`. The account cannot reach Docker, so the base came straight from the registry (15 s in the first probe).
2. The harness's micromamba and uv, the host's CA bundle, `locks/r.txt`, and `requirements.lock` were copied into the sandbox.
3. `singularity exec --writable --containall --bind <tools>/mamba/pkgs:/opt/wayline/pkgs .wayline/env.sandbox /usr/local/bin/micromamba create -y -p /opt/env --file /opt/wayline/locks/r.txt`.
4. `micromamba install ... python=3.12`, the `.venv`'s minor version.
5. `uv pip sync --python /opt/env/bin/python /opt/wayline/locks/requirements.lock`.
6. `singularity build .wayline/env.sif.new .wayline/env.sandbox` (13 s in the first probe), then a rename into place.

Then each version check ran inside the image:

- `/opt/env/bin/R --version` and `/opt/env/bin/Rscript --version` printed 4.5.3, which `tools.json` records;
- `/opt/env/bin/python --version` printed 3.12.15, minor 3.12 as in the `.venv`;
- `uv pip freeze` inside matched the lock.

Only then did `harness.json` say `"environment": "container"` and the journal get `control {command: environment, args: {environment: container, from: shared}, by: cli}`. The move took 122 s the first time and 118 s the second. The image is 483 MB.

After the switch:

- `WAYLINE_PROJECT=/tmp/wl83/proj wayline tools run rscript -- -e 'cat(R.version.string)'` ran inside the image and printed `R version 4.5.3 (2026-03-11)` (3.6 s);
- `wayline tools run python -- -c 'import six, sys; ...'` printed `3.12.15 1.17.0` (1.4 s);
- `echo '{"tool": "rscript", "command": ["-e", "cat(1)"]}' | wayline job add --ticket 1` wrote a job with `environment: container` and `command` `[/opt/singularity-3.8.1/bin/singularity, exec, --bind, /tmp/wl83/proj, /tmp/wl83/proj/.wayline/env.sif, /opt/env/bin/Rscript, -e, cat(1)]`. The project lay outside the home, which Singularity binds by default, so it is bound by name.

**What the live run changed.**

- The first move failed its check, and the project stayed in `shared`. conda-forge's Python brings `pip`, which `uv pip freeze` lists as `pip @ file:///home/conda/feedstock-root/...`, and the lock, frozen from uv's venv, does not hold it. The check now lets conda-forge's own installers (pip, setuptools, wheel) stand beside the lock, and fails on any other package.
- The first tool run then warned that `LC_CTYPE` and six more locale settings failed. The image holds no locale but glibc's built-in `C.UTF-8`, and the host's `LANG` came in with the command. Every tool and job in the image now runs with `LC_ALL=C.UTF-8`.

**A refused move.** With `# edited` appended to `locks/r.txt`, `wayline switch --environment conda` printed `the move to conda failed at 'build r': its lock /tmp/wl83/home/tools/locks/r.txt changed since r was recorded; the project stays in container` (0.6 s). `harness.json` and the journal were unchanged.

**The conda prefix and the venv, the same day.**

- `wayline switch --environment shared` took 0.5 s: the shared tools, checked.
- `--environment conda` built `.wayline/env` from `locks/r.txt` and `python=3.12` through the harness's micromamba and synced the lock into it (26 s, 1.5 GB). `wayline tools run rscript -- -e 'cat(R.home())'` then printed `/tmp/wl83/proj/.wayline/env/lib/R`.
- `--environment venv` built `.wayline/env-venv` through `uv venv --python 3.12` and `uv pip sync` (1.8 s), with R staying the shared one. `wayline tools run python` printed the venv's prefix and six 1.17.0.

**After the review fixes, the same day.** The image now runs with `--nv` and is checked as `.wayline/env.sif.new` before it replaces the old one. `wayline switch --environment container` from the venv took 96 s. `wayline tools run rscript` (2.6 s) and `wayline tools run python` (1.7 s) printed the same versions as before, with no warning. A second identical switch printed `the environment is already container` in 1.6 s, its locks unchanged.
