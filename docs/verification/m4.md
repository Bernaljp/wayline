### What the failing verdict did with the paths it was given

The question was one the work does not answer, and the session did not soften it. It read the
ticket file and `notes/alpha.md` with `Read`, then went to the diff on its own initiative
(`git log --oneline -5 -- notes/alpha.md`, then `git show fed1bd1 -- notes/alpha.md`) and
returned four findings, two of them blockers, each at a locator it had opened:

- `notes/alpha.md:1-2`, that the whole file is two bare tokens with no sentences in it.
- `notes/alpha.md (commit fed1bd1)`, that the commit which is ticket 3's work adds one line and
  no prose, so the criterion is unaddressed by the change itself rather than by the file's prior
  state. This is the distinction the gate exists for, and no one asked for it.
- the ticket's own `## Result` section, that it records the line added and the acceptance run and
  never claims the prose the criterion asks for, while the frontmatter says `status: done`.
- the ticket's `acceptance.machine`, at `minor`, that two `grep -qx` checks on bare lines are
  satisfiable in a way that pulls against the quality criterion beside them.

The fourth is about the ticket rather than the work, which is what the scope limit allows at
`minor` and refuses as a fail.

### Two facts about `dontAsk` that the role's tool list does not carry on its own

**An unallowlisted Bash command runs when it only reads.** Verdict 1's session ran
`grep -qx 'alpha extended' notes/alpha.md; od -c notes/alpha.md`, and verdicts 3 and 4 ran
`cat -A notes/alpha.md`. Neither `grep`, `od`, nor `cat -A` is covered by a
`Bash(...)` rule in `roles/verifier/wayline.json`, `permission_denials` was empty, and the output
came back. `docs/verification/m0.md` records the opposite outcome for the coder, where
`mkdir -p m0 && printf ... >> ...` was refused with `decision_reason_type: "mode"`. The
difference is what the command does, not whether a rule names it.

**A Bash command that writes is refused, inside the project and with no rule against it.** One
cheap `sonnet low` probe session on the verifier role was asked to attempt four things in order
and to report each outcome. `cat notes/alpha.md` and `wc -l notes/alpha.md` ran; `printf 'probe\n'
> notes/probe.txt` was refused, with `decision_reason_type: "subcommandResults"` and the message
"Permission to use Bash with command printf 'probe\n' > notes/probe.txt has been denied"; the
`Write` tool was not in the session's tool list at all. Neither file exists on disk. So the
verifier is read-only live, and the layer that makes it so is the permission system's own reading
of the command, with the absent write tools behind it, not the `Bash(...)` allowlist.

**The verifier's tool list is exactly five tools.** Read off `system/init` rather than guessed at:
`Bash, Glob, Grep, Read, StructuredOutput`. Verdicts 1 and 2 and the first probe showed a sixth,
`ToolSearch`, which was on neither of the role's lists and which exists to fetch the schemas of
deferred host tools; it is now in `disallowed_tools`, and verdicts 3 and 4 are with it there. The
coder's list does not name it either, and nothing here shows whether a tool fetched that way
would reach past `--disallowedTools`. That is a question for the guards (OPEN-5, OPEN-7), not an
answer this run has.

**Ten host tools did not reach the verifier.** `docs/verification/m0.md` records the coder's live
session inheriting ten tools from the owner's own configuration, because `--settings` adds to it
rather than replacing it. None of them is in the list above, so the role's denylist, which names
all ten, held.

The five-hour window's `rate_limit_event` arrived as `status: allowed` with `unifiedWindows`
present, as in M0 and M3; no verdict came near a limit.

## The recorded intake of the wayline-intake skill (ticket 28, criterion 4)

Ran on 2026-09-13 on Claude Code 2.1.270, nested inside an interactive Claude Code session. The
project was laid out by `wayline init` under a scratch `WAYLINE_HOME`, with the fixture's
`input/context/` (a paragraph of intent, three references, a three-row expression table) copied
into its root, and the session was launched there on the fixture's prompt:

```
claude -p "$(cat fixtures/skill/wayline-intake/input/prompt.md)" \
  --model opus --effort high --permission-mode dontAsk \
  --allowedTools Read Glob Grep "Bash(wayline intake*)" \
  --disallowedTools Edit Write NotebookEdit Agent WebFetch WebSearch "mcp__*" Workflow ToolSearch \
  --max-turns 100 --add-dir <harness> --output-format stream-json --verbose
```

The prompt opens with `/wayline-intake` and says the owner is not available for questions. The
skill was run three times, because the first two runs each found a way the skill's instructions
did not survive `dontAsk`. The skill was changed after each, and the third run is what
`fixtures/skill/wayline-intake/recorded/` holds.

| Run | Session | Turns | Wall clock | How it called the verb | Written |
|---|---|---|---|---|---|
| 1 | `2ae92901` | 5 | 48.2 s | `wayline intake --from - <<'EOF' ... EOF; echo "exit=$?"; cat research/INTAKE.md; git status --short` | nothing |
| 2 | `8d227364` | 9 | 63.6 s | the same heredoc alone, refused; then the same answers as options | `INTAKE.md`, `harness.json` |
| 3 | `8ac866e7` | 8 | 47.7 s | options, first time | `INTAKE.md`, `harness.json` |

**A command chained after the verb is refused whole.** Run 1 piped the spec in and chained the
read-back onto the same line. The permission system refused it, and nothing was written. The
session did not try another way to write the files. It told the owner the intake was not written,
explained why, and printed the command for them to run. The skill then said to run the verb on
its own and read the result back separately.

**A heredoc on stdin is refused under `dontAsk`, even on its own.** Run 2 sent
`wayline intake --from - <<'EOF' ... EOF` with nothing else on the line. The denial read
"Permission to use Bash has been denied because Claude Code is running in don't ask mode". The
session passed the same content as `--intent`, `--reference`, `--data`, and `--constraint`
options, and that ran. The skill now says to pass plain options when nobody is there to approve a
command. It keeps `--from -` for a session with the owner present.

**What the three runs agreed on is the behavior the fixture pins.** None wrote a `GOAL.json` or
invented a goal. Every assumption went into the constraints as an `Assumed:` line: the defaults
for autonomy and radius, the data staying on the machine, no held-out split. The three
references were listed exactly as given, which is what `intake_references` reads. All three runs
also noticed, without being asked, that two cells and three genes cannot answer the intent.
Runs 1 and 2 noticed that the references are not about gene programs, and run 3 said the same
more cautiously in its constraints. Each said a larger table or other references would be a data
or goal decision for the owner.

**Read-only commands ran, and `git -C` did not.** `cat`, `ls`, `head`, `wc`, `git status --short`,
and `git diff harness.json` all ran with no rule naming them, as the verifier's did above. Run 3's
`git -C <project> diff --stat` was refused, which is the only denial in the recorded run. That
matches the command guard, which treats `git -C` as a way to reach outside the working
directory.
