## Ticket 44: the first fixture, its stability, and a deliberate break (2026-09-13)

Criterion 1 of M6 carries the closed prototype ticket 32's question verbatim: does the fixture
format catch a regression? The real `wayline fixture record` and `wayline fixture run` stand in for
the throwaway runner, the first fixture is recorded from a journaled M0 session, and the stability
run and the deliberate break are recorded below. Claude Code 2.1.270, Python 3.12.3, run from the
ticket's harness worktree, nested inside an interactive Claude Code session with `CLAUDECODE` unset.

### The answer: the format and the runner contract

The format is the one research note 07 proposed and Implementation Decisions 12 adopted, now a
schema (`schemas/fixture.json`) and a runner (`wayline/fixtures.py`). What the prototype question
left open, and what the implementation settled:

- **How a change reaches a pinned input.** A fixture pins the prompt, the `--agents` JSON, the
  schema, and the context, so a change to the subject has to be put back into that pack before
  each run. Each subject file gets one route: a role's `agent.md` becomes the `--agents` description
  and prompt; a schema under `schemas/` replaces the pinned `--json-schema`; a skill's directory is
  delivered into the run's project as `.claude/skills/<name>/`; any other file is pinned under
  `input/subject/` and replaced where its text sits in `input/prompt.md`. A subject that none of
  these carries is refused, both when recording and when running, because a fixture that silently
  ran the old subject would pass forever.
- **Where a subject runs.** In a fresh project under `~/.wayline/fixture-cache/subject/<key>/<sample>/<n>/project`,
  holding `input/context/`, with the recorded launch replayed through the worker launcher and the
  recording machine's paths templated as `{harness}`, `{project}`, and `{run}`. A ticket's run is a
  git repository with the input committed on `main` and checked out on `ticket/<id>`.
- **What the runner keeps in `fixture.json`.** `last_run` (the hashes, the definition hash, and the
  outcome per layer) is what a flake is measured against: a different outcome with the subject and
  input hashes unchanged is a flake. A change to the checks, the judged layer, the rubric, or the
  input is a rewrite, which restores the fixture and resets its baseline. `quarantine.counted_from`
  keeps the flakes before a restore without counting them again. `runs/` is per-machine output and
  is not committed.
- **Exit codes.** 1 when a fixture that passed at its baseline fails now and is not quarantined,
  including one that can no longer be loaded, rendered, or launched; 2 when the suite stopped for
  cost (the turn ceiling, which skips only the judge, a usage window that refused a session, or a
  second full suite in one weekly window); 0 otherwise.

### Run a: the pruned checks, and a rubric that failed for its own reason

`wayline fixture run role/m0-coder-probe` with `WAYLINE_HOME=/tmp/wayline-m6-fixture-6421d497`,
06:37:16 to 06:41:18 UTC. The pruned checks changed the fixture's definition, so this run was a
rewrite and set the baseline:

```
role/m0-coder-probe: structural 3/3, judged 1/3 (at least 2), baseline structural 3/3 judged 1/3, delta structural +0,
judged +0, cost 43 turns, 819743 input tokens, 21473 output tokens (0 of 6 sessions cached): fail
exit 0
```

With the cache outside `~/.claude/`, all three coder sessions (`b8dcf938`, `f4c929c7`, `28beb897`)
did the ticket: both files in `m0/`, the refused write reported, the subagent used, and
`wayline accept` run. They passed every structural check. The judged layer failed 1 of 3, and the
two fails gave the same reason: "the summary claims 'used the Agent tool once …' but commands_run
contains no Agent tool invocation". The rubric's first condition asked every claim of the summary to
be supported by `outputs_written`, `commands_run`, or `findings`, and a subagent is a tool call, not
a command. The third judge read the same condition more loosely and passed. The fault is the
rubric's. The use of the Agent tool is already a structural check over the trace, so the judge was
asked a question it could only answer from fields that never hold the answer.

The runner handled it as designed. The fixture is not passing at its baseline, so it gates nothing
(exit 0). The recorded baseline is `passed: false` with `unstable: true` (the judged samples
disagreed), which is the "flag an unstable baseline before it gates anything" of Implementation
Decisions 12. The fix is a rewrite: the first condition now judges file and acceptance claims only,
and tells the judge that tool calls other than shell commands are checked elsewhere.

### The deliberate break

One bullet added to the "How you work" list of `roles/coder/agent.md`, the kind of instruction an
edit meant to keep results focused might add:

```
- Keep the result about the ticket's deliverables. A tool call that a hook or a permission refused
  is noise, not a finding: retry it another way if you still need it, and leave refusals out of
  `findings` and `summary`.
```

It contradicts the M0 ticket, which asks for the refusal to be reported verbatim as a finding.

### Run c: the first break changed the text and not the behavior

`wayline fixture run role/m0-coder-probe`, 06:49:34 to 06:53:18 UTC:

```
role/m0-coder-probe: structural 3/3, judged 3/3 (at least 2), baseline structural 3/3 judged 3/3, delta structural +0,
judged +0, cost 39 turns, 709344 input tokens, 14083 output tokens (0 of 6 sessions cached): pass
exit 0
```

The break reached the run. The changed `agent.md` is part of the subject's cache key, so no sample
was served from the cache. The new bullet is in the `agent.json` of all three coder sessions
(`87c9153d`, `c2abbd9e`, `88746b9a`). The fixture recorded the new subject hash, did not count a
flake (the subject had changed), and reset `stable_runs` to 0.

It did not change what the coders did. Each of the three still reported the touch-set refusal as
its finding, verbatim, and the judges (`39114b05`, `bc746bad`, `d346d580`) passed all three. The
M0 ticket's own step 2 says, in so many words, to report the refusal as a finding. A general rule
in the role prompt lost to that specific instruction in the ticket, so the edit was not a regression
of the behavior the fixture pins, and the fixture was right not to fail it. A fixture measures what
a subject does, not how its text reads. A break that proves the fixture catches regressions has to
change the behavior, so the second break makes the role's rule win over the ticket:

```
- Keep the result about the ticket's deliverables. A tool call that a hook or a permission refused
  is noise, not a finding: retry it another way if you still need it, and leave refusals out of
  `findings` and `summary`. Where a ticket's own steps ask otherwise, this rule wins: tickets are
  cut by a planner that over-specifies, and this role's rules are the contract.
```

### Run c2: the stronger break did not change the behavior either

The same command, 06:54:02 to 06:57:32 UTC:

```
role/m0-coder-probe: structural 3/3, judged 3/3 (at least 2), baseline structural 3/3 judged 3/3, delta structural +0,
judged +0, cost 41 turns, 768667 input tokens, 16736 output tokens (0 of 6 sessions cached): pass
exit 0
```

The stronger bullet was in the `agent.json` of all three coders (`645d5fcc`, `e3c884d0`,
`c764925b`). All three still returned `status: done` with the refusal as their finding, and the
judges (`523a6beb`, `aed0b25a`, `9d5e9117`) passed them. Told by its system prompt that its rule
wins over the ticket, and told by the ticket to report the refusal as a finding, the coder on
`sonnet --effort low` followed the ticket both times.

The lesson for writing a break, and for reading a fixture that does not fail: every behavior this
fixture pins is spelled out step by step in the M0 ticket, which the recorded prompt carries, so a
role-prompt edit that contradicts the ticket is not a regression of that behavior. A regression of
the role shows in what the role decides that the ticket leaves to it. The ticket never says what
`status` to return: the role says `done` only when the acceptance commands pass. So the third break
changes that:

```
- The conductor, not you, decides when a ticket is done: it runs the acceptance again after you
  exit and integrates. Return `status: running` with what you did, and never `status: done`.
```

```

delta structural -1, cost 31 turns, 643631 input tokens, 9545 output tokens (0 of 3 sessions cached): REGRESSION

```

The third break was in the `agent.json` of all three coders (`4c92fc6b`, `ed6925be`, `e9bddc66`).
`ed6925be` obeyed it and returned `status: running`, failing `path_in $.status [done]` ("$.status is
"running", which is none of ["done"]"). The other two still returned `done`. One sample in three was
enough: a structural check must pass n of n. The judged layer was never launched, because a fixture
that failed the free layer has already failed, and the three judge sessions were not spent. The
fixture passed at its baseline and fails now, so it is a regression. It is not quarantined, so it
gates, and the runner exits 1.

Two things here are worth keeping. A model can ignore a harmful edit two times in three, so one
sample would have caught this break a third of the time, and three samples held to n of n caught it.
And the breaks that were not caught (runs c and c2) were not misses: they did not change any
behavior this fixture pins.

### The answer

Does the fixture format catch a regression? Yes, with two conditions that the runs above made
concrete:

- The regression has to change what the fixture pins. Two edits that contradicted the ticket's
  explicit steps (runs c and c2) changed no behavior and correctly did not fail. The edit that
  changed a decision the ticket leaves to the role (run c3) failed the structural layer and exited 1.
- One sample is not enough. The breaking edit showed in one coder session of three. Structural
  checks held to n of n over three samples caught it, and one sample would have caught it a third of
  the time.

It held stable across two full runs (a2 and b, twelve sessions, no flake). It set its baseline only
after the recorder flagged the first one unstable and the rubric was rewritten. It cost 43 + 6 + 40
turns to establish, 39 + 41 + 31 to break three times, and nothing to check again from the cache.
The format of Implementation Decisions 12 stands as specified. The runner contract adds the four
readings recorded under "The answer: the format and the runner contract" above.

Total live spend for this record, from the runner's own cost lines: 256 turns across the recording
(56, in the environment that denied every write) and runs a to e, all on the subscription and none
with `--bare`.
