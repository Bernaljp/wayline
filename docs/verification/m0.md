### Deviations from the research notes

- None in the hook contract: `--settings` hooks fired in `-p` under `dontAsk`, exit 2 blocked
  the call, stderr became the model's denial reason, and the denial appeared in
  `permission_denials`, exactly as `research-notes/03-hook-shape.md` records from the smoke run.
- One trap worth writing down, found the first time this launch was run: the scratch worktree
  was under `~/.claude/jobs/...`, and the settings' own `Edit(~/.claude/**)` deny rule blocked
  the Write before any hook mattered. The model then reported the permission system's generic
  text, "File is in a directory that is denied by your permission settings", not the guard's.
  A deny rule fires ahead of the hook's message, so a guard's reason only reaches the model when
  no deny rule matches first. The worktree moved to `/tmp` and the guard's reason came through.
- Not verified here, and answered by ticket 06 below: whether the guards fire inside an `--agents`
  subagent (they do, with `agent_id` and `agent_type` in the stdin), and the hook stdin as seen
  under `--agent`.

### What the command guard deliberately does and does not reach

Written down here because the spec's phrase is "in any spelling", and the boundary matters
when a later milestone reads this.

- One deviation from Implementation Decisions 4, taken on purpose: the temporary directory is
  a write root alongside the worktree and `results/`. Scratch output (`2>/dev/null`,
  `> $TMPDIR/x`, `mkdir -p /tmp/...`) is routine, and a temporary file is not data, so losing
  one is not irreversible. `WAYLINE_ALLOWED_ROOTS` widens the set further per launch.
- The guard reads a command line, not a program. `python3 -c`, `perl -e`, an `ssh` command
  line and a container run are analysed as the invocation they are, never as the code they
  carry. The spec says the same, quoting the permissions documentation: a rule "doesn't apply
  to arbitrary subprocesses that read or write files indirectly, like a Python or Node
  script". What holds there is the role's tool allowlist and the absence of network tools.
- Where it cannot see, it blocks rather than guesses: a target path behind a variable or a
  substitution, an `rm` whose targets arrive on stdin, a pipe into a shell, a `cd` out of the
  worktree, and a command too long, too deeply nested, or too expensive to lex. The lexing
  budget exists because a timed-out `PreToolUse` hook does not block, so running past the
  30 second handler timeout would fail open.
- An independent review of the first cut found five families that slipped through, all now
  blocked and all in the case table: a shell reserved word or brace group in front of the
  command (`if true; then git push; fi`, `{ rm -rf /etc; }`), a here-string or heredoc into a
  shell (`bash <<< 'rm -rf /etc'`), `env -S` carrying the whole command, git's long-option
  abbreviations (`git reset --har`) and the short force pair (`git branch -d -f`), and curl's
  attached-value flags (`curl -XPOST`, `curl -dfoo`).

### Two things the launch needed that nothing had

Both were found by running it, and neither could have been found any other way, because neither
the smoke of ticket 03 nor the hook launches of ticket 04 went through the conductor.

1. **`--json-schema` refused the harness's own schema.** The first launch died before its session
   began, with `stream.jsonl` empty and one line on stderr:

   ```
   Error: --json-schema is not a valid JSON Schema: no schema with key or ref "https://json-schema.org/draft/2020-12/schema"
   ```

   Every file under `schemas/` opens with `"$schema": "https://json-schema.org/draft/2020-12/schema"`,
   and the CLI resolves `$schema` against the schemas it holds rather than fetching one. The
   smoke's schema is built in code and has no such key, which is why ticket 03 never met this. The
   flag now carries the schema without its meta-schema reference; nothing downstream wants the key,
   since the harness re-validates the result with its own validator, whose subset is a 2020-12
   subset by construction.

2. **`wayline` was not on the worker's `PATH`.** The contract line tells the worker to run
   `wayline accept`, the role's allowlist has `Bash(wayline accept*)`, and the stop guard blocks
   the stop until the file that verb writes exists, but nothing put the command where a worker
   could reach it. The harness `bin/` now goes first on the launch environment's `PATH`.

### The touch-set guard under `dontAsk`, and the allowlist beside it (criterion 2)

The one write outside the touch set was refused, in both runs, and `escaped.txt` is on no branch
and on no disk. The refusal reached the model verbatim, and the model quoted it back as a finding:

It is in the envelope as well, where the conductor reads it:

   "tool_input": {"command": "mkdir -p m0 && printf 'm0-note: plumbline-4f2a\\n' >> m0/skills-seen.txt && ..."}},

The first of those two is the allowlist, not a hook, and it is the more interesting one. The
worker tried to do the whole of step 1 in one shell command; `mkdir` is in no `Bash(...)` rule the

```json

```

The `permissions.deny` first layer was in the settings for both runs, quoted above, and neither
run gave it anything to catch: the ticket asks for no command on the list, and the allowlist has
no `git push` rule for one to reach past. The layer's live proof is the ticket 04 record, where a
`git -C . push` was put through it on purpose.

So the order is: the `PreToolUse` hook runs first and exits 0, meaning no decision, and the normal
permission flow then refuses the call on the allowlist. The command guard's own record shows the
same command passing through it a moment before the mode refused it. A hook's silence is not
permission, and an allowlist miss reads to the model as a `dontAsk` refusal rather than as a rule.
The worker recovered by using the `Write` tool instead, which is what the denial message suggests.

### The portability seam, by inspection (criterion 4)

One `launch` and one `resume` over a `LaunchRequest`, one of each per backend, one backend named
`claude_cli`, and no other place in the harness that starts `claude`. It is asserted rather than
described: `tests/test_worker.py`'s `SeamTest` walks the package's syntax trees for every `launch`
and `resume` definition and for every spelling of the executable, including a path-qualified one,
an environment-indirected one, and one inside a shell string.
