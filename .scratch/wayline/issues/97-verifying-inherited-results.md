# 97 - Verifying inherited results

**What to build:** Every inherited result (one inherited Results heading, all its claims judged together, a large one split by the planner) is verified. It is re-run, and then its wording is judged, so an overstated claim is narrowed to what the evidence shows. A gap that needs new experiments is a proposed `add`, not the verification's to close.

At every start midway, the critic proposes the objective "Do the inherited results hold?", open by default and human-only. The grill settles it, and the owner may park it. Specify drafts one claim per inherited result under it, and code answers it once every inherited result has a verdict or is unverifiable.

Each verdict names its route:

- **reproduced**: the project's own code at the commit intake recorded, changed only to run here;
- **ported**: the same logic in another language or runtime;
- **reimplemented**: written from the inherited Methods;
- **read**: a cited claim checked against its reference by the consultant, batched per reference, from the L0 abstract first. A claim the abstract cannot settle stays unchecked until its work is promoted under the budget.

A verdict reached on substitute data covers only the claim narrowed to that data. Contradictions that "95 - Repeated claims" attached to a result go into its verification. **Unverifiable** is a standing with its reason, apart from unchecked.

A verification ticket blocks every ticket built on its result. The planner wires the edge from the objectives' and concerns' ties, and an unverifiable result releases what it blocked.

The critic's memo gains a table: per inherited result, the code, data, and software it needs, each present or missing (fetchable data is not missing). The grill asks about every missing item in one setup question, each with the replies "I'll provide it", "rebuild it" (recommended wherever a rebuild can work), or "leave it unverified". Licensed software gets provide, port to Octave, or port to Python. After setup, a pending or newly found gap is a decision ticket offering provide, rebuild, or leave unverified, pausing only that verification:

- under `interactive` and `checkpoints` the owner answers;
- under `autonomous` the decider answers (rebuild or leave unverified, never provide), and a verification that ends `needs_human` makes its result unverifiable.

The fresh verifier at acceptance checks each verdict on an inherited claim explicitly.

Not part of this ticket:

- the setup's parser comparison of the stated methods and parameters with the code, whose disagreements go into these verifications, which is "108 - Methods generated by the inventory";
- the paper's supplementary table of verdicts and routes, which is "117 - Builds at the order".

**Blocked by:** 81 - Specify and the plan name objectives; 85 - The code repository; 93 - Inherited passages; 94 - Consulting one document; 96 - Critiques and concerns. It blocks 108, 109, 111, 115, and 117.
