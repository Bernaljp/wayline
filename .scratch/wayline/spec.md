## Problem Statement

The owner is a computational researcher who works alone on a workstation (one NVIDIA RTX 3090 with 24 GB, 128 cores, 1 TB RAM, 11 TB disk, Ubuntu with systemd 255 and user lingering enabled) with a Claude Code Max subscription and no API keys. A research effort starts anywhere between a vague direction with a pile of references and a precise plan with half an implementation, sometimes with a quantitative goal. Carrying it to a report today means the owner sits in the loop at every step: reading papers, deciding what to try next, launching experiments, waiting on them, checking results, and typing prompts into skills that call other skills and skip steps silently. Nothing keeps working when the usage window closes or the terminal dies. Nothing forces full reading of the papers that matter. Nothing stops a session from acquitting its own work. Nothing traces a claim in a report back to the file it came from. Every project leaks into the next through shared skills and carried-over context, and when the owner sees what should have gone better there is no safe way to make the pipeline change itself. The subscription also counts Fable, the model that the hardest tickets run on (and, until Opus 5.5, the planner, the decider, the writer, and the verifier of every Opus author), in a weekly window of its own apart from the all-models week; once that window is spent, every Fable request is refused until the weekly reset, days away, and a conductor that treats the refusal like a closed window for every model stops all of the night's work, not only Fable's. And a ticket that fails at one difficulty can only jump a whole level, from Sonnet straight to Opus or from Opus straight to Fable, when the same model at a higher effort would often do for less; the subscription is token bound, so the size of that step matters.

The first real project showed what v1.0 could not do. A research effort that starts midway, from a colleague's rejected manuscript with its referee reports, a separate Methods, a supplement, and half a MATLAB and Python repository, with no metric at all, could not get past intake: position and specify refused a project without a quantitative goal, a loose PDF became a reference and a Word file a data line, and a passing outage of arXiv's API was cached and replayed forever. Even a project that ran produced a report mostly about what the harness did rather than about the research (three quarters of the toy's report was the decider's rationale), with findings grouped by the ticket that made them and no plot of any result, and a paper only at the very end, written in one pass as one Markdown string with a reference list the writer typed itself. The owner wants soft objectives that results can reframe, reports on the research that are always current and explore every result in every useful plot, the paper's sections and outline growing with every ticket, inherited claims verified before anything is built on them, the code that backs the Methods published and reproducible, the software a project needs installed without root, a conversation in the dashboard where the owner sees things, and a paper compiled only on an explicit order.

## Solution

wayline is a harness repository and one command, `wayline`, that turns a research intent into `REPORT.md`, the stopping point, under the owner's subscription alone. Deterministic Python (standard library only) decides what runs, when, on which resources, and what counts as done; models decide only content, one ticket per fresh `claude -p` session in a conductor-owned git worktree, under `--permission-mode dontAsk`, a per-role tool restriction, and hooks that deny writes outside the ticket's touch set. Everything durable about a project is the ledger under `<project>/research/`, written only by the ledger module from structured results; the append-only journal is what the conductor replays to resume and what the report is built from. Experiments and analyses run as detached jobs under the user's systemd manager, pinned to assigned GPUs and cores, polled by code; no session waits. A recurrent tick relaunches the conductor after usage windows and answered decision tickets and reaches the owner's phone through Telegram. Type-A gates are judged by code; Type-B verdicts come from a fresh Claude session that carries none of the author's context, on a different model from the author whenever the model table's choice is available. When Fable's weekly window is spent, only Fable work is held: under the owner's fallback consent `auto` it runs on Opus at the same effort, marked as fallback; under `ask`, the default, the owner is asked; under `wait` it waits for the reset. A ticket's difficulty names a rung of an ordered list, a model and an effort cheapest first, a failed ticket climbs one rung at a time, and ticket work never runs above `high` effort. Every claim in the report carries a provenance tag the linter resolves. The owner steers from a local dashboard reached through one SSH tunnel, answers decision tickets from it or from the command line, raises autonomy at any moment, and files feedback that the evolve loop turns into tested, tagged harness changes, local to the project first and promoted to the harness only by the owner. On request the report continues into a paper under a chosen venue's guidelines. The build is eight tracer bullets, M0 to M7, each demoable on its own exactly as BRIEF.md Section 16 states.

v1.1.0 (Implementation Decision 17, milestone M8) carries an effort from any starting point to a paper. A project holds objectives, questions the research answers, and a goal is an objective with a measure; a stopping rule and real budgets set at setup end a run. Every ticket returns passages for the paper's five sections, which code writes and the owner can steer; findings cluster into results, each explored at rest points by a plotter session in every useful plot; code renders the general report on the research, a current report per result, the account of what wayline did, and the paper's outline, at no model cost. A project's own documents are sorted, deconstructed verbatim into inherited passages, and verified by reproduction, port, reimplementation, or reading, and critiques become concerns the work must answer. Workers check references through the scout as they work, and a surveyor searches the literature mid-run. The code that backs the Methods lives in `code/`, checked against Methods at every acceptance, and is cut into a private code repository the owner may publish. The harness installs the software a project needs without root and calls each tool only through its record. The owner talks with the project in the dashboard's chat or any Claude Code session through one `wayline` skill, marks batches in a marks view, and orders the paper, which is written as venue-free parts and compiled through pandoc for any venue; under `autonomous` the decider orders it at the run's end. A release that changes how a project is kept refuses older projects rather than migrating them.

## User Stories

1. As the owner, I want to give wayline anything I have (a vague direction, references, data pointers, a precise plan, half an implementation, an optional quantitative goal), so that the effort starts from where I am rather than from a form.
2. As the owner, I want a goal recorded only when its command printed its metric on an artifact the harness can produce (an objective with a measure, decision 17), so that I never chase an unmeasurable target overnight.
3. As the owner, I want a position memo before any decision is asked (closest prior work with verified citations, feasibility with my compute and data, what a hostile reviewer would say, three reformulations ranked by radius), so that I know whether the idea makes sense before a window is spent on it.
4. As the owner, I want the grill to ask me the whole frontier of open questions in tiers, each with a recommended answer and with facts looked up rather than asked, so that my time goes to decisions only.
5. As the owner, I want to say "this is enough, decide the rest yourself" at any moment, so that a max-effort decider resolves every open question and every decision ticket not marked `human_only`, each with rationale, confidence, and `decided-by: decider`, listed in the account until I let it stand or reverse it (decision 17).
6. As the owner, I want the autonomy setting (`interactive`, `checkpoints`, `autonomous`) and the radius (`strict`, `moderate`, `exploratory`) recorded in the project, so that the planner and the decider cannot wander beyond what I allowed.
7. As the owner, I want a spec with claims, anti-claims, experiments per claim, baselines, metrics, budgets, and seams, checked by code and by one independent verdict that every claim has an experiment and every experiment defends a claim, so that the ticket graph is cut from something sound.
8. As the owner, I want every ticket to carry a demo, machine acceptance commands, a touch set, a difficulty, a context pack, a role, and assigned skills, so that a fresh session can do it without me and code can tell whether it did.
9. As the owner, I want tickets whose touch sets intersect never to run at the same time, so that parallel workers cannot corrupt each other's files.
10. As the owner, I want a worker that needs to write outside its touch set to stop and report the path rather than write, so that the planner re-cuts the ticket instead of the worker widening it.

### 2. The ledger and the journal

- **The ledger module is the only code that writes under `research/`** (C3, seam 3). Every other module returns structured values and the ledger writes them: JSON and markdown by write-to-temp-then-rename; `journal.jsonl`, `findings.jsonl`, `qa_log.md`, and from decision 17 `passages.jsonl` by append. The one exception is the conductor's heartbeat `conductor.json`, rewritten in place under the lock, because its own `flock` is what keeps a second conductor off the project (decision 5) and a rename would move the locked inode out from under every later reader (ticket 09). Every write takes `fcntl.flock` on `research/.lock`, because the conductor, the tick, the dashboard, and the CLI verbs are separate processes that all write through this module.
- **The journal is the bus** (spec decision). Every process appends its events; the conductor remembers its own byte offset and, at the start of each wave, reads what others appended since (answers, `control` commands, feedback, autonomy changes) and applies them. Resume is the same replay from offset zero. The dashboard's journal tail uses the byte offset as its version (map ticket 08).

- **Ticket files** (BRIEF 8.2; format per OPEN-4, map ticket 15): `tickets/NN-slug.md` with a frontmatter in a restricted flat YAML subset written by code and parsed by the in-house parser, then a markdown body. The subset (spec decision): `key: scalar` (integer, boolean, `null`, bare or double-quoted string), `key: [a, b]` flow lists of scalars, `key: {k: v, ...}` flow maps of scalars, and one layer of block nesting whose children are `subkey: scalar`, `subkey: [..]`, or `- item` lines (this covers `acceptance`, `resources`, `goal_metric`, `budget`, and `outputs`). A `#` preceded by a space starts a comment outside quotes. No anchors, no multi-line scalars, no deeper nesting. The body carries `## Demo` and free prose; the ledger appends `## Result` after each attempt and `## Answer` on decision tickets. The fields are exactly BRIEF 8.2's: `id, title, kind, difficulty, status, blocked_by, blocking, human_only, touches, resources, role, skills, inputs, outputs, acceptance.machine, acceptance.quality, goal_metric, budget, context_pack, origin, proposed_by, demo`, plus `pinned_difficulty` (OPEN-12, map ticket 24: the human can pin) and `retry` (the footprint ladder of decision 6, experiment tickets only). Decision 17 replaces `goal_metric` with `goal` and adds `objectives`, `sections`, and `software`; ticket 81 made the first two: `objectives` lists the open objectives a ticket serves (empty for one no objective asked for), and `goal: "O2"` names the goal whose measure gives the metric and the direction a ticket reports.
- **Ticket kinds** (BRIEF 8.1): `dossier, lit, code, docs, experiment, analysis, figure, writing, review, decision, harness`, and `drawing` from decision 17 (a `dossier` ticket then runs as a promotion with no worker session, and a `lit` ticket on the surveyor). **Status** (BRIEF 8.2): `open, running, done, accepted, failed, blocked, needs_human, parked`. Transitions: `open` to `running` on launch; `running` to `done` when acceptance passed on `main` (or, for experiment tickets, when every job exited 0 and the outputs parsed); `done` to `accepted` on a passing Type-B verdict; `running` to `failed`, `blocked`, or `needs_human` from the result or the escalation; `failed` back to `running` on the next attempt; `open` to `parked` when the planner cut it beyond the radius cap or the owner parked it; `rerun` sets `open` with a new attempt counter; a decision ticket goes `open` to `done` when answered.
- **`graph.json`** is regenerated from `tickets/` by code at the start of every wave (one `os.scandir` snapshot decides whether anything changed) and holds, per ticket, the scheduling fields only: `id, kind, status, difficulty, blocked_by, blocking, human_only, touches, resources, role, skills, attempt`, and `software` on a ticket that names tools (ticket 82: it is launchable only once each is recorded). It is the only thing the conductor schedules from; the ticket file is the human view and the place a human pins a difficulty or answers a decision.

ticket 81 widens `spec` with `summary` and claims' `objectives`, and `ticket` and `plan` with `objectives` and `goal` in place of `goal_metric` (`objectives` required in a plan's tickets); ticket 82 widens `ticket` and `plan` with `software` (the tools a ticket needs, by name) and `job` with `tools` (the name, version, and lock digest of every tool a job calls); ticket 86 widens `result` with `passages` and its findings with `heading` and `replaces`, `ticket` and `plan` with `sections` (set by kind; a `writing` ticket's touch set empty), and `spec` with `gap` (the Introduction's passages on the gap, written at the confirmation); decision 17 names the schemas v1.1.0 adds, widens, and retires, and ticket 71 widens `dossier` with `retry` (service, failure, date, since, gave_up), `resolved_by: owner`, `notes`, the `names` a joined dossier records, the pointer's `joined_into`, the owner's `handed_over` answers, a `file` query kind, and the attempt outcomes `found`, `no match`, `failed`, and `skipped`. They are JSON Schema documents restricted to the subset the in-house validator implements (spec decision, because the standard library has no validator): `type`, `required`, `properties`, `additionalProperties`, `enum`, `const`, `items`, `minItems`, `maxItems`, `minimum`, `maximum`, `pattern`, `oneOf` of object schemas, and `$ref` within the same file. Every structured result a model returns is re-validated in code; the CLI's own `--json-schema` validation is not trusted alone (map ticket 01: a `success` envelope can lack `structured_output`).

### 3. The worker launcher (seam 1)

- **Interface.** One function `launch(request) -> Envelope` and one `resume(request, session_id, message) -> Envelope` over a `LaunchRequest` with `role, model, effort, prompt, agent_json, allowed_tools, disallowed_tools, settings_path, add_dirs, cwd, env, schema_path, max_minutes`. `Envelope` carries `session_id, model, structured_output (or None), is_error, subtype, num_turns, duration_ms, duration_api_ms, usage, model_usage, permission_denials, api_error_status, rate_limit_events (list), exit_code, stream_path`. Backends: `claude_cli` (the only real one) and `fake` (tests). Nothing else in the harness starts `claude`; this is the portability seam for another subscription CLI (BRIEF Section 14), and M0 leaves it at that.
- **Every model call goes through it**: workers, the verifier, the consultant (from `wayline consult`), the decider, the planner, the critic, the synthesizer, the evolver, the absorb session, the sentence classifier, the fixture judge. The fake backend therefore fakes all of them.
- **Launch** (OPEN-1, map ticket 12; map tickets 01, 02, 03, 16, 17; BRIEF Appendix B). With `RUN = <project>/research/sessions/<ticket>/<attempt>`:

  ```bash
  git -C "$PROJECT" worktree add -b "ticket/$ID" ".worktrees/$ID" main
  cd "$PROJECT/.worktrees/$ID"
  TICKET_TOUCHES="<colon-separated touch set>" TICKET_ACCEPTANCE_FILE="$RUN/acceptance.json" \
  WAYLINE_PROJECT="$PROJECT" WAYLINE_TICKET="$ID" WAYLINE_RUN="$RUN" CLAUDE_CODE_DISABLE_LEGACY_MODEL_REMAP=1 \
  claude -p "$(cat "$RUN/prompt.md")" \
    --agents "$(cat "$RUN/agent.json")" --agent "<role>" \
    --model "<the rung's model>" --effort "<the rung's effort>" \
    --permission-mode dontAsk --permission-prompts none \
    --allowedTools <the role's allowed_tools> \
    --disallowedTools <the role's disallowed_tools> \
    --settings "$RUN/settings.json" \
    --add-dir "$HARNESS" --add-dir "$PROJECT" \
    --output-format stream-json --verbose \
    --json-schema "$(cat "$HARNESS/schemas/result.json")" \
    --fallback-model sonnet \
    < /dev/null > "$RUN/stream.jsonl" 2> "$RUN/stderr.txt"
  ```

  `agent.json` is `{"<role>": {"description": "...", "prompt": "<role system prompt>", "model": "<alias>", "effort": "<effort>", "maxTurns": <by budget>, "permissionMode": "dontAsk"}}` with no `tools` and no `skills` key (map ticket 01: `skills` in `--agents` did not inject when the agent runs as the main session). `--add-dir "$PROJECT"` is passed because a worktree cwd does not discover the main checkout's `.claude/` (map ticket 01); it also grants file access to the project root, which is harmless because the touch-set guard denies writes outside the touch set regardless of access. `--fallback-model` never fires on usage limits (map ticket 02); it covers overload only. `CLAUDE_CODE_RETRY_WATCHDOG` is left unset so workers fail fast and the conductor owns the wait. `< /dev/null` avoids the 3 s stdin wait. Worktrees branch from `main`; the conductor never fetches or pushes (spec decision: pushing is on the irreversible list, and a project may have no remote).
- **The prompt** is assembled by code in this order: one `/wayline-<skill>` line per assigned skill at the top (map ticket 01: this is what injects a skill; if M0 finds only the first expands, the remaining skills' bodies are inlined under a heading); the ticket restated (title, kind, demo, touch set, acceptance commands, budget); the context pack (each file's contents under a header with its locator, in the ticket's order, cut at the cap of the rung's model family with the cut noted); the role protocol from `prompts/`; the result schema and the instruction to return it through the structured output; the contract lines: "write only under the touch set; run `wayline accept` before you stop; commit on the ticket branch; never integrate, never close the ticket, never edit `research/`; ask the consultant with `wayline consult <slug> "<question>"`, at most five times".
- **The stream** is kept whole in `stream.jsonl`. The conductor parses `system/init` (`session_id`, `model`; journaled as `ticket_session`), every `rate_limit_event` (`rate_limit_info.status`, `resetsAt`, `rateLimitType`, `unifiedWindows.five_hour.utilization`, `unifiedWindows.seven_day.utilization`, `unifiedWindows.*.resetsAt`; the `unifiedWindows` block is observed, not documented, so its absence degrades to `status` and the `/usage` reading), and the final `result` message, which it copies to `result.json`. The validated object is `structured_output`; a `success` result without that key, or `subtype: error_max_structured_output_retries`, is an invalid result and triggers one resume with the error text (BRIEF 9.1). A `rateLimitType` of `seven_day_overage_included` is Fable's weekly window, which only a Fable request's own event carries; a subagent's failed task (`task_updated` with `status: failed` and `error: rate_limit`) inside an allowed session is parsed as that subagent's refusal, because the parent's `result` stays a success (decision 15).
- **Resume**: `claude -p "<message>" --resume <session_id>` with `--agents`, `--settings`, `--permission-mode`, `--permission-prompts`, `--allowedTools`, `--disallowedTools`, `--add-dir`, `--fallback-model`, `--output-format`, `--json-schema` passed again (map ticket 01: not restored); the `--agent` choice is restored; `--system-prompt-snapshot` stays at its default. A worker whose process died (exit 143, or the pid gone after a conductor restart) is resumed when `system/init` was seen and relaunched otherwise. After a conductor restart, a worker whose pid is still alive and whose environment still names its session directory (`WAYLINE_RUN`) is re-adopted by tailing its `stream.jsonl` for the final result, and so is a worker, alive or not, whose stream already holds that result; both are journaled `ticket_resumed` with `reason: readopted`. A dead one without a result is journaled with `reason: worker_died`, carrying the session id it is resumed by, or none when it is relaunched in the same attempt; while the run is paused or stopping, that resume or relaunch waits (ticket 09). A worker that exceeds `budget.max_minutes` is sent SIGTERM, journaled `ticket_resumed` with `reason: timeout`, resumed once with "you ran out of time; return the structured result now", and then escalated. A session a usage window refused before its first turn is never resumed, verdicts included: it is relaunched (decision 15).
- **Models** are passed as a rung's `model`, a CLI alias (`haiku`, `sonnet`, `opus`, `fable`) or a full version name, with the legacy remap turned off so that a retired name fails instead of running on its family's newest; `system/init` echoes the name asked for, so the model that ran is read from the result's `modelUsage`, compared with the rung's, and journaled when it differs (decision 16). A Fable launch that falls back (decision 15) is passed `opus` at the same effort, and every agent its `agent.json` defines on `fable` is launched on `opus` with it.
- **Nested launches** are fine (map ticket 01): tests, `wayline consult` from inside a worker, and the evolve loop all launch `claude -p` from inside a session.

### 4. Guards and permissions (OPEN-5, map ticket 17; OPEN-7, map ticket 19; map ticket 03)

- **Per launch** the conductor writes `settings.json` from `hooks/worker-settings.json` with `${CLAUDE_PROJECT_DIR}` replaced by the absolute harness path (hooks and settings load from the worktree cwd only, with no parent fallback). The shape, verified live on 2.1.268:

  ```json
  {"hooks": {"PreToolUse": [
      {"matcher": "Write|Edit|NotebookEdit", "hooks": [{"type": "command", "command": "<harness>/hooks/touch_set_guard.sh", "args": [], "timeout": 30}]},
      {"matcher": "Bash", "hooks": [{"type": "command", "command": "<harness>/hooks/command_guard.sh", "args": [], "timeout": 30}]}],
     "Stop": [{"hooks": [{"type": "command", "command": "<harness>/hooks/stop_guard.sh", "args": [], "timeout": 30}]}]},
   "permissions": {"deny": ["Bash(git push *)", "Bash(git push)", "Bash(git reset --hard *)", "Bash(rm -rf *)", "Bash(rm -fr *)", "Edit(//etc/**)", "Edit(~/.claude/**)"]}}
  ```

  `args: []` runs the script in exec form; the 30 s timeout matters because a timed-out `PreToolUse` hook does not block. Hooks from `--settings` apply in `-p` and inside subagents (`agent_id`, `agent_type` in the input); a `SubagentStop` matcher, if ever added, must accept `workflow-subagent`.
- **Touch-set guard**: `research-notes/03-hooks/touch_set_guard.sh` as validated (reads `tool_input.file_path` or `notebook_path`, resolves with `realpath -m` against `CLAUDE_PROJECT_DIR`, exits 2 with the path and the touch set on stderr, fails closed when `TICKET_TOUCHES` or the path is missing, directory entries match below, file entries match exactly, `jq` required). Touch sets are relative to the worktree root or absolute; an `experiments/ablation_bX/` prefix trick does not match `experiments/ablation_b/`.
- **Command guard** (new in M0): reads `tool_input.command`, normalizes it (strips leading `VAR=` assignments, `env`, `sudo`, `nice`, `xargs`, `sh -c`/`bash -c` wrappers, `$(...)` bodies, pipelines and `&&`/`;` segments, and absolute paths to `rm`, `git`, `find`, `chmod`), and exits 2 on: `git push` in any spelling including `git -C <dir> push`, `git reset --hard`, `git clean -f`, `git branch -D`, `git worktree remove`, `rm -r`/`rm -rf`/`rm -fr` outside the touch set, `find ... -delete`, `chmod -R`, `truncate`, `dd of=`, `curl`/`wget` with an upload flag (`-T`, `--upload-file`, `-d`, `--data`, `-F`, `--post-data`), `pip upload`, `twine`, `gh pr`, `gh release`, `gh repo create` and every other `gh` write (decision 17), and any command whose target path resolves outside the worktree and `results/`. `permissions.deny` is the cheap first layer for the literal spellings; the guard is the second (map ticket 03: deny rules miss `/bin/rm`, `bash -c`, `git -C`).
- **Stop guard**: `research-notes/03-hooks/stop_guard.sh` as validated. The contract is settled here (an M0 open item in map ticket 03): the conductor exports `TICKET_ACCEPTANCE_FILE=$RUN/acceptance.json`; `wayline accept`, run by the worker inside the worktree, executes the ticket's `acceptance.machine` commands with `shell=True`, each under `policy.acceptance_timeout_s`, and writes that file (`ran_at`, `where`, `results: [{cmd, exit_code, seconds, tail}]`, `pass`); the guard blocks the stop once while the file is missing and always allows it when `stop_hook_active` is true. The conductor never trusts the worker's file: it reruns acceptance itself after the worker exits.
- **Tool restriction per role** (defaults in `wayline.json`, overridable per project): a `coder` gets `Read, Edit, Write, Glob, Grep, Agent, Bash(python *), Bash(python3 *), Bash(pytest*), Bash(ruff *), Bash(git add *), Bash(git commit *), Bash(git status*), Bash(git diff*), Bash(git log*), Bash(ls *), Bash(cat *), Bash(wayline accept*), Bash(wayline consult *)` as `allowed_tools` and `WebFetch, WebSearch, NotebookEdit` as `disallowed_tools`; an `experimenter` adds `Bash(wayline job *)` (the verb that writes a job file for the runner) and `Bash(nvidia-smi *)`; the `verifier`, `critic`, `consultant`, `reader`, and `decider` get `Read, Glob, Grep` only, with `Edit, Write, NotebookEdit, Bash, Agent, WebFetch, WebSearch` disallowed. No worker has network tools: fetching is the scout's job, in code (spec decision: network writes are irreversible, and reads are the scout's).
- **The irreversible list** (OPEN-7, map ticket 19): delete or overwrite data, force-push, push to shared branches, exceed the compute or usage budget, spend money, change the goal or the data, change the harness globally, any network write beyond fetching sources. Decision 17 narrows "change the goal" to "change a goal's measure", adds changing the stopping rule or raising a budget after setup and making the code repository public, and lets code (never a worker) push the code repository's split to its private remote. Enforced by: the deny list and the command guard (git and deletion), the absence of network tools (network writes), the resource manager and the pacing thresholds (budgets), `human_only` on goal and data decisions, and the rule that a global harness change under autonomy `autonomous` is proposed, not applied. Default autonomy is `checkpoints`; `human_only` classes default to decisions that change the goal or the data, extendable at intake; the class `ladder` joins them while the ladder consent is not `auto` (decision 16). Decision 17 renames the class `goal` to `objective`, lets setup name `concern`, and adds the decision class `software`.
- Containers are deferred (map ticket 17); nothing in M0 to M7 needs one.

### 5. The conductor (seam 4)

- **Process.** `wayline run` is one process, foreground by default, or the transient unit `wayline-conductor` with `--detach` (a plain `systemd-run --user --unit=wayline-conductor -p WorkingDirectory=<harness> <python> -m wayline run --resume`, no `--collect`; the tick relaunches it the same way). The unit also loads `~/.wayline/env` with `EnvironmentFile=-` and carries the caller's `PATH` and `WAYLINE_*` variables, because a transient unit starts from the manager's environment, not the caller's, and the manager's `PATH` lacks `~/.local/bin` where `claude` lives (ticket 13). It writes the heartbeat `research/conductor.json` (`pid, started_at, last_wave_at, harness_tag`) every poll. Two conductors on one project are prevented by `flock` on `research/conductor.json`. `run` refuses to start when the harness checkout's tag (`git describe --tags --exact-match`) differs from `harness.json`'s `harness_tag`, or when `git status --porcelain` on `main` shows changes outside `research/`, and prints the command to fix each.
- **A wave** is one pass of the loop (BRIEF 9.1), and the loop wakes every `policy.poll_seconds` (60). Tests call the wave function directly; sleeping and the window wait live in the `run` verb around it, not inside it (spec decision, so that no test sleeps). The steps, in order:
  1. Read the journal tail since the last offset; apply `control`, `decision`, `feedback`, and `switched` events; regenerate `graph.json` if `tickets/` changed.
  2. Poll every job in `jobs/` (decision 6): exited jobs with parsed outputs close their tickets as done; OOM failures step the ladder; other failures fail the ticket.
  3. Poll every running worker: a final `result` message in its stream, or a dead pid, produces an outcome (below).
  4. Answered decision tickets: journal nothing new (the `decision` event already exists), mark them done, and unblock their subgraph.
  5. Admit proposals (below) and create the tickets the workers requested; create decision tickets from `decision_requests`; under autonomy `autonomous`, launch the decider for open decision tickets not marked `human_only`.
  6. Goal check: with `stop_when: goal_reached` and the best kept `progress` value at or beyond `target` in `direction`, journal `run_ended` with `goal_reached` and go to P6. From decision 17 this step reads the stopping rule and the budgets, and an empty frontier with an objective the rule waits on opens the empty-frontier decision ticket.
  7. Frontier: open tickets whose blockers are all `done` or `accepted` (a difficulty-5 blocker counts only when `accepted`; spec decision from BRIEF 8.4's "accepted only after it"), minus tickets blocked by an open decision ticket, minus everything when a `blocking: all` decision ticket is open. Launchable: the frontier minus tickets whose touch set intersects a running ticket's, minus tickets whose job resources are not free.
  8. Pacing: compute the action from the latest utilization (decision 5, pacing); when the action is `stop` or the run is paused, launch nothing that needs a model; while Fable's weekly window is held (decision 15), drop only the launches on Fable, which fall back or wait as the fallback consent says; under `cheap_only` every launch runs one rung down, except an attempt that is itself a tier up (decision 16); subscription-free work (jobs, machine checks, index builds, report rendering) proceeds first.
  9. While launchable is non-empty, worker slots are free (`max_parallel_workers`), and the action allows it: pick by critical-path length (longest chain of dependents), then the objective class (decision 17, ticket 81: 0 for a ticket serving an objective the stopping rule waits on, 1 for another open objective, 2 for none; which objectives are open is `objectives.json`'s, and until `stop_when` lands the rule is its default, every open objective), then difficulty, then id; allocate resources for job-bearing tickets; add the worktree; launch; journal `ticket_launched`.
  10. Stall check (below). Commit ledger changes to `main`. Write the heartbeat. If the frontier is empty, nothing is running, and no job is pending: P6 (verdicts on every claim), P7 (report), `run_ended` with `frontier_empty`. From decision 17 the run-end gates (drawings, sampled verdicts, the kill argument on the general report) run at each end as that decision says, and P7 retires.
- **Worker outcome** (BRIEF 9.1): validate the envelope and the result against `result.json` (invalid: resume once with the error, then treat as failed); run acceptance in the worktree (fail: resume once with the output, then escalate); integrate (below); the ledger writes the findings (refusing any whose provenance is unmanifested), sets `done`, journals `ticket_done`, removes the worktree; quality criteria and difficulty 3 to 5 queue a Type-B verdict (decision 11), whose pass sets `accepted`; `proposals` go to admission; `decision_requests` become decision tickets; `goal_progress` runs the keep-if-better protocol; `touched_outside_declared` non-empty or `blocked_on` set marks the ticket `blocked` with the path for the planner to re-cut; `needs_human` notifies. A `running` result (experiment tickets) records the job ids and leaves the ticket running for the job poller.
- **Integration protocol** (M1; spec decision on the details): one integration at a time under the ledger lock. In the worktree, `git rebase main`; on conflict, `git rebase --abort` and launch the integrator role once in the worktree with the conflicting paths as its touch set and the conflict markers as its context, then rebase again; a second conflict fails the ticket with `next: split`. The integrator runs `git rebase main` itself and resolves it, because a resolution committed on the old branch would meet the same conflict when the commit that conflicted is replayed; the conductor's second rebase is the check (ticket 08). Its session is not journaled as a `ticket_*` event, and it waits, like any model work, while the run holds launches. After a clean rebase, rerun acceptance (`where: rebased`); then `git -C "$PROJECT" merge --ff-only ticket/<id>` on `main`, rerun acceptance on `main` (`where: main`), journal `integrated` with the commit, delete the branch and the worktree. A kept-if-better decision that discards keeps the branch and skips the fast-forward.
- **Escalation** (BRIEF 8.4; OPEN-12, map ticket 24; decision 16): on a failed attempt, resume the same session once with the failure output; then, while the next rung is on the same model family as the attempt's, relaunch one rung up (new attempt, new session) before filing a planner ticket to split it, and when the next rung is on Fable, split first and tier up after; then `needs_human` (the owner's orders: on 2026-09-17 the split came before the tier up because a tier up to Fable is the dearer step, and the finer tiers map then put a one-rung step inside a family, at about 1.3 to 1.6 times the cost, before a split that duplicates the context across two or more sessions; BRIEF 8.4 gave the tier up first). A split that fails goes on to the tier up, a tier up that fails goes on to the split, and a ticket a split cut is never split again. A kind that fails twice at a difficulty level raises that kind's default difficulty by one level for the rest of the run (`difficulty_raised`), unless the ticket's `pinned_difficulty` is set; the rung follows from the level. A failure on a launch that fell back (decision 15) counts toward the ticket's escalation and never toward `difficulty_raised`. The step the chain takes is the `next` of the ticket's last `ticket_failed`, which each wave acts on, so a restart climbs on where the chain stood; a failure met after the session returned (a job, a verdict) is resumed in that session with the failure output; a pinned ticket skips the tier up, and a ticket on the top rung has none, so its chain falls through to `needs_human` with `reason: top_rung` once the split has been tried; failures are counted by the `difficulty` on `ticket_launched`, and only once the attempt's resume is behind it (a `ticket_failed` with `next: resume` does not count); a tier up lands one rung above the attempt that failed, whatever the kind was raised to, and onto a held Fable rung it falls back, waits, or asks as the fallback consent says; a failed acceptance journals `ticket_failed` with `next: resume` before its resume (ticket 38). Outcomes also feed the registry's outcome record for the skills involved.
- **Stall** (BRIEF 9.7; spec decision on counting): a settling wave is one that processed at least one worker or job outcome. The stall counter increments on each settling wave that produced no `ticket_done`, no `finding`, no `progress` with `kept: true`, and no `job_finished` with `outputs_ok: true` (a sweep finishing one job a wave is progress; ticket 19), and resets on any of them. At 2, journal `stall` and file a replan ticket for the planner (it reads the journal and the failures; the conductor runs the cut `wayline plan --replan` runs, once the run may launch the planner, ticket 38) or, in radius `strict`, journal `run_ended` with `stall_strict` and render the report. The conductor journals `wave` (`number`, `outcomes`, `progressed`) at the end of every settling wave, which is what a restart rebuilds the counter from, and the count starts again after a `stall` (ticket 09).
- **Keep-if-better** (map ticket 39; per goal from decision 17, the measure read from `objectives.json`): for every ticket whose `goal` names an open goal whose measure has `GOAL.json`'s metric and direction (`goal_metric` before ticket 81), a Type-A evaluation script named in `GOAL.json` (`eval_command`, receiving the held-out split and the ticket's outputs) computes the metric per seed; the change is kept (fast-forwarded) only if the mean improves in `direction` over the best kept value by more than one standard deviation across at least three seeds; otherwise `discarded` is journaled with the metric, the branch stays, and the findings enter `findings.jsonl` as negative results. Revival is only by a new ticket citing new evidence.
- **Proposals** (BRIEF 9.5; OPEN-13, map ticket 25): admitted when inside the radius (`strict` admits only tickets tracing to a spec claim; `moderate` adds follow-ups probing a claim's failure; `exploratory` adds new directions gated on a scout novelty check), not a duplicate (mechanical comparison first: same kind and normalized-title similarity above 0.8 or identical touch set and origin; then one `haiku --effort low` judgment when the similarity is between 0.6 and 0.8), under the per-wave cap (`strict` 0, `moderate` 3, `exploratory` 6), and with every `blocked_by` existing. Otherwise parked with the reason, listed in `REPORT.md` under "not pursued" (in the account from decision 17), never deleted; under `autonomous` the decider reconsiders parked proposals at the end of each wave.
- **Decision tickets** (BRIEF 6.6): created by the planner or from a worker's `decision_requests`, with the question, options, recommended answer, evidence, `blocking`, and `human_only`; `decision_opened` notifies. Answers arrive as `decision` events from `wayline answer`, the dashboard, an edit of the ticket's `## Answer` section (the tick and the conductor detect the edit and journal it), or an interactive session; the decider answers the rest under `autonomous`.
- **Pacing and pause** (OPEN-8, map ticket 20; map ticket 02): utilization comes from every worker's `rate_limit_event` and from `claude -p "/usage" --output-format json` at every tick and at every `run` start (parsed with the regexes `Current session: (\d+)% used · resets (.+?) \(` and `Current week \(all models\): (\d+)% used`, and Fable's weekly window with `Current week \(Fable\): (\d+)% used · resets (.+?) \(`, decision 15); the action is `stop` when either window is at or above `pacing.stop_at` (0.90), `cheap_only` at or above `pacing.cheap_at` (0.80), under which every launch runs one rung down (decision 16), else `normal` (spec decision: the same thresholds apply to the weekly window, because a fan-out can exhaust the week before the session window resets). A hit limit is any of: a `rate_limit_event` with `status: rejected`, a `result` with `api_error_status: 429`, or a non-zero exit whose stderr or result text contains "hit your" or "reached your", and "limit"; the conductor journals `paused` with `resets_at` from the event or the message (else the next known window reset, else now plus five hours), lets running workers finish, keeps polling jobs, and continues at the reset; the tick relaunches it if it is not alive then. A refusal of Fable's weekly window holds only Fable work instead of pausing the run (decision 15). No quiet hours and no per-window worker budget until a night is measured.
- **Resume** is start: replay the journal from offset zero to rebuild statuses, attempts, session ids, pids, jobs, the pause, the hold on Fable and an open ask (decision 15), pacing, and the stall counter; reconcile with `tickets/` (a hand edit wins for `pinned_difficulty` and answers) and with `.worktrees/`; re-adopt live workers by pid and stream file; resume or relaunch dead ones. Idempotent: replaying twice yields the same view. A result journaled and never carried is carried from its stream, and the verdicts a done ticket earned and no conductor took are queued again. A `control` event carries its arguments in `args`: `stop` takes `drain` and, when `switch` wrote it, `switch_to`; `cancel` and `rerun` take `ticket`; `autonomy` takes `autonomy`; `pacing` takes `stop_at` and `cheap_at`; `model_fallback` takes `model_fallback`; `ladder_changes` takes `ladder_changes`. The run that is running applies a `stop`: without `drain` it ends at its next wave and leaves the workers still running to finish, for the next run to re-adopt; with `drain` it launches nothing new and ends once they have returned. A run started after a `stop` is not stopped by it; whether the tick relaunches a stopped project is the tick's contract. A `cancel` or a `rerun` ends the ticket's running worker and waits for its `ticket_cancelled` or `ticket_rerun`, across restarts; a rerun of an answered decision ticket renames its `## Answer` heading to `## Superseded answer`, so that it can be answered again (ticket 09).
- **Termination**: `run_ended` when the frontier is empty and nothing is running and no job is pending, when the goal is reached under `stop_when: goal_reached`, on `control stop`, on `switched`, or on a strict stall. Then P6 and P7 run (decision 11) unless the reason was `switched`. Decision 17 replaces this with the stopping rule (`objectives_closed`, `goal_reached`, `frontier_empty`), `budget_spent`, and the run-end gates.
- **Context packs** (map "Not yet specified"; spec decision on the initial numbers): the pack is the ticket's `context_pack` list rendered in order under locator headers, cut at `policy.context_pack.max_chars[<family>]`, the family of the rung's model, with the cut announced in the prompt; initial caps are in decision 14 and M1 records what was used and how the tickets fared.

### 6. Jobs and resources (seam 2; OPEN-15, map ticket 28; OPEN-8, map ticket 20; OPEN-14, map ticket 26; map ticket 05)

- **Interface.** `JobRunner.launch(spec) -> handle`, `poll(handle) -> JobState`, `kill(handle, hard=False)`, `cleanup(handle)`. Backends: `systemd_run` (default), `setsid` (chosen automatically when `systemctl --user show-environment` fails, that is, when no user manager is reachable), `fake` (tests). The resource manager and the conductor only ever see `JobState` (`running`, `exited`, `oom_host`, `oom_gpu`, `failed`, `killed`, `gone`).
- **Launch line** (map ticket 05, A1, with the unit prefix renamed for wayline and `RuntimeMaxSec` added from the ticket's `wallclock_minutes`, a spec decision so a runaway job frees its slot):

  ```
  systemd-run --user --unit=wayline-job-<id> --slice=wayline-jobs --remain-after-exit --expand-environment=no \
    -p CPUAffinity=<cores> -p MemoryMax=<bytes> -p MemorySwapMax=0 -p TimeoutStopSec=30 \
    -p RuntimeMaxSec=<wallclock seconds> -p WorkingDirectory=<abs project dir> \
    -p StandardOutput=append:<abs log path> -p StandardError=append:<same log path> \
    -E CUDA_VISIBLE_DEVICES=<ids> -E PYTHONUNBUFFERED=1 \
    <abs interpreter> <script> <args>
  ```

  Never `--collect` (it unloads a failed unit before the poller reads it). `AllowedCPUs` is unavailable to the user manager here; `CPUAffinity` is the pinning knob. `MemoryMax` comes from the ticket's `ram_gb`, `MemoryHigh` stays unset. The unit name is the job id and must be unique among loaded units.
- **Poll line and decoding** (map ticket 05, A2): `systemctl --user show wayline-job-<id>.service -p LoadState,ActiveState,SubState,Result,ExecMainCode,ExecMainStatus`. `active/exited, Result=success, ExecMainStatus=0` is exit 0; `failed, Result=exit-code, ExecMainCode=1, ExecMainStatus=N` is exit N; `failed, Result=oom-kill, ExecMainCode=2, ExecMainStatus=9` is a host memory kill; `Result=signal` with 9 and no `oom-kill` is a cancellation; `LoadState=not-found` never implies success (consult the job file and the log). `RuntimeMaxSec` expiry shows as `Result=timeout` and is `failed` with reason `wallclock`.
- **OOM rule** (map ticket 05, A3): `Result=oom-kill` is host RAM (empty log); `Result=exit-code` plus one of `CUDA out of memory`, `torch.OutOfMemoryError`, `torch.cuda.OutOfMemoryError`, `CUDA_ERROR_OUT_OF_MEMORY`, `cudaErrorMemoryAllocation`, `RESOURCE_EXHAUSTED`, `CUBLAS_STATUS_ALLOC_FAILED`, `CUDNN_STATUS_ALLOC_FAILED` in the last 64 KB of the log is GPU OOM; the signature list is one table in the resources module. Retry: host OOM first doubles `MemoryMax` up to the free RAM minus the reserve, then steps the ticket's `retry.host_oom` ladder; GPU OOM steps `retry.gpu_oom`; each step is a set of argument or environment overrides the experiment worker declared (for example `{"--batch-size": 16}`; a key starting with `-` is an argument, any other key an environment variable, and a ticket file, whose frontmatter lists hold scalars only, spells the same step `"--batch-size=16"`, ticket 19); an exhausted ladder fails the job and the ticket with the log tail.
- **Kill and cleanup** (map ticket 05, A4): `systemctl --user stop <unit>` (SIGTERM, SIGKILL after 30 s), `systemctl --user kill --signal=SIGKILL <unit>` when hard, `systemctl --user stop wayline-jobs.slice` for everything; `reset-failed` for failed units and `stop` for exited remain-after-exit units after the result is read; a nonzero exit from either cleanup is ignored.
- **Fallback** (map ticket 05, A5): `setsid nohup env CUDA_VISIBLE_DEVICES=<ids> taskset -c <cores> sh -c '<abs interpreter> <script> <args>; echo $? > <abs jobs dir>/<id>.exit' >> <abs log path> 2>&1 < /dev/null &` with the pid in `<id>.pid`; poll by the exit file and `kill -0`; kill with `kill -TERM -- -<pid>` then `-KILL`. It loses `MemoryMax`, the `oom-kill` signal, cgroup-wide kill, and manager-recorded status; the job file records `backend: setsid` so the report can say so.
- **Job file** `jobs/<id>.json` (schema `job`, M2 verifies): `id, ticket, array (group id or null), backend, unit, command (argv), cwd, env, devices: {gpu_uuids, gpu_indices, cores, ram_gb}, log, expected_outputs, retry: {host_oom: [...], gpu_oom: [...]}, attempts: [{n, started_at, ended_at, result, exit_code, oom, overrides}], status, wallclock_minutes`, and from decision 17 `tools` (ticket 82: a job spec naming `"tool"` has that tool's absolute executable and environment written into `command` and `env`, and every tool the job calls is listed by name, version, and lock digest). GPUs are recorded by uuid because the index can change per boot; the index is resolved at launch.
- **Detection and slots** (map ticket 05, A8; OPEN-8): `nvidia-smi --query-gpu=index,uuid,memory.total,memory.used,memory.free,utilization.gpu,utilization.memory --format=csv,noheader,nounits`, `nvidia-smi --query-compute-apps=pid,used_memory --format=csv,noheader,nounits`, `/proc/loadavg` field 1 against `nproc`, `/proc/pressure/cpu`, `MemAvailable` from `/proc/meminfo`, `df -B1 --output=avail /home`. Reservation defaults for this machine: no GPU, 8 cores (0 to 7), 64 GB; `harness.json.reservations.processes` lists process names whose GPU memory and cores count as reserved. A GPU slot is free when `memory.free >= need + reserve`, `utilization.gpu < 20` for two consecutive samples, and no wayline job holds it (one GPU job at a time on this box; jobs take the GPU whole). A CPU slot is free when `loadavg1 + cores_needed <= nproc - reserved_cores` and the core allocator (a pool of the unreserved cores, ranges handed out and returned per job) can supply the request. RAM is free when `MemAvailable - reserved - sum(MemoryMax of running jobs) >= need`.
- **Sweeps** are job arrays: the experiment worker writes one job file per member with the same `array` id through `wayline job add`; the conductor launches as many members as fit each wave and the ticket closes when every member exited 0 and its outputs parse.
- **Artifacts** (OPEN-14, map ticket 26): `results/` is git-ignored; every expected output and every file a finding cites gets a `manifest.json` entry `{path, size, sha256, job, run_id, ticket, ts}` where `run_id` is `t<ticket>-a<attempt>` for the attempt that produced or registered it and `job` the job id when a job wrote it; the ledger refuses a finding whose provenance is not in the manifest. Files under about 1 MB may be committed; a heavier file may be when a ticket or the owner says it is necessary (`commit_threshold_bytes` in policy is a soft default).

### 8. The dashboard (OPEN-20, map ticket 37; OPEN-21, map ticket 38; map ticket 08)

- **Server**: `http.server.ThreadingHTTPServer` with a small path table; JSON endpoints that read the ledger of every project in `projects.json`; static files from `dashboard/`; no framework, no build step. Change detection is one `os.scandir` snapshot of `(st_mtime_ns, st_size)` per ledger directory inside the poll handler with a 1 s memo. `request_queue_size` is 16 when bound wider than localhost.
- **Transport**: polling. The journal tail reads `/api/projects/<id>/journal?since=<byte offset>` every 2 s and receives only the bytes appended; every other view polls its JSON every 5 s with `If-None-Match` and gets 304 when the snapshot is unchanged. The server-sent events alternative for the journal tail exists behind `?transport=sse` (unchunked `Connection: close` `text/event-stream`, `id:` set to the byte offset, `retry: 2000`, a `select()`-based dead-client check) and becomes the default for the logs view only if the owner judges the 2 s tail latency annoying through the tunnel.
- **Endpoints**: `GET /api/projects`; per project `overview`, `graph.svg` (server-side layered layout: longest path, two barycenter sweeps, straight edges, one link per node, status fills), `tickets`, `tickets/<id>`, `decisions`, `outputs`, `journal?since=`, `logs/<kind>/<id>?since=` (worker streams, job logs, the tick log), `download/<path>` (single files with `Accept-Ranges: bytes` and single-range 206 and 416; a directory streams as a zip through a chunked-encoding wrapper with `write` and `tell`, ZIP_DEFLATED, data descriptors, flat memory); `POST /api/projects/<id>/actions/<name>` for `answer`, `autonomy`, `pause`, `resume`, `switch`, `cancel`, `rerun`, `feedback`, `promote`, `paper`, `pacing`, `model_fallback`, `ladder_changes`, `intake` (file drop), each calling the CLI function of decision 1 in-process and nothing else; no endpoint runs a shell.
- **Views**: overview (phase, autonomy, radius, goal progress, window status with Fable's weekly window and its hold line of decision 15 and the `stepping down` note of decision 16, slots in use, running workers and jobs, last events); graph with the frontier highlighted and a page per ticket (the rung label of decision 16, frontmatter, context pack, result, findings, session and job logs); decisions (open decision tickets with options, evidence, and the answer form; the decision record from `DECISIONS.md`, decider decisions first); outputs (an index of `results/`, findings, figures, dossiers, `REPORT.md`, `paper/`, the docs site, every file downloadable, markdown and images rendered inline through `DOMPurify.sanitize(marked.parse(md))`, large artifacts streamed); logs; intake and feedback. Decision 17 replaces the one stacked page with five routed views, a projects page, the marks view, the chat, the popup viewer with KaTeX math and zoom (sanitizing after rendering and forbidding `<style>`), and the actions its verbs add.
- **Exposure**: bind `127.0.0.1` and print `ssh -L <port>:127.0.0.1:<port> <workstation>` at start; `serve --bind 0.0.0.0` requires the random URL token on every request. Actions always require the token as a header (spec decision: a page open on the laptop could otherwise POST to the tunneled port; views on localhost need no token). The token lives in `~/.wayline/dashboard.json` and `serve` prints the URL that carries it.
- `wayline run` does not host the dashboard; it prints the address and starts `wayline-dashboard.service` if it is not active, so the dashboard outlives every conductor and the tick keeps it alive (BRIEF 9.9).

### 9. Dossiers, the scout, the absorb workflow, the consultant, the knowledge base (BRIEF 7; OPEN-16, map ticket 31; map ticket 04; map ticket 06; map ticket 41)

- **Levels and budgets.** L0: metadata, abstract, verified identifiers, a knowledge-base node, for every reference. L1: one `sonnet --effort medium` call per paper over an input capped at `policy.absorb.l1_max_chars` (40,000) holding the title, abstract, introduction, conclusion, figure captions, and results table headers, returning the L1 record (a short structured record, `relation_to_intent`, `deserves_l2_if`). L2: the full dossier, only on promotion, capped per phase at 3 papers in P1 and 2 each in P3 and P5; every 7.2 trigger promotes automatically inside the budget (named primary at intake; cited by a spec claim, baseline, or method to implement; named in a ticket's context pack; a consultant question L1 cannot answer; the planner or decider promotes) and a decision ticket is opened beyond it. Promotions and demotions are journaled with the trigger; the report lists papers not read in full and why. The numbers live in `policy.json` and are revised from M3's measurements.
- **The scout** (map ticket 06, Section 3) resolves through the fetch seam with `User-Agent: wayline/<tag> (mailto:<owner email from harness.json>)`: for a DOI, Crossref `works/{doi}?mailto=` (polite pool, 10 requests per second), then OpenAlex `works/doi:{doi}` (keyless budget about USD 0.10 per day; sparingly), then Unpaywall `v2/{doi}?email=` for the PDF location, then Europe PMC for biomedical DOIs; for a title, Crossref `works?query.bibliographic=` with `rows=3` and a title-similarity check in code, then OpenAlex `search=`, then Europe PMC `TITLE:`; for an arXiv id, the arXiv API `query?id_list=` at one request per 3 s; bioRxiv and medRxiv through `api.biorxiv.org/details/{server}/{doi}/na/json`. Semantic Scholar is not used keyless (429 on the first call). A reference that resolves nowhere is `existence: unresolved`, never `fabricated`. Every lookup is cached under `research/.cache/scout/` by request hash. Decision 17 records each attempt as found, no match, or failed, replays only works already found, adds the `arxiv.org/abs` fallback, the `retry` flag, one dossier per work, and `wayline scout` for workers.
- **arXiv sources** (map ticket 06, Section 2): `https://export.arxiv.org/src/<id>[vN]` (always a gzipped tar; PDF-only submissions return a PDF), one request per 3 s, one connection, ETag cache forever, the source kept under `refs/<slug>/source/` and never published anywhere; the main file from `00README` or the `\documentclass` grep; `latexpand main.tex > flat.tex`, comments stripped, environments by regex (`equation`, `align`, `figure`, `table`, `algorithm`, `theorem` and its kin, `\label`, `\caption`, `\section`); exact equation and figure numbers from the `.aux` `\newlabel` lines after one `pdflatex` run when the source compiles, document-order counting honoring `\nonumber` and `\tag` otherwise; figures from `\includegraphics` targets, PDF figures rasterized with `pdftoppm`; `https://arxiv.org/html/<id>` as the second source when the tarball will not flatten.
- **Non-arXiv PDFs** (map ticket 06, Section 1): always `pdftotext -layout`, `pdfinfo`, `pdfimages -list`, and pdfplumber for the text layer, page count, raw images, word and character boxes, ruled tables; docling as the primary structural converter (typed items with page and bbox, figures and tables to PNG, `do_formula_enrichment` on the GPU); marker 2.0 (GPU, vLLM server) then MinerU `pipeline` as fallbacks; GROBID CRF for structured references and header metadata; nougat rejected; PyMuPDF optional only (AGPL). Converters live in the tools venv from `wayline tools install` and are called as subprocesses; when absent, the inventory records `converter: none` and the reader pass fills more.
- **Inventory** `refs/<slug>/inventory.json` (schema `inventory`; M3's first criterion records the reliable split): `page_count`, `text_layer`, `raw_images[]`, `sections[]` (title, level, page, bbox, numbering by regex), `figures[]` (image file, caption, page), `tables[]` (cells, caption), `equations[]` (latex, number, page; LaTeX from a converter is OCR-derived and marked so, numbers regex-recovered from adjacent `(N)` and confirmed by a reader), `algorithms[]`, `theorems[]` (regex on `^(Algorithm|Theorem|Lemma|Proposition|Definition|Corollary)\s+\d`, boundaries confirmed by a reader), `appendices[]`, `references[]` (GROBID `biblStruct`), `metadata`; every model-derived field carries `provenance: "<tool>-<version>"` and keeps page and bbox so a reader can look at the crop (`pdftoppm -r 150 -f P -l P`).
- **The absorb workflow** (map ticket 04; map ticket 12 (b); map "Not yet specified"): one `claude -p` session per L2 paper, cwd the project root, launched through the launcher with `--allowedTools Workflow Skill Read Glob Grep` (the narrower `Workflow(absorb)` and `Skill(absorb)` forms are tried first and recorded in M3), `--disallowedTools Edit Write NotebookEdit Bash WebFetch WebSearch`, `--agents` defining `reader` (sonnet, medium) and `synthesizer` (opus, high), and a prompt whose first line is `/absorb <path to the chunk manifest>`. Chunking is code: one chunk per section's text cut at `policy.absorb.chunk_max_chars` (20,000, revised from 30,000 by the M3 measurements) with the inventory items located in it as its obligation list; every figure and table is its own chunk with the image file; equations, algorithms, and theorems ride with their section. `absorb.js` runs `pipeline` over chunks with `agent(prompt, {agentType: 'reader', schema: dossier_entry_list})` (up to 16 concurrent on this box), one entry per obligation item (`item_id, locator, kind, content` in exact form, `importance` 1 to 5, `relation_to_intent`, `oddities`; figure entries add `what_it_shows`, `supports_cited_claim`, `anything_odd`), then one `synthesizer` call over all entries for the prose sections (method, claims, results, assumptions, limitations, flaws found, reusable ideas, open questions, relation to intent), every sentence with a locator. The script returns `{entries, sections, failures}`; the conductor reads it from the run file found by `glob ~/.claude/projects/*/<session_id>/workflows/wf_*.json` and journals `absorbed`. Code merges entries into `entries.jsonl` and `dossier.json`, renders `dossier.md`, runs the coverage audit (Type-A: every inventory item has at least one entry), and queues the depth spot-check (Type-B, the critic, on the five most important items and every claimed flaw). Fallback: N `claude -p` reader launches through the launcher, one chunk each, with the coverage bookkeeping in the conductor; same function signature, selected by `policy.absorb.fanout: workflow | conductor`.
- **Code dossiers** (map ticket 06, Section 4): `git clone --filter=blob:none --no-checkout <url> && git checkout <sha>` (or `fetch --depth 1 origin <sha>`), recording `url, sha, author_date, nearest tag, submodules`; inventory with the standard library `ast` (functions, classes, `__all__`, public symbols, docstrings, line ranges), entry points from `pyproject.toml` through `tomllib` and from `setup.cfg`, configs, tests, scripts, and data requirements by glob and grep; a verified recipe: install into a fresh venv (`pkg @ git+<url>@<sha>`), run the smallest test or example, record the log, `verified: true` only if it ran; the API map records per module what is good, bad, risky, reusable, and how to call the pieces that matter. Other languages wait for the first non-Python dossier, except MATLAB, which decision 17's tree-sitter-matlab parser inventories.
- **The consultant** (map ticket 41; from decision 17 it answers from one dossier or one document): one role definition, two entry points. From code, `wayline consult <slug> "<question>"` launches `claude -p "<question>" --agent consultant --add-dir <project>/research/refs/<slug> --disallowedTools Edit Write --json-schema consultant_answer.json` through the launcher (with the same `dontAsk`, `--permission-prompts none`, stream-json, and `NotebookEdit Bash Agent WebFetch WebSearch` removals as every read-only role); in a Workflow script, `agent(question, {agentType: 'consultant', schema})` whose result the script returns to code. The answer (`answer, locators[], confidence, not_in_source, promote_requested`) is validated and the ledger appends it to `refs/<slug>/qa_log.md` and journals `consulted`. `promote_requested: true` becomes a promotion inside the budget or a decision ticket beyond it. Workers call the CLI form only: `wayline consult` reads `WAYLINE_TICKET`, counts the ticket's `consulted` events, and refuses the sixth. High-value answers are folded into the dossier at the next absorb pass.
- **The knowledge base** (BRIEF 7.5; OPEN-11, map ticket 23): `research/kb/nodes/<id>.json` for papers, ideas, experiments, and claims; `edges.jsonl` with `extends, contradicts, tested_by, supports, refutes, uses, depends_on`; `query_pack.md` regenerated by code under `policy.kb.query_pack_max_chars` (20,000) for injection into planning and ideation. Dossiers hold depth; the knowledge base holds relations; no prose is duplicated between them. Structured records with locators are the representation; alternatives enter only through the evolve loop when they win the benchmark built from `qa_log.md` questions and journaled ticket outcomes (retrieval hit rate and first-time pass rate).

### 11. Verification, provenance, and the report (C6, C8; OPEN-6, map ticket 18; map ticket 40; OPEN-10, map ticket 22)

- **Type-B verdicts are Claude-only** (map ticket 18, narrowing C6's chain by the owner's choice): a fresh session on the verifier role that carries none of the author's context (never the session that wrote the work, a resume of it, or a subagent inside it), at the verifier's own effort, for every difficulty 1 to 5; no external model and no human verdict unless the owner enables them per step (the external backend's invocation is out of this spec). The verifier has its own system prompt, none of the author's skills, receives paths (the worktree or `main` at a commit, the result artifact, the claim) rather than summaries, and a scope limit stating the one question it answers. Model table (spec decision; in `policy.json`, keyed by the family of the author's rung, decision 16): author `sonnet` gets verifier `opus high`; author `opus` gets `opus max`; author `fable` gets `opus max` (ticket 65: Opus 5.5 ranks above Fable 5.1 and costs less, research note 04). The table is the default choice, not the rule: a verdict on the author's own model from such a session is a verdict, which is what the table gives an Opus author ([Verdicts while Fable is spent](https://github.com/Bernaljp/wayline/issues/93)), and while Fable's weekly window is spent a verdict whose table verifier is Fable follows decision 15. Verdicts are roles, not ticket work, so the cap of decision 16 does not bind them. The verdict schema is `{pass, findings: [{text, locator, severity}], question_limit, session_id, model}` and every verdict is journaled.
- **What gets a verdict** (decision 17 adds every ticket that carries an objective proposal and an explicit check of each verdict on an inherited claim): every done ticket with `acceptance.quality`; every difficulty 3 ticket (an independent read of the diff); every difficulty 4 and 5 ticket (an independent read of the result); the spec (claims versus experiments); the depth spot-check of every L2 dossier; every claim in `REPORT.md` and the paper by sampling (below); the figure honesty verdict; the docs read; the kill argument. Verdicts are queued after `done` and launched by the conductor like any model work, subject to pacing; `accepted` follows a pass; a fail journals findings and, for tickets, sets `failed` with `next: resume` carrying the findings as the failure output.
- **The kill argument** (BRIEF 3.2, 13.3; spec decision on shape): two threads, both the verifier role on different sessions: the first writes the single strongest rejection memo against the report or paper from the paths (from decision 17, the general report at a run end when it changed, and the paper once per build); the second adjudicates it point by point against the artifacts; the outcome is a verdict whose fail scopes claims down (a `writing` ticket) rather than blocking forever.
- **Provenance tags** (map ticket 40; decision 17 adds `code`, `doc`, and `plot` tags, `ref` tags by identifier, the five sections, and the linter at each acceptance): every claim sentence in `REPORT.md` and the paper ends with one or more tags `{res:<run-id>/<artifact>#<locator>}` or `{ref:<slug>#<locator>}`; they render as citations or supplementary references. Sentences are classified (claim, definition, transition, method description) in batches by one `haiku --effort low` call per batch, cached under `research/.cache/claims.json` by sentence hash so a rebuild classifies only changed sentences. Negative results are claims and need a tag. The linter (Type-A) requires a tag on every claim and resolves every `res` tag against `manifest.json` and every `ref` tag against `kb/` and `refs/<slug>/`, failing the build otherwise. The verifier (Type-B) samples 10 percent of tagged claims, at least ten, plus every claim originating from a difficulty-5 ticket, and checks that the artifact or locator supports the sentence. Ticket 40 settled four readings: the linter reads prose only, so the listings code renders from the journal sit between `<!-- wayline:records -->` and `<!-- /wayline:records -->` and are neither classified nor linted; in `REPORT.md` the tags render as numbered footnote citations with a supplementary reference list, which the linter reads back to lint the file on disk; the 10 percent and the minimum of ten are taken of all tagged claims and drawn from those not originating from a difficulty-5 ticket, a claim originating from a ticket when one of its `res` tags names a run of it; and the classifier and the writer are the roles `classifier` and `writer`. `render_report` and `verify_claims` are what P7 and P6 call, `offline` whenever pacing or a closed window forbids model work (as the tick renders), and `wayline report [--verify]` runs them by hand; a session a usage window refuses is a note in the report, never resumed.
- **REPORT.md** (OPEN-10, map ticket 22; BRIEF 6.1 P7; for a project at `research_version` 2, decision 17 makes it the general report on the research and moves everything else below to `ACCOUNT.md`) is always the stopping point, rendered by code from the journal, `findings.jsonl`, `DECISIONS.md`, `GOAL.json`, and `graph.json`, with these sections in order: decider decisions (first, with rationale and confidence), open decision tickets and `needs_human` items (an item the escalation chain ended on the top rung marked "at the ladder's top rung", decision 16), the goal trajectory (every kept `progress` value with its run id, discarded changes with their metrics), findings by claim (each sentence tagged), tickets closed with `done` versus `accepted`, judged on Opus while Fable was spent (every verdict and decider answer carrying `fallback_from`, decision 15), negative results, papers read at each level and promotions not read in full and why, "not pursued" (parked proposals, never deleted), proposed global harness changes (under `autonomous`), resources spent (windows, turns per closed ticket, GPU hours), and the run's events. The documentation site is part of done whenever a `code` ticket added public API. The paper is only on request.

### 12. The evolve loop (C10; BRIEF 12; OPEN-17, map ticket 33; map ticket 07; map "Not yet specified")

- **Intake**: `wayline evolve "<text>"`, the dashboard feedback form, or files in `research/feedback/`, each journaled as `feedback`; after every `run_ended` the evolver runs a retrospective over the journal (failures, escalations, stalls, rework, turns per closed ticket, skills whose outcome record is below the registry's median first-time pass rate).
- **Change records** (`change.json`): `{id, observed: {text, journal_events[]}, desired, mechanism: prompt | skill | role | policy | hook | code, scope_kind: local | global, risk: low | medium | high, fixture, status}`. The evolver session (opus, xhigh) writes them from the feedback and the retrospective; code files one `harness` ticket per record through the conductor, with the touch set of a local change being the project's `.claude/skills/<name>/`, `.claude/agents/<role>.md`, or `harness.json`, and the touch set of a global change being a path in the harness repository on the branch `evolve/<id>` checked out as a worktree of the harness repository. A change record whose mechanism is `policy` and whose keys include `tiers` or `difficulty` is always `risk: high`, and under `autonomous` it is applied only as the ladder consent says (decision 16).
- **Application**: a local change is used from the next wave (the registry is rebuilt at every planner launch and the conductor rereads `harness.json` every wave); a global change runs the harness tests and the whole fixture suite on its branch, and the owner merges it to the harness `main` and tags it (or, under `autonomous`, the report proposes it and nothing is applied).
- **As built** (ticket 45, spec decisions on what the two bullets above leave open): a change record is `research/changes/<id>.json` with the id `NNN-<slug of its title>`, and `research/evolve.json` holds what the evolver has read and what it made of each feedback item. `observed.journal_events` are locators `research/journal.jsonl#L<n>`, checked against the journal. The retrospective is filed as one more feedback item, source `retrospective`, by `wayline run` once `run_ended` is journaled, only when the journal since the last one holds something worth a session and the run launched a ticket that is not a harness ticket, so the loop cannot feed itself; a run the owner stopped files it and launches no session, and neither does one that ended paused or under `cheap_only`. The dashboard's `changes` view writes nothing: a dropped file the journal does not hold yet is listed as such, and whoever next looks for pending feedback journals it. A running conductor launches the evolver in the wave that finds feedback pending, under the rules the decider's launch follows (`cheap_only` holds it, the hold on Fable's weekly window holds it or sends it to Opus). The items a session reads are claimed in `research/evolve.json` for its length, so `wayline evolve` and a running conductor never spend two sessions on one item, and a list that passed its checks and could not be filed marks its items read rather than costing a session every wave. A harness ticket's touch set is the record's target and `fixtures/<kind>/<slug>/`, since the fixture that proves a change ships with it; its origin `change <id>` is how the conductor finds the record, and a global one's names its branch, `change <id>: evolve/<id>`, which is how the owed-verdicts rule the conductor's restart and the tick share knows it earns none. The record keeps the evolver's `difficulty` and `acceptance`, so a proposal applied later is filed as it would have been. The proof runs on a copy of the fixture, on the changed subject first and then on the subject as it was (the project's `main` for a local change, the commit `evolve/<id>` left the harness `main` at for a global one), and the passing run becomes the fixture's baseline, committed on the ticket branch; an old-subject run that could not happen counts as a failure only when the old tree does not hold the subject, and a branch still at the head it was proven at is not proven again. A global change's worktree is `~/.wayline/worktrees/evolve-<id>`; its ticket closes `done` without `integrated` and with no Type-B verdict, the record waits as `awaiting_owner`, and `wayline evolve` tags once `main` holds the branch, by merge, squash, or rebase. A proposal under `autonomous` is applied by the owner with `wayline evolve --apply <id>`. The ladder decision has the options `approve` and `decline`, and an answer that does not approve parks the harness ticket at once.
- **As built** (ticket 47, what the M6 demo's live run settled):
  - **Staged writes.** Claude Code refuses every write a headless session makes under `.claude/`, so a worker
    writes a touch there at the same path under `.wayline-staged/`, which its launch admits. `wayline accept`
    and the conductor move it into place and commit it.
  - **The proof's old subject.** For a local role override that did not exist it is the harness's
    `roles/<role>/agent.md`, which the override replaces. For a new local skill it is the pack with no skill.
    Both run, rather than counting as failed for a missing file.
  - **What a proof runs and says.** Each run of the proof stops at its first sample that fails the structural
    layer. A proof that does not pass names the checks that failed and the session's last words.
  - **Fixture sessions.** A subject session gets its role's `policy.budget` minutes when the fixture names
    none. One stopped by its time or its output cap is kept aside, never served from the cache.
  - **A change record owns its harness ticket.** No re-cut, send-back, or split of the graph takes it.
  - **Assignable skills.** The registry reads a baseline the runner set by its own `passed`.
- **Fixtures** (map ticket 07, the proposed format adopted by map ticket 33): layout `fixtures/<kind>/<slug>/` with `kind` in `prompt, role, skill, verifier, conductor`, holding `fixture.json`, `input/` (`prompt.md`, `agent.json`, `schema.json`, `context/` or `manifest.json` with a sha256 per file), `rubric.md`, `recorded/` (the seed envelope and optional stream trace), and `runs/` (written by the runner only). The record, trimmed to the decision-rich parts of the research note's example:

  Structural checks (Type-A, free): `schema_valid` (always first; the runner re-validates), `path_equals`, `path_in`, `path_matches`, `path_contains_all`, `path_contains_any`, `path_count` (`min`, `max`), `path_absent_or_empty`, `file_exists`, `file_absent` (in the run's worktree), `tool_used`, `tool_not_used` (over the stream trace), and `python` (a function in `checks.py` beside the fixture); JSONPath over the validated result; must pass n of n. The judged layer (Type-B): a fresh `claude -p` with no tools, the rubric, and only the `show_judge` fields, answering `{"verdict": "pass" | "fail", "reason"}`; never the subject's session; passes at `at_least` of `sample_size` (2 of 3; `strict` forces n of n). Subject outputs are cached by the hash of (prompt, agent JSON, context manifest, schema, model, effort) and verdicts by (rubric, judge model, output), with a separate namespace per sample index; on a change only fixtures whose `subject.sha256` changed run, the full suite at most once per weekly window; `fixtures.max_turns_per_suite` skips remaining judged samples but still runs the free layer. Fixtures never use `--bare`.
- **Runner contract**: `wayline fixture run [--changed] [--suite]` prints per fixture `structural i/n`, `judged j/n`, the baseline, the delta, and the cost; exit 1 on any regression (a fixture that passed at its baseline now fails), exit 2 on a cost-ceiling stop with partial results. A flake is a run whose outcome differs from the previous run with `subject.sha256` and `input_hash` unchanged; the second flake quarantines (keeps running and reporting, no longer gates, listed in the retrospective, a change record opened to tighten it); `stable_runs_to_restore` consecutive identical outcomes or a rewrite restores it; the runner never deletes a fixture.
- **Recording**: `wayline fixture record --session <id> --kind <kind> --slug <slug>` resolves the session directory from the journal, copies the input pack and the envelope, proposes one `path_equals` per scalar and one `path_count` per array for the author to prune, runs the fixture n times to set the baseline, flags an unstable baseline, and links the fixture id into the change record and, for a skill, its registry sidecar. A fixture born from feedback encodes the desired behavior and must fail on the old subject before the change is accepted.
- **Versioning, pins, upgrade, rollback** (spec decision on mechanics): the harness repository is tagged `vMAJOR.MINOR.PATCH` on every global change; `harness.json.harness_tag` is the pin; `wayline run` refuses when the checkout is not at the pinned tag; `wayline upgrade [--to <tag>]` checks the harness repository out at the target tag (a detached checkout is fine), rewrites the pin, refreshes the skill and workflow symlinks, migrates a `harness.json.policy` override of the old `difficulty` table to the rung map of decision 16 and says what it changed, prints the `CHANGELOG.md` entries between the two tags, and journals `pinned` with `previous`; rollback is `upgrade --to <older tag>`. Global changes are on the irreversible list, so under `autonomous` they are proposed in `REPORT.md` (the account from decision 17), not applied. Decision 17 adds `research_version`: an upgrade across a change of it refuses and changes nothing.
- **Promotion** (`promote skill | role | policy <name>`): copies the local artifact and its fixtures into the harness on a branch `promote/<name>`, runs the tests and the full fixture suite, and once the owner integrates it into the harness `main`, tags; the evolver recommends promotion when a local skill's outcome record is good over several tickets; the decision is the owner's.

    goes back to the same writer session (a resume) with the list, at most three builds in all; a draft that
    still fails is the owner's to read, and no verdict is spent on it. `wayline paper --continue` resumes that
    session for three builds more, with the last list or, after a failed gate, with the points that stood, so
    the figures it asked for are not asked for anew (the M7 run: a fresh writer rewords its figure claims, and
    a reworded claim is a new figure to draw); `--continue --venue <slug>` moves the draft to another venue,
    telling the writer its guidelines. A figure request that differs only in the venue's name, at the same
    size, type, resolution, formats, and library, is the same figure.
  - **Figures.** The draft asks for a figure as a line `{figure:<figure_id>}` and an entry naming its claim and
    its manifested data. The figure role gets the venue's `target`: its formats and resolution, the house
    library, and an 89 mm column with 6 pt type, since `guidelines.json` records no width. A request identical
    to the one on disk is not drawn again, and one that waited is resumed. A placed figure and the figure role's
    caption sit between the records markers, as the report's listings do, because the figure role's own
    `provenance` check and honesty verdict trace them; a figure that waits on the owner holds the gate. So does
    the reference list, which claims nothing.
  - **The gate.** The kill argument, then one independent verdict, the read (`verdict_type: paper_read`), all on
    the verifier the table gives for the writer's model; the read is not spent on a draft the kill argument sent
    back. Each fail files a `writing` ticket with the paper as its origin, one per point while it stands open, and
    the next `wayline paper` gives the writer the open ones; a draft passing both cancels them. At a venue taking
    neither PDF nor PNG, a figure's format is the owner's to convert, a note rather than a build failure.
  - **Sampling.** `wayline paper --verify` samples the draft's tagged claims after a gate that passed, as
    `wayline report --verify` does the report's.
  - **The venue.** `wayline paper` without `--venue` asks the decider once, with each venue's limits as evidence;
    the pick is a `decision` with no ticket, answered `paper venue: <slug>`, which the report lists first. A
    refusal or an answer naming no one venue stops the command before `paper_started`.

### 15. A spent Fable weekly window (the Fable fallback map, [Bernaljp/wayline #89](https://github.com/Bernaljp/wayline/issues/89))

The subscription counts Fable in a weekly window of its own, apart from the all-models week and resetting with it on this account. Opus, Sonnet, and Haiku share the all-models week, so Fable is the only model with anything to fall back to, and it falls back only to Opus. Since the Opus 5.5 check (ticket 70) the shipped policy puts no rung, role, or verifier on Fable, so these rules hold wherever a project's `harness.json` puts one there, a Fable rung included; each keys on a rung's family, never its index. This decision covers the harness's own sessions; the owner's build sessions on this repository are graded in `models.md` (decision 16).

- **Reading the window** ([Fable's weekly window: what the harness can read before and at a refusal](https://github.com/Bernaljp/wayline/issues/90)): `claude -p "/usage"` prints `Current week (Fable): N% used · resets <time> (<zone>)` beside the all-models line, parsed with `Current week \(Fable\): (\d+)% used · resets (.+?) \(` and journaled as `pacing.fable`; it is read at `run` start, at every tick, and before any wave that would launch Fable work (the reading takes no turn and costs nothing). Only a Fable request's own `rate_limit_event` carries the window, as `rateLimitType: seven_day_overage_included`; other models' events never do. A refusal is any of: that event with `status: rejected`; a `result` with `is_error`, `api_error_status: 429`, and exit 1; the text "You've reached your Fable limit" (the text signal matches "reached your" beside "hit your"); a subagent's failed task with `error: rate_limit` in an allowed parent's stream, whose own `result` stays a success. No alias or effort escapes the window, `--fallback-model` does not fire on it, and paid overage is on the irreversible list and unavailable to this account.
- **The hold** ([Holding only Fable launches while Fable's weekly window is spent](https://github.com/Bernaljp/wayline/issues/94)): at a refusal, or when `pacing.fable` is at or above `pacing.stop_at` (before it, `cheap_at` steps a launch on a project's top Fable rung to the Fable rung below it, decision 16), the conductor journals `paused` with `model: fable` and `window: seven_day`; it journals `unpaused` with `model: fable` at the refusal's `resets_at`, or earlier when `/usage` reads Fable under `stop_at`. A `paused` without `model` stays the whole-run pause of decision 5, so a five-hour pause can start and end inside a hold. While the hold stands, launchable drops every launch whose model is Fable or that defines an agent on Fable (tickets, verdicts, the depth spot-check, and the planner, decider, writer, and evolver sessions), and everything else keeps launching; a done ticket any of whose verdicts needs Fable waits whole. Replay rebuilds the hold. A session refused before its first turn is relaunched, never resumed, by every launch path including the gates. A Fable session stopped mid-work waits and is resumed on Fable after the reset under `wait`, or under `ask` before the answer; under fallback it is relaunched as a fresh Opus session in the same attempt and worktree, its prompt saying that a stopped session left partial work there, because resuming a Fable transcript on Opus is unverified.
- **The fallback consent** ([Consent to fall back to Opus: values, default, and where setup records it](https://github.com/Bernaljp/wayline/issues/91)): `model_fallback` in `harness.json` is `auto` (fall back without asking), `ask` (open the ask below), or `wait` (never fall back). The intake asks it beside autonomy and budgets; one value covers the project. A project without the key behaves as `ask`, except for the timeout below, so a missing key stays distinct from an explicit `ask`. `wayline switch --fallback auto|ask|wait` writes `harness.json` first and then journals `control` with `command: model_fallback` and `args: {model_fallback: <value>}`, the way `switch --autonomy` changes autonomy; `project.set_model_fallback` is the function the dashboard's action calls; any value is accepted at any time.
- **What Fable work becomes on Opus** ([What Fable work becomes on Opus: effort, budget, and context cap](https://github.com/Bernaljp/wayline/issues/92)): the same effort (a ticket on a Fable rung at `low` becomes `opus low`, and one at `high` becomes `opus high`, decision 16; a planner, writer, or evolver a project puts on Fable `opus xhigh`, a decider `opus max`, the efforts the shipped policy gives them on Opus); difficulty and the turn and minute budget unchanged; the context pack cut at `context_pack.max_chars.opus` with the cut announced. A fallback attempt counts toward the ticket's escalation and never toward `difficulty_raised`; the tier up lands on the next rung's launch, which falls back like any launch. `ticket_launched` carries `fallback_from`, naming the Fable rung, beside `model: opus`. No role is exempt, and every agent a launch defines on Fable (`--agents` entries, Workflow `agentType`s) is launched on Opus with it.
- **Verdicts while Fable is spent** ([Verdicts while Fable is spent](https://github.com/Bernaljp/wayline/issues/93)): a verdict whose table verifier is Fable is Fable work under the consent. The shipped table puts no verifier on Fable (decision 14), so this holds where a project's `harness.json` puts one there; its `fallback_from` names the rung when the project's ladder has one at the verifier's effort. Under fallback, a fresh Opus session at the table verifier's effort (`fable high` becomes `opus high`) takes it: ticket verdicts, claim sampling, both threads of the kill argument, the figure honesty verdict, and the depth spot-check, which never goes to Haiku. Under `wait`, or under `ask` before the answer, it waits, queued, and the ticket stays `done`. `verdict` carries `fallback_from`. The difficulty-5 rule of decision 5 stands. The tick counts a verdict queue that waits only on Fable as work once the window has reset.
- **Asking the owner** ([Asking the owner when Fable is spent and nobody is at the laptop](https://github.com/Bernaljp/wayline/issues/95)): under `ask`, one decision ticket per spent window, keyed by the window's `resets_at`, opened when the hold first drops a launch (a spent week with no Fable work waiting asks nothing); `human_only` under every autonomy, because the consent is the owner's trade of quality against waiting (the rule dates from the decider on Fable); `blocking: null`, because the hold already holds Fable work. `decision_opened` notifies with the reset, what is held, the recommended answer, and `wayline answer <id> "<option>"`. The options: `fall back` and `wait` for this window; `always fall back` and `always wait`, which also journal `control model_fallback` with `auto` or `wait`. The answer text is matched against the options trimmed and case-insensitively, and an answer matching none counts as `wait` for this window, with a notification saying so. The recommended answer is `wait` when the reset is under `policy.model_fallback.wait_under_hours` (12) away, `fall back` otherwise. At the first wave past the reset, or on a `control` event setting the consent to `auto` or `wait`, the conductor closes the ticket with a `decision` carrying `answer: superseded` and `decided_by: conductor`, and a late `wayline answer` is refused as for any answered ticket. When nobody answers: an explicit `ask` never times out; a project without the key under `autonomous` gets `fall back` for this window after `policy.model_fallback.ask_timeout_hours` (2), journaled as a `decision` with `decided_by: conductor` and a rationale naming the timeout; otherwise the ticket waits for an answer or the reset.
- **Judgments made by fallback** ([Re-taking judgments on Fable after the reset](https://github.com/Bernaljp/wayline/issues/96)): nothing is taken again after the reset. `decision` gains `model`, and `fallback_from` when the decider ran by fallback; `REPORT.md` lists every verdict and decider answer carrying `fallback_from` in its section "Judged on Opus while Fable was spent" (the account's run section from decision 17); `wayline rerun <id>` re-asks a decision ticket on demand, answered on Fable once the window has reset.
- **What `wayline status` and the dashboard show** ([What wayline status and the dashboard show while Fable is spent](https://github.com/Bernaljp/wayline/issues/98)): the window line gains `fable <N>`. While the hold stands, a second line follows: `fable    held until <reset>   consent <auto|ask|wait|ask (unset)>   waiting <n>   fallen back <m>`, where `ask (unset)` names a project without the key, `waiting` counts the Fable launches the hold holds, and `fallen back` counts the `ticket_launched`, `verdict`, and `decision` events carrying `fallback_from` since the hold's `paused`. The ask is listed with the other open decision tickets, adding `falls back at <time> unless answered` when the timeout applies. The overview reads the same view, the decisions view answers the ask on its form, and the dashboard gains the `model_fallback` action; no view of its own.
- **Vocabulary the build adds.** `harness.json` gains `model_fallback`. The journal gains `pacing.fable`; `model` on `paused` and `unpaused` (`fable` for the hold, absent for the whole-run pause); `fallback_from` on `ticket_launched` and `verdict`; `model` and `fallback_from` on `decision`, whose `decided_by` gains `conductor` (the superseded close and the timeout); and the `control` command `model_fallback`, whose `args` carry `model_fallback`. The policy gains `model_fallback.wait_under_hours` (12; the ask recommends `wait` below it) and `model_fallback.ask_timeout_hours` (2; only for a project without the key, under `autonomous`). Each lands in the event table of decision 2 or the policy table of decision 14 in the same ticket as the code that writes or reads it, because the suite holds those tables and the code to each other.
- **Build order** ([Where the fallback work lands in the ticket graph](https://github.com/Bernaljp/wayline/issues/99)): the hold lands first, in M1, before the tick; the fallback, the verdicts, and the ask follow in M5; the M5 overnight demo forces a Fable fallback with `--simulate-limit fable:<seconds>` rather than waiting for a genuinely spent week.

### 16. Rungs, the rung ladder, and the cap (the finer tiers map, [Bernaljp/wayline #129](https://github.com/Bernaljp/wayline/issues/129))

The planner still grades difficulty 1 to 5 by BRIEF 8.4's rubric, but a level no longer names a model and an effort: it names a **rung** of an ordered list, the **rung ladder**, and the escalation chain and pacing move along that list one rung at a time. The research behind it (Claude Code 2.1.274, 2026-09-17): the subscription serves eleven model versions, each named in full on `--model` and none reachable by an alias except the newest of each family ([Model versions the subscription serves](https://github.com/Bernaljp/wayline/issues/130)); per-token price is flat within a family (every Opus version $5 and $25 per million input and output tokens, both Fables $10 and $50) and runs backwards inside Sonnet, and the usage windows report utilization to 1 percent, too coarse to price a launch, so rungs are ordered by list-price token cost on one matched task ([What each model version costs of the usage windows](https://github.com/Bernaljp/wayline/issues/131)); within a family the newer version wins at equal effort, so every older version is dominated by its family's newest at a lower effort ([How older model versions compare in quality to their neighbours](https://github.com/Bernaljp/wayline/issues/132)). The rungs therefore come from effort, not from older versions.

- **The rung ladder** ([The shape of finer tiers](https://github.com/Bernaljp/wayline/issues/133)): `policy.tiers` is an ordered list of rungs, cheapest first; a rung is a `model`, an `effort`, and a `budget`. `policy.difficulty` maps each level to a rung index. The shipped ladder, with its cost in multiples of Opus 5 at `high` on the matched task:

  | Rung | Model | Effort | Budget | Cost | Difficulty |
  |---|---|---|---|---|---|
  | 1 | `haiku` | `medium` | small | 0.16 | none |
  | 2 | `sonnet` | `low` | small | about 0.35 | 1 |
  | 3 | `sonnet` | `high` | small | 0.50 | 2 |
  | 4 | `opus` | `low` | medium | not measured: the catalog gives Opus 5.5 no effort index and the card no figure | none |
  | 5 | `opus` | `medium` | medium | about 0.54: rung 6's 0.72 at CursorBench's $3 against $4 | 3 |
  | 6 | `opus` | `high` | large | 0.72, research note 04's matched probe | 4 and 5 |

  The ladder stops at Opus 5.5 (ticket 70). A rung stays only when it sits between its neighbors on cost and quality, and Opus 5.5 dominates Fable 5.1 on both (`.scratch/model-tiers/research-notes/04-opus-5-5.md`): on CursorBench 4.0 Opus 5.5 at `medium` scores 52.5% against Fable 5.1 at `max` with 51.8% and Opus 5 at `max` with 46.6%, for about $3 a problem against $4 at `high` (system card, section 8.8), and on FrontierCode it peaks at `medium`. So no shipped ticket work draws on Fable's weekly window. Rung 6 takes the `large` budget that difficulties 4 and 5 had on the Fable rungs, so hard tickets keep their turns and minutes, and a difficulty 3 ticket that tiers up to it gets that budget too. A project may put Fable rungs back in its `harness.json` (v1.0.0 shipped `fable low` and `fable high` as rungs 6 and 7, above `opus high` on rung 5); they go above its Opus rungs even where a Fable rung is cheaper in dollars, because Fable's weekly window is the scarce resource and dollars do not measure it, and every rule about a Fable rung (the hold, the step down on Fable's window, the fallback, `fallback_from`) keys on the rung's family, never its index, so such a project behaves as it did on v1.0.0. Sonnet above `high` is never a rung (`xhigh` costs 2.41 and `max` 5.59 times its own `high`, dearer than Opus for less). A rung's `model` is a CLI alias or a full version name (`claude-opus-4-8`), and the policy schema accepts both; the shipped ladder names only aliases. No level lands on rungs 1 and 4; they are reached only by a tier up or a step down.
- **The cap**: ticket work never runs above `high` effort, so `xhigh` and `max` are not rungs, and the policy schema refuses a rung above `high`. Difficulty 4 and 5 land on `opus high` (they were `fable xhigh` and `fable max` before the cap, and `fable low` and `fable high` until ticket 70). Why: Fable 5.1 and Opus 5 both score worse above `high` on FrontierCode by editing outside the task's scope, which is what the touch set forbids, and those are the dearest efforts. `policy.roles` is not drawn from `tiers` and is not capped: the planner (`opus xhigh`), the decider (`opus max`), the writer and evolver (`opus xhigh`), and every verdict at the verifier table's effort stay where decision 14 puts them.
- **The escalation chain by rung** ([The escalation ladder over finer rungs](https://github.com/Bernaljp/wayline/issues/135)): `escalation.tier_up` counts rungs, so a tier up moves one rung. After the resume, the tier up comes before the split while the next rung is on the same model family as the attempt's, and the split comes first when the next rung is on Fable and the attempt's was not; then `needs_human` (decision 5). On the shipped ladder a tier up stays on Opus up to the top rung, so the split-first rule applies only to a project's own Fable rungs (rung 5 to rung 6 on the v1.0.0 ladder). A tier up from the top rung (rung 6 shipped) has nowhere to climb, so the chain falls through to `needs_human` with `reason: top_rung` once the split has been tried. A tier up onto a held Fable rung falls back, waits, or asks as the fallback consent says (decision 15). `difficulty_raised` still moves a kind's difficulty level by one, and the rung follows from the level.
- **Pacing and the fallback by rung** ([Pacing and the Fable fallback with more model versions](https://github.com/Bernaljp/wayline/issues/134)): a Fable rung reads Fable's weekly window and the all-models week; every other rung reads the five-hour and all-models windows. At `pacing.cheap_at` every launch runs one rung down, with rung 2 as the floor, which replaces the deferral of hard tickets under `cheap_only`; on a project's own Fable rungs, Fable's window steps a launch from its top Fable rung to the Fable rung below it and no further, since stepping below its lowest Fable rung would leave Fable, which only the hold and the fallback do. An attempt that is itself a tier up is never stepped down, or pacing would cancel the escalation. The hold still holds Fable rungs alone at `stop_at`. A held Fable rung falls back to Opus at the same effort and budget (on the v1.0.0 ladder, rung 6 `fable low` to `opus low` and rung 7 `fable high` to `opus high`), and `fallback_from` names the rung it came from.
- **Verifiers and context packs** ([Keying the verifier table and the context pack by version](https://github.com/Bernaljp/wayline/issues/136)): `policy.verifier` and `policy.context_pack.max_chars` stay keyed by family; a rung's family picks both. Verdicts are roles, not ticket work, so the cap does not bind them. The difficulty-5 rules (the dependents' wait, `provenance.all_difficulty_5`, the verdict on every difficulty 4 and 5 ticket) stay keyed to the level, so nothing moves when difficulty 5 shares rung 6 with difficulty 4.
- **The model that ran** ([An unknown, retired, or silently remapped version](https://github.com/Bernaljp/wayline/issues/138)): a model name the subscription does not serve fails free (exit 1, `is_error` with `subtype: success`, `api_error_status: 404`, the text "There's an issue with the selected model (<name>)"), while a retired name such as `claude-opus-4-1` exits 0 and runs on its family's newest through a client-side remap, with `system/init` echoing the name asked for. So every launch sets `CLAUDE_CODE_DISABLE_LEGACY_MODEL_REMAP=1`, and the launcher compares the model named in the result's `modelUsage` with the rung's: a mismatch is journaled as `model_ran` and fails the attempt with `reason: model_mismatch`. A not-served failure (`reason: model_not_served`) is not retried: the conductor holds launches at that rung and opens a `human_only` decision ticket naming it, because a policy naming a dead model needs the owner's edit, and the rest of the run continues on other rungs. No probe runs at `run` start, since aliases cannot rot, and no retirement date is stored; the nearest ones (Sonnet 4.5 not sooner than 2026-09-29, Haiku 4.5 not sooner than 2026-10-15) touch no shipped rung.
- **What `wayline status`, the dashboard, and the report show** ([What status, the dashboard, and the report show about rungs](https://github.com/Bernaljp/wayline/issues/139)): a launch is labeled `r<index> <model> <effort>` (for example `r6 opus high`) on the ticket lines of `wayline status` and on the dashboard's ticket page, with both models when the one that ran differs. While `cheap_at` is in force the window line says so, for example `all-models 83%   stepping down one rung`, or, on a project whose own ladder has the v1.0.0 Fable rungs, `fable 85%   stepping down to r6 fable low`, beside the hold line of decision 15. A ticket that ended at the top rung reads "at the ladder's top rung" in status, on the dashboard, and among the `needs_human` items of `REPORT.md` (the account from decision 17). The report gains no table of spending by rung.
- **The ladder consent and the evolve loop** ([Rungs in the evolve loop and the fixtures](https://github.com/Bernaljp/wayline/issues/140)): `ladder_changes` in `harness.json` is `auto` (under `autonomous`, the decider may approve a proposed change to `tiers` or `difficulty`) or `ask` (such a change is a `human_only` decision ticket of class `ladder` under every autonomy). A project without the key behaves as `ask`. The intake asks it beside `autonomy` and `model_fallback`, with `ask` recommended; `wayline switch --ladder auto|ask` writes `harness.json` first and then journals `control` with `command: ladder_changes` and `args: {ladder_changes: <value>}`, the way `switch --fallback` does, and the dashboard gains the `ladder_changes` action. Under `interactive` and `checkpoints` it changes nothing, since the owner already answers every decision ticket. A change record whose mechanism is `policy` and whose keys include `tiers` or `difficulty` is always `risk: high`, so a global one runs the tests and the whole fixture suite like any global change. Fixtures stay per recorded launch (the runner already records and caches by model and effort), no fixture checks the ladder's order (that is a research fact, checked again by hand when the ladder is edited), and a price change is the owner's to act on.
- **The owner's build sessions** ([Finer tiers for the owner's build sessions in models.md](https://github.com/Bernaljp/wayline/issues/137)): `.scratch/wayline/models.md` keeps a model and an effort per ticket rather than a rung, because an implement session has no harness budget; it is graded against the rung ladder's cost order, drops a ticket to `opus high` wherever Fable is not needed, and takes the cap, so no implement or review session runs above `high`.
- **Migration.** The harness's own `policy.json` moves to `tiers` and the level to rung map. The policy schema refuses the old `difficulty` shape with a message naming `wayline upgrade`, which rewrites a project's `harness.json.policy` override of the old table to the nearest rungs and prints what it changed. Each rewrite is printed. A project whose own `tiers` override defines its ladder is left as it is.
- **Vocabulary the build adds.** `CONTEXT.md` gains **rung**, **rung ladder**, **the cap**, and **ladder consent**. The journal gains `rung` on `ticket_launched` and `verdict`, and `model_ran` on `ticket_result` and `verdict` (a launch event is written when the process starts, before any result names the model that ran, so the launch's `model_ran` is on its result); `fable_action` on `pacing`; `reason` on `ticket_needs_human` (`top_rung`); the `ticket_failed` reasons `model_mismatch` and `model_not_served`; `fallback_from` naming the rung; and the `control` command `ladder_changes`. The human-only classes gain `ladder`. ### 17. A paper that grows with the work (the living paper map, [Bernaljp/wayline #173](https://github.com/Bernaljp/wayline/issues/173))

The owner's first real project, PINF_Project, started midway: a colleague's rejected manuscript as `.docx` and PDF, a separate Methods and a supplement, two referee reports and a collaborator's list of required experiments, a partial MATLAB and Python repository, and no metric. v1.0.1 could not take it: `position` and `specify` refused a project without `GOAL.json`, a loose PDF became a reference and a `.docx` a Data line, the scout replayed recorded failures forever, and the paper came only at the end, as one Markdown string the writer returned with a reference list it wrote itself. The owner's brief (`.scratch/living-paper/owner-brief.md`, section 1) asks for the opposite: soft objectives, research reports that are always current and about the research rather than about what wayline did, the paper's section files and outline growing with every ticket, and a paper compiled only on an explicit order. This decision is that design, as one release, v1.1.0. Its sources are the 25 closed tickets of the map (#174 to #195, #201, #203, #211), the research notes on the branches `research/converting-documents`, `research/methods-inventory`, `research/installing-software`, and `research/viewer-math-and-zoom` (`.scratch/living-paper/research-notes/01` to `04`), and two prototypes: the toy's reports on the branch `prototype/research-report`, and a seeded copy of PINF outside the repository, since nothing of PINF enters it. Two reference cases hold every rule: the toy, a start from zero with a goal, which must keep working; and PINF, a start midway with no metric. Where this decision and an earlier one disagree, this one holds for a project at `research_version` 2; a project made before it is refused, not migrated (below). Every rule says what happens under `interactive`, `checkpoints`, and `autonomous`; an automated run asks the owner only during its setup and then runs to the end its setup set.

- **Objectives, goals, and measures** ([What an objective is, and what takes the place of GOAL.json](https://github.com/Bernaljp/wayline/issues/174)): `GOAL.json` retires and nothing reads it. `research/objectives.json`, written only by code and rendered as `research/OBJECTIVES.md`, holds objectives with ids O1 onward, never reused: `id`, `text` (the question), `measure` (null, or `{metric, direction, target, held_out_split, eval_command, baseline: {value, source}, dataset_or_split, min_seeds}`), `status` (`open`, `parked`, `answered`, `dropped`, `reframed`), `answer` (null while open), `evidence` (locators in the linter's `res:` and `ref:` forms), and `reframed_as`. A measure's `target` may be null (keep improving, never reached); it stands only when its `eval_command` printed the metric on a sample artifact (today's intake check); an objective has at most one. GOAL.json's `budget` goes and its `stop_when` moves to `harness.json` (below). Claims and tickets name objectives only when they serve one: `claims[].objectives` and a ticket's `objectives` may be empty, any id they name must be open, and a ticket's `goal_metric` becomes `goal: "O2"`, the metric and direction read from the goal. Every open objective is answered by at least one claim (a Type-A check at specify), and each goal's metric is among the spec's metrics. The owner talks normally and never types a verb: the conversation records objectives through `wayline objective add "<question>" [--measure <file> --sample <artifact>]`, asking in one line only when it is unclear whether something is an objective, a goal, or a remark, and records a goal with no command yet as an objective without a measure, saying so. Intake takes information only (INTAKE.md loses its `Goal` section and `intake --goal` goes). Position's guard on GOAL.json goes; its memo reads `OBJECTIVES.md` and the intent, and `goal_feasibility` becomes `objectives`, one row per objective with a verdict (`reachable`, `uncertain`, `out_of_reach`), the reasoning, and a revised target for a goal out of reach; its three directions name the objectives they would pursue, as proposals. The grill's first tier settles which objectives the project takes, open or parked, each reserved for the owner. Specify drafts once one objective is open (that objective may be the question to answer first, not the project's end); with none open the conversation asks "what should the project answer first?". The decider reads `OBJECTIVES.md` in place of GOAL.json, and the human-only class `goal` becomes `objective`, which covers goals. `wayline switch --autonomy autonomous` refuses while no objective is open, so setup cannot end without one.
- **How objectives change as results come in** ([How objectives change as results come in](https://github.com/Bernaljp/wayline/issues/181)): a ticket result and a verdict gain `objective_proposals[]`, each `{kind: add | answer | park | drop | reframe | reopen, objective (or the new question's text for add and a reframe's successor), reason, evidence, feasibility}` (feasibility, in the memo's row form, for `add` and `reframe`). Whoever proposes never makes the change. A ticket that carries a proposal always gets its Type-B verdict (forced at difficulty 1 and 2), which judges each proposal "upheld" or "not upheld" with a reason in the same session; a proposal made inside a verdict goes straight on; one not upheld is journaled and listed in the account under "Not pursued". Code gathers every upheld proposal into one open decision ticket, "Objective changes", which takes new ones until answered and pauses the unstarted tickets that serve only an objective an upheld `park`, `drop`, `reframe`, or `answer` names (`add` and `reopen` pause nothing; a declined proposal resumes what it paused). The owner approves under `interactive` and `checkpoints`; under `autonomous` the decider takes each batch in one session: it answers, parks, and drops (never parking or dropping an objective the stopping rule names), and adds, reframes, or reopens only if the owner took `objective` off the human-only list at setup, its additions bounded by the radius (`strict`: none; `moderate`: a prerequisite or a narrowing reframe that an open objective's own work raises; `exploratory`: also one new question within the intent per wave), while reopening a parked objective is allowed at every radius. What the decider may not take waits on the owner, and the tickets it paused resume. The owner's word in the conversation applies directly, with no proposal and no verdict. A goal is written "reached" by code from the measured values; another objective's answer is written by the verifier that upheld it, never the worker, or, when the owner or the decider chooses "answer it as it stands", by one fresh verifier session per objective on `opus high`; both pass the numbers and locator checks, and code writes the answer as a Discussion passage. When approved: answered, parked, or dropped parks the unstarted tickets serving only that objective (`ticket_cancelled` with the reason), a ticket serving several keeps going while one is open, and claims tied only to closed objectives are **set aside** (kept in the spec, shown as set aside in `SPEC.md`, back when one reopens); reframed re-ties claims and tickets to the successor. An added or reframed objective gets a **spec amendment**: one specify session scoped to it appends claims, experiments, metrics, and anti-claims under new ids and rewrites nothing, the spec verifier judges the amendment only, the planner cuts tickets for the new claims only, and a `lit` ticket follows when no Introduction passage with a `ref` tag covers it; under `checkpoints` a "Confirm the amendment" decision ticket pauses only the new tickets (not `blocking: all`), under `interactive` the conversation confirms, under `autonomous` the decider does. Reopening a parked objective needs no amendment; reopening an answered or dropped one is the owner's alone, keeps the old answer as superseded, and has the planner cut fresh tickets. A claim no objective asked for is a result under "Beyond the objectives" when its evidence holds, and an `add` when it needs more work. A dropped objective's concerns are sorted in the same answer, and a batch still waiting when the frontier empties folds into the empty-frontier ticket. Decision 4's "change the goal or the data" becomes "change a goal's measure, or the data"; adding, answering, parking, dropping, reframing, and reopening an objective leave the irreversible list. A stall proposes nothing, and position is never re-run for a new objective unless the owner asks.
- **Keep-if-better per goal, the stopping rule, and budgets** ([Keep-if-better and the end of a run without a metric](https://github.com/Bernaljp/wayline/issues/182)): keep-if-better runs per goal: `progress` and `discarded` gain `goal`, each goal's best kept value is recomputed from its own events starting at its baseline, and the metric, direction, split, and command come from its measure. The rule is unchanged (`policy.goal.min_seeds` 3 and `margin_sd` 1), except that a measure may carry its own `min_seeds`, down to 1 for a deterministic computation, where any strict gain is kept. A change kept for one goal is never re-measured on another. A ticket serving an objective with no measure gets nothing in place of keep-if-better. **The stopping rule**, `stop_when` in `harness.json`, set at setup: `objectives` (the default: no objective open), a list of objective ids (those closed), or `frontier` (no work left, the v1.0 `graph_empty` made real). The conductor reads it every wave in place of today's goal check, and the tick does not relaunch a run it ended. `run_ended` gains the reasons `objectives_closed` and `budget_spent`; `goal_reached` stays for a rule whose objectives all closed by reaching their targets. **Budgets**: `harness.json.budgets` keeps `wallclock_hours` (counted from the end of setup) and `gpu_hours` (each job's hours times the GPUs it held), now read by code; spending one ends the run `budget_spent`, and the decider never extends one; `usage_windows` goes. After setup, changing `stop_when` or raising a budget is on the irreversible list. When nothing is launchable, running, or owed and the rule still waits on open objectives, code opens one decision ticket covering each such objective with four options: replan for it (allowed at every radius, since it stays within the spec), answer it as it stands, park it, or drop it; code recommends a replan only if a ticket serving it progressed since its last replan. The owner answers under `interactive` and `checkpoints` (the run ends `frontier_empty` meanwhile and the tick relaunches after the answer); the decider under `autonomous`, one session per empty frontier, limited to replan or answer for an objective the rule names. Under `stop_when: frontier` no ticket opens and the end notice lists the open objectives. The stall counter is unchanged. Scheduling's second key becomes a class: 0 for a ticket serving an objective the rule waits on, 1 for another open objective, 2 for none. **The run-end gates** (the drawings, then the sampled claim verdicts and the kill argument on the general report): at the rule's own ends they run first, and their scope-downs continue the run until an end holds with no gate owed; after `budget_spent` or `stall_strict` they run once and their scope-downs wait for the next run, the failed claims marked; after `stopped` or `switched` none run. The setup asks the stopping rule and the budgets in one question reserved for the owner, recommending `objectives` and, under `autonomous`, a wall-clock budget whose number the owner picks.
- **Sections and passages** ([How the section files are written and updated by every ticket](https://github.com/Bernaljp/wayline/issues/175)): five **sections**, `research/sections/introduction.md`, `results.md`, `discussion.md`, `methods.md`, and `references.md`, exist from `init` and are rendered by code after every integration and every edit taken in; no model edits them, so BRIEF Section 14 and decision 2 hold as written. A ticket result gains `passages[]`, each `{section, heading, text, replaces}`, written by the worker who did the work; the ledger keeps them in `research/passages.jsonl` (ids P1 onward, with `by` naming a ticket and attempt, the owner, a document, a front-door step, an answered objective, or a consolidation, and the ticket's `objectives`). A **finding** is a Results passage: findings keep `findings.jsonl` and their F ids and gain `heading`, `replaces`, and `objectives`, so a scope-down replaces the finding it narrows instead of standing beside it. A replaced passage leaves the file and stays in the log; two tickets replacing one passage in the same wave are both kept and the section notes it. Within a heading passages keep their arrival order, a replacement takes the place of what it replaces, and headings keep their first-appearance order until the outline orders them; a worker reuses an existing heading when one fits. The plan and ticket schemas gain `sections`, set by kind: `code` and `experiment` declare Methods, `analysis` Methods and Results, `lit` Introduction, `writing` what it writes, the other kinds none; a Type-A check at acceptance sends a worker back when a declared section got no passage (for Results, no finding). Sections never enter a touch set, and tickets adding to one section run in the same wave, integrated one at a time in id order under the ledger lock. A worker's context pack holds, per declared section, its headings with each passage's id and first sentence and the owner's passages in full. The format is Markdown with LaTeX math (`$...$`, `$$...$$`, a numbered equation as `$$...$$ {#eq:label}`), a provenance tag at the end of each claim sentence with no space in its locator, symbols such as σ written as math, and plots cited by id, never as figures. Tags: `res` and `ref` as before, in every section; `{code:<path>#<symbol>}` or `#L10-L42` for a sentence stating what the project's code does, resolved against `main` and flagged when it no longer resolves; `{doc:<document>#<locator>}` for inherited text, which is provenance and never a citation; `{plot:R4.3}` for a plot. The linter runs on a ticket's passages and findings at its acceptance (a failing sentence sends the worker back) and on every render; before the order a claim tagged only `doc` and an untagged claim in an owner's passage are listed, never failed. The owner adds by conversation (the session's tool, asking only when the section or place is unclear) or by editing a section file: before the next render code takes the edit in (new text becomes the owner's passages, changed text the owner's replacement, removed text a withdrawal), using the file's first-line render stamp so passages that arrived since are never taken for deletions. The owner's passages steer with no lock: a later passage replaces one only with evidence and a stated reason, listed in the account. No model rewrites a section before the order except a **consolidation**, one read-only writer session the owner asks for (never an automated run), which replaces a section's current passages with fewer that keep their tags. The conversation reads "compile" said of a section as a consolidation and of the paper as the paper order, and asks when unclear. Introduction is seeded at setup by code from the memo's verified prior work and by the specify session's passages on the gap; Discussion gains a code-written passage at each answered objective and at each reframe; parked objectives reach the paper as future work at the order; Methods gains what the methods inventory generates (below); References is rendered by code. The planner no longer cuts a writing ticket after each analysis; a `writing` ticket remains for a scope-down and for work the owner asks for, with an empty touch set that never names `research/`.
- **Results and the reports** ([The research reports: general, current, and the earlier ones](https://github.com/Bernaljp/wayline/issues/183); [A research report to react to](https://github.com/Bernaljp/wayline/issues/176)): a **result** is one Results heading with its current findings, given an id R1 onward when the heading first appears; a heading names the question, not the number. Results cluster at acceptance with no session of their own: a reused heading, `replaces`, and the repeated-claims check (below). A result's objectives are the union of its findings'. The owner merges or renames results by saying so. **The general report** stays `research/REPORT.md`, rendered by code alone after every integration and by the tick, in this order: what the project is (about 120 words from the spec's new `summary`, which the specify session writes; a spec without one falls back to its question and data); one headline per result; a table, one row per result, with its objectives, standing (supported, negative, or mixed), counts, current report, and last change; each objective in id order (open and answered first, then parked; dropped and reframed one line each with their lineage) with its status, answer and evidence, a goal's kept values, its concerns and their standing, and its results (findings, headline plots with Purpose, Data, and What it shows, the synthesis, links to the current and earlier reports); results beyond the objectives; inherited claims not yet checked, counted per section; and what can and cannot be inferred with the open questions. Everything else of v1.0's twelve sections leaves it for the account. **A current report**, `research/reports/R<n>-<version>.md`, covers one result at full depth; a new version starts when that result's drawing is accepted, between drawings code re-renders it with new findings under "Since the plots were drawn" and replaced ones marked, and the next accepted drawing freezes it as an **earlier report**, never edited again. Reports show only current findings, each replacement with a one-line note ("replaces F12: narrows"); negative results stay in place, marked, and the table flags them. An inference a drawing makes about the research is a finding under its result's heading. The Results section renders from the same findings under the same headings, citing plot ids, without the plots or the report's apparatus. **The numbers check** (Type-A, at acceptance): every number in a finding, a plot explanation, or a synthesis matches a value at one of its sentence's `res` locators, allowing for rounding, percents, and the scales 100 and 1000; drawings quote only numbers their script wrote into `numbers.json`; counts in words and parameters the spec names are exempt; what code cannot match goes to a fresh verifier, every such sentence; a failure sends the ticket back. Sampled claim verdicts become automatic at every run end on the general report (only claims never sampled, cached by sentence hash, 10 percent, at least ten, plus every difficulty-5 claim), and the kill argument runs on it at a run end when it changed since the last; both file scope-downs whose findings replace what they narrow. BRIEF P7's "one independent read" is dropped. Reports are read-only: an edited report is noticed by its hash against the last `report_rendered`, committed as it stood, and listed in the next render's banner; code never takes it in. `findings.md` and the unused `add_finding` and `render_findings` retire, and the writer session that rendered report prose goes.
- **Drawings and plots** ([Exploring each result in every useful plot](https://github.com/Bernaljp/wayline/issues/185)): code creates one ticket of the new kind `drawing` per result (spec decision on the kind's name) and the planner never writes one; it runs on the new **plotter** role on `opus medium` (the owner's choice; budget `small`), stepping down to `sonnet medium` when pacing steps Opus work down. Results are drawn at rest points only: at each run end before the run-end gates, before each checkpoint pause under `checkpoints`, and on the owner's word ("draw R4 again"); only results changed since their last accepted drawing and holding at least one finding from the project's own evidence; the stopping rule's results first. A drawing reads the result's findings and their `res` artifacts in place, the objectives, the project summary, the sorted plot index, the house style, and the previous drawing with the owner's marks; writes one script that draws every plot and table and computes every quoted number into `numbers.json`; and is read-only on the research (CPU only, no job, never the project's own code; missing data becomes an open question). It names the result's data views and draws one plot per canonical chart type whose data shape matches, leaving out near duplicates, a series over an index with no order, collapsed marks, and plots it cannot make readable, at most 20 plots and 4 tables, with no minimum. The plotter writes each plot's Purpose, Data, and What it shows and the synthesis, headline, what can and cannot be inferred, and open questions in the same session; its prompt says a plot of a quantity against one of its own terms says so, and every mark is explained. `wayline figures build-index` fills each index entry's `data_shape` (one of `dist`, `xy`, `series`, `category`, `whole`, `matrix`, `multivar`, `none`) and a canonical chart type with one Haiku call per entry, cached by page hash. Acceptance reruns the script in the clean room and compares the plots and `numbers.json`, then runs six of the figure checks (`min_font_pt`, `text_overlap`, `palette`, `generator_clean`, `regenerates`, `provenance`) and five new ones from the owner's notes (no rotated text but the y-axis label; no axis label over 40 characters; no figure title above titled panels; heatmap cell labels only up to 36 cells; no flat summary mark), the numbers check, and provenance; the checks read the SVG every library writes, `generator_clean` lints Python only, and a check that cannot run is listed as not run. A failing plot gets one repair resume, then is left out and listed; a drawing that still fails leaves the result with its last accepted drawing, listed in the account, with no tier up, split, or ask. A **plot** keeps its id across drawings (`R4.3`; tables `R4.T1`), redrawn while useful, retired when left out, never reused; sections cite it as `{plot:R4.3}`, which the linter checks. The ledger writes `research/plots.json` (each plot's result, chart type, index entries, data view, status, headline flag, the owner's mark and note, its drawings) and one record per drawing, `research/drawings/R4-2.json`; the script, PNG and SVG files, CSVs, and `numbers.json` are the drawing ticket's artifacts. The drawing marks at most four headline plots. The owner's marks (keep, maybe, or drop, with a note) stay with the plot: drop retires it at the next drawing, a note is an instruction for it, keep means a drawing never retires it alone, and no mark starts a drawing. A plot the owner asks for is a small drawing of its result, carrying the result's other plots into the new version unchanged; one for data no result holds is an ordinary analysis ticket. Tables are data tables written as CSV by the script, their own items in the reports and in the paper. Plotting defaults to Python with matplotlib and seaborn in the tools venv, the one interpreter for drawings, figure scripts, and the checks' clean room; the owner may switch to Altair or to R with ggplot2 at any time (`harness.json.plotting`, applied at each result's next drawing, the owner's word being the yes to install what it needs, never changed by the decider). An earlier figure in a project's documents is folded into the drawing of the result that replaces its claim, which draws the same view where the data allows and says whether it agrees.
- **The account** ([Where the run's own account goes](https://github.com/Bernaljp/wayline/issues/184)): what wayline did leaves the general report for `research/ACCOUNT.md`, rendered by code in the same pass, committed each wave, read-only under the reports' edit rule, and journaled through `report_rendered`. Its first line says code writes it, the research is in `REPORT.md`, and anything the owner wants to tell the project goes to the conversation. In order, empty sections left out: where the project stands (one paragraph: running since or ended with its reason, each objective's status, the stopping rule, each budget spent against its limit; the same text opens the end notice); **Decided for you** (each decider decision and conductor default not yet reviewed, one line with when, what, the answer, the confidence, "on Opus while Fable was spent" where it applies, and a link to the rationale where it already lives; superseded ones leave); **Waiting on you** (decision tickets for the owner, tickets needing a person, proposed global harness changes in one wording, important unresolved references, reports edited and not yet turned into passages, a repository still private at the order, the outline's open proposals as one line with their count); **Changed without asking you** (the owner's passages a later passage replaced, with the reason and evidence, and the merges made at setup); **Runs** (the latest in full: its start, end, reason, and waves, each ticket's outcome with its verdict type and model, the run-end gates and the scope-downs they filed, the drawings with their tokens, turns, and minutes and what they left out, the verdicts and decisions on Opus while Fable was spent, wall-clock and GPU hours, pauses and holds, peak utilization, and turns, minutes, and tokens per ticket from `ticket_result.usage`, with no dollar figure since none is journaled; earlier runs one table row each); **Not pursued** (parked proposals with their reason, parked tickets, proposals not upheld); and **Library** (papers by dossier level, promotions not read in full, dossiers that now resolve to a different work, and a pointer to References' "Not yet resolved" list). A decider decision stays listed until the owner lets it stand or reverses it, by saying so or marking it, journaled as `reviewed`; a reviewed one stays counted in its run. A reversal is the owner's own answer through the existing verbs (`grill answer --revise`, the owner's answer to the decision ticket, admitting a parked proposal), makes that decision human-only so the decider never takes it again, and never stops the run; "undo it" without what instead reopens it human-only and asks in one line. One end notice per run end, sent by the conductor after the gates or by the tick when the conductor died first, opens with the account's first paragraph plus "N decided for you, M waiting on you" and the path; it replaces the split between the conductor's and the tick's notices. `wayline status` stays the live view, its decisions narrowed to those not yet reviewed and one line added: "Account: N decided for you, M waiting on you: research/ACCOUNT.md". Under `autonomous`, a conversation the owner opens starts with "Decided for you" as one numbered item recommending "let them stand"; the owner's yes records the review. The events table of v1.0's report goes.
- **The outline** ([The outline of the paper](https://github.com/Bernaljp/wayline/issues/186)): code alone builds `research/OUTLINE.md` at every render, with no model tokens, from the objectives, the results, every section's headings, the concerns, the inherited passages and what checks them, the methods inventory, the venue once named, and the owner's changes. In order: a storyline (the objectives in outline order with status, results, standing, and answer); the gaps (what the outline names that holds nothing yet; an empty main-text Gaps list is the order's test of complete); Introduction (its headings, then the objectives as the paper's questions); Results (one subsection per objective, the critic's `first` leading, then by id, each result with its id, heading, standing, findings and headline plots counted, its concerns, the inherited claims it decides, the contradictions it resolves, and its measure; then "Beyond the objectives" and "Inherited, checked by no objective"); Discussion (each answered objective's passage, the owner's headings, the parked objectives as future work); Methods (its headings, then the parameter table); the venue block once a venue is named (its `required_structure` mapped to the sections by `check_structure`'s word matching, the parts no section feeds listed as made at the order); Supplement and Cut; "Proposed, not settled" (merges of results whose headings sit close under one objective by the local embedding model, and inherited headings no objective checks); and the concerns for the order. No figures: each result lists its headline plots by id. The owner changes it by talking or by editing the file (moving lines, placing one under Supplement or Cut, a `Note:` line, a heading added to Introduction, Discussion, or Methods), taken in like a section edit; `research/outline.json`, written by the ledger and journaled as `outline`, holds only what the owner set, which always wins: code never moves a placed line, puts new lines after the placed ones marked new, lists a placed line whose item is gone once, and carries a note through a merge or a reframe. Renaming or merging a result changes the result; a new Results subsection that needs work is offered as an objective. Before the order the sections render their headings in the outline's order (what is placed in the supplement or cut still renders at the end under a marker), a worker's context pack gains its objective's outline entry with the owner's notes, and a consolidation follows it. At the order it binds: each heading of the paper carries its outline id as a pandoc attribute (`## ... {#R3}`), a Type-A check compares order and placement, `check_structure` also checks order on a venue that is not `structure_flexible`, and a change the writer wants is a proposal in its notes. Under `autonomous` the decider settles the open proposals in the session that judges the order, never moving a line the owner placed.
- **Documents, critiques, and concerns** ([A project's own documents as first-class inputs](https://github.com/Bernaljp/wayline/issues/190); [PINF seeded from its own documents](https://github.com/Bernaljp/wayline/issues/191)): a **document** is the project's own writing; published work, its preprints included, is a reference. The session sorts each converted document as `inherited` (an earlier manuscript, a separate Methods, a supplement, a thesis chapter), `critique` (a referee report, an editor's letter with points, a collaborator's list of required experiments), or `other`, asking in one line only when unclear; a file dropped on the dashboard with no session gets code's cautious guess (an identifier makes it a reference, review markers a critique, anything else `other`, never `inherited`). Per text one version is inherited, the newest in its source format, tracked changes accepted; a newer version handed over later is taken in like a section edit. Each lives under `research/documents/<id>/` (`source/` and `media/` gitignored, `text.md` with LaTeX math and block anchors, `comments.json`, `citations.json` as CSL-JSON, tables as CSV), recorded in `research/documents.json` (id, title, kind, version, each file's sha256, converter and version, what the conversion lost, conversion damage counted) and journaled as `document`; `research/DOCUMENTS.md`, rendered by code and capped at 20,000 characters, gives each document's kind, version, losses, counts, an inherited one's abstract, and its headings with locators and first sentences, and is how every session finds its way in. Every document is chunked like an L2 source for the consultant, which now answers from one dossier or one document. An inherited document's body under headings that map to Introduction, Results, Discussion, or Methods is deconstructed; its title, abstract, captions, back matter, availability statements, and reference list are kept and read, never deconstructed, so none reaches the paper. Headings map through a fixed table (Introduction or Background; Discussion, Conclusions, or Outlook; Methods, Materials and methods, Theory, Model, or Algorithm; "Results and discussion" to Results), a subheading following its parent, any other placed by the session at setup or, with no session, under Results as written and listed. A separate Methods or supplement document is placed by content: the setup session that reads the inherited passages proposes, for each passage that reports or interprets an outcome, its place in Results or Discussion, and code moves it, listed for the owner; a separate document's own front matter is kept, not deconstructed. A critique's points become **concerns** in `research/concerns.json`, rendered `CONCERNS.md` and journaled as `concern`: ids K1 onward, each with its sources (critique, locator, verbatim text), its targeted inherited passages, its objectives or "for the order", and its status `open`, `answered`, or `declined` with the answer or reason. One Sonnet session at medium per batch of critiques splits them (verbatim spans code checks, praise and summary left out, a two-point item split, near-identical points from different critiques merged, targets among the inherited claims); an open Word comment thread becomes a concern by code; an objection of the position memo's hostile review the owner accepts at the grill becomes a concern with the memo as its source. At setup the critic's memo ties concerns to objective rows or proposes "for the order" or a decline, the grill settles them in groups, and specify drafts only when every concern is sorted. Code answers a concern when every objective tied to it is answered and every inherited claim it targets is replaced or withdrawn; it follows a reframe and goes back to be sorted when its objective drops (inside the same "Objective changes" answer). After setup, a concern that needs sorting is a decision ticket, the decider's under `autonomous` (tie, for the order, or decline with a reason; a new objective only if handed `objective`), unless the owner named `concern` human-only at setup. Who reads what: the critic gets `DOCUMENTS.md` and every concern inlined, with its tools reaching `research/documents/`; the grill, specify, the planner, workers' context packs (the concerns of the ticket's objectives), and the writer at the order read the index and the concerns. The intake wording tells the owner to hand over anything in any form; references are bare identifiers, the owner's plan stays the plan, a collaborator's list of experiments is a critique, a folder is sorted file by file and a `.zip` unpacked.
- **Inherited passages and repeated claims** (the same two tickets): code deconstructs verbatim. Every paragraph is split at its claims (the classifier's claim sentences become one inherited passage each, the sentences between them stay together), each carrying a `doc` tag naming document, paragraph, and sentence, and the rendered section rejoins a paragraph's passages with each claim marked unchecked. An inherited claim stands **unchecked** until a ticket's passage or finding replaces it with whether this project's evidence supports, narrows, or contradicts it, or it is found **unverifiable**. Without pandoc a `.docx` is kept but nothing is deconstructed from it. A claim made in several places is one passage citing every occurrence's `doc` tag and every work any occurrence cites: at setup one consistency read on `opus high` per inherited set finds repeat groups and contradictions, and the local embedding model (BAAI/bge-base-en-v1.5, no tokens) proposes pairwise repeats that a confirmer on Opus, seeing each sentence's heading, labels the same, contradicting, or different; TF-IDF and Haiku leave this check. A merge stays automatic and listed for the owner, but its kept text, the fuller occurrence verbatim or a sentence combined from both, must cover every occurrence (the confirmer checks nothing is lost, code checks nothing is added: no number, symbol, or citation neither has); when either check fails the occurrences stay apart, with no fallback to one of them. A pair kept apart may carry a flag that lists it for the grill. Contradicting pairs both stay, listed for the grill and for the verification of the result they touch. At each ticket's acceptance the embedding net and the same confirmer run on its new passages and findings, and one that repeats a current passage without naming it in `replaces` is sent back. Text the harness writes from inherited passages (a combined merge, a later replacement) is allowed: a start midway uses what was given as a base to build on. Cost for PINF, once at setup: the classifier about $1.14, the consistency read $0.89, the confirmer and merger about $0.14, the critique splitter $0.31, the critic $0.79, about $3.50 to $4 in all.
- **Verifying what a project inherited** ([Verifying what a project inherited](https://github.com/Bernaljp/wayline/issues/201)): every inherited result (one inherited Results heading, all its claims judged together, a large one split by the planner) is verified by re-running it and then judging its wording, so an overstated claim is narrowed to what the evidence shows; a gap that needs new experiments is a proposed `add`, not the verification's to close. At every start midway the critic proposes the objective "Do the inherited results hold?", open by default and human-only; the grill settles it (the owner may park it), specify drafts one claim per inherited result under it, and code answers it once every inherited result has a verdict or is unverifiable. Each verdict names its route: **reproduced** (the project's own code at the commit intake recorded, changed only to run here), **ported** (the same logic in another language or runtime), **reimplemented** (written from the inherited Methods), or **read** (a cited claim checked against its reference by the consultant, batched per reference, from the L0 abstract first; a claim the abstract cannot settle stays unchecked until its work is promoted under the budget). A verdict reached on substitute data covers only the claim narrowed to that data. At setup the parser inventory compares the stated methods and parameters with the code, and each disagreement goes into the verification of the result that uses it; contradictions go there too. **Unverifiable** is a standing with its reason, apart from unchecked. A verification ticket blocks every ticket built on its result (the planner wires the edge from the objectives' and concerns' ties), and an unverifiable result releases what it blocked. The critic's memo gains a table: per inherited result, the code, data, and software it needs, present or missing (fetchable data is not missing); the grill asks about every missing item in one setup question, each with the replies "I'll provide it", "rebuild it" (recommended wherever a rebuild can work), or "leave it unverified", and licensed software with provide, port to Octave, or port to Python. After setup, under `interactive` and `checkpoints`, a pending or newly found gap is a decision ticket offering provide, rebuild, or leave unverified, pausing only that verification; under `autonomous` it is the decider's (rebuild or leave unverified, never provide), and a verification that ends `needs_human` makes its result unverifiable. The fresh verifier at acceptance checks each verdict on an inherited claim explicitly. PINF's six results are estimated at $30 to $60 in sessions, unmeasured.
- **A reference found during a ticket** ([A reference found during a ticket](https://github.com/Bernaljp/wayline/issues/189)): a ticket result gains `references[]`, `{identifier, note}` (a DOI, an arXiv id, or an exact title; a URL is never looked up; the note is kept on the dossier with the ticket's id and the scout never reads it), listing every work the ticket drew on; a work enters References only by being cited. Workers, who have no network, check a work mid-ticket with `wayline scout <identifier>`: code, no tokens, counted under `WAYLINE_TICKET` and capped at 20 calls a ticket, given to the coder, analyst, experimenter, writer, and surveyor; it files the L0 dossier at once and prints the slug, details, and abstract, files an unresolved dossier with the `retry` flag on a service failure, and files nothing on no such work. A `ref` tag names a work by slug or by identifier (`{ref:doi:10.1038/...#abstract}`, `{ref:arxiv:1802.03426#abstract}`), mapped through `position`'s identifier index, passages never rewritten; inherited citations are identifier tags from the start, with no locator. At acceptance (Type-A) every cited work is a dossier or in `references`; the scout runs free on the rest, "no such work" sends the worker back as most likely invented, and a service failure accepts with the flag. The locator names what the dossier holds at its level (`abstract` or `metadata.<field>` at L0 and L1, an entry's locator at L2); a claim beyond the abstract says only what it says or proposes the work's promotion. Dossiers stay at L0 when cited; spec decision 9's promotion triggers stand. A `dossier` ticket has no worker session: the conductor runs it as a promotion through `absorb` (the reader keeps the L1 skim, and `proposals.KIND_ROLE` loses its `dossier` and `lit` routes). The literature is searched mid-run by `lit` tickets on the new **surveyor** role (`sonnet medium`, kinds `["lit"]`, tools Read, Glob, Grep, `wayline scout`, `wayline consult`) through `wayline scout search "<query>"` and by the works that cite a seed: code asking arXiv, Crossref, and Europe PMC free and OpenAlex sparingly (code counts the day's 100), always live, capped at 20 searches a ticket; a `lit` ticket returns Introduction passages tagged at `#abstract`, its `references`, and proposals. The planner cuts one at specify per open objective with no Introduction passage carrying a `ref` tag (merging objectives that share a literature), again when an objective is added or reframed, and on a worker's proposal or the owner's word; position's `missing_prior_work` is scouted at setup and handed to the first `lit` tickets. After every render code writes `references.md` (entries numbered by first citation through the sections in outline order, authors to three then "et al.", year, title, venue, identifier, a dossier link, then **Not yet resolved**: each work "to the scout", "retrying" with service and date, "gave up", or "claim kept, to be resolved") and `research/references.json` (CSL-JSON from the dossiers). The linter lists an unresolved citation before the order and never fails it.
- **The scout's outcomes, cache, and joins** ([The four PINF_Project bugs](https://github.com/Bernaljp/wayline/issues/194); [Rechecking the four PINF_Project bugs](https://github.com/Bernaljp/wayline/issues/203)): every lookup attempt records **found**, **no match** (the service answered and nothing matched), or **failed** (an error status, a timeout, or an unreadable answer); "no such work" means every service asked answered no match, and any failed attempt on a work not found sets the `retry` flag (service, failure, date). The cache replays an answer only for a work already found, at every caller (absorb at L0, `wayline scout`, the check at acceptance, the tick's retry, the order's last retry); every lookup about a work not yet found goes to the network, only successful answers are written, and `wayline scout search` is always live; the plot-gallery crawl keeps only successful answers too, and the suite's recorded fixtures still replay failures. When arXiv's API fails, the scout reads the `arxiv.org/abs` page's meta tags and records the arXiv DOI `10.48550/arXiv.<id>` as an attempt of its own; a work found that way keeps the flag so the API fills in the rest. Flagged references are retried at most once a day by whatever runs next (an absorb, or the tick while a run is live) and give up after 7 days. A lookup replaces the lookup's own fields (`existence`, `resolved_by`, `identifiers`, `metadata`, `abstract`, `open_access`, `attempts`) only when it finds the same work, keeps the level, the L1 fields, the `l2` record, `created`, and the node's level, sets `updated`, and journals a level 0 `absorbed` only for a new dossier or a changed existence; a failure or no match leaves a found dossier as it was; a dossier at L1 or above that now resolves to a different work is left as it was and the disagreement goes to absorb's report and the account's Library. One work has one dossier: after a lookup absorb matches by DOI, arXiv id, or published DOI, a second reference to a filed work joins it (recording every way it was named), and where two dossiers exist the higher level (the older on a tie) stays and the other becomes a pointer with its notes moved. An unresolved reference is **important** when the owner named it or a standing passage, a concern, or an objective cites it; it is raised once its failure is final (no match anywhere, the flag given up, a URL no service can look up), never while retrying: under `interactive` a notice linking to it, a line under "Waiting on you", and the first item of the next conversation; under `checkpoints` under "Waiting on you" and put at the next conversation or with the end notice; under `autonomous` asked at setup only (the setup batch includes those still retrying) and afterward listed, never notified. The owner hands over a DOI or an exact title (back to the scout) or a PDF (the reference's source, gitignored, the scout trying its title; failing that the dossier is found with `resolved_by: owner`, details read from the PDF), recorded without asking; "leave it" settles the item until the order. Intake records references as `{identifier, note}`, never looked up there; `INTAKE.md` renders each as a top-level item with the note nested under it, absorb reads only top-level items, and a local file is never a title query (a PDF sorted as a reference becomes its source; any other file is a document). The dossier schema gains `retry`, `resolved_by: owner`, notes, and the names a joined dossier records. No model tokens; OpenAlex at USD 0.001 a request is the only paid lookup.
- **Methods and the code** ([Methods and the code: the repository and the rule both ways](https://github.com/Bernaljp/wayline/issues/187); [Inventorying the methods a codebase develops and uses](https://github.com/Bernaljp/wayline/issues/178)): a project stays one working repository, and everything to publish lives under `code/` (the package or scripts, tests, environment locks, `README.md`, `LICENSE`); code cuts the **code repository** from it with `git subtree split --prefix=code`, never including `research/`, `harness.json`, `jobs/`, or `results/`. Code tickets' touch sets go under `code/`. Its shape, settled by one setup question with its remote and license: a package holding the developed method and every model the work applies it to, each callable from the package, with a method that has its own maintained package (SINDy through pysindy) a pinned dependency, never copied; or a reproducibility repository of scripts, helpers, and the environment alone. Intake absorbs a project's own clone into `code/` with its history (`git subtree add --prefix=code <clone> <recorded commit>`, uncommitted changes as the next commit named as such, the clone's `.git` kept outside the tree, the upstream remote and commit and the inherited license recorded), which fixes the empty gitlink; code from someone else's paper stays `absorb --code`, a reference. The harness creates a private GitHub repository with `gh` (a new private repository carrying the upstream history for a taken-over one that is not the owner's, never a fork; the owner's own repository as the remote when the owner says wayline can take it over, confirmed once if it is public), and code, never a worker, pushes `code/`'s split after every wave that changed it and the `paper-N` tag at each order; making it public is the owner's word only, at setup or later by a confirmation card, on the irreversible list. "Aligned" means the code repository at the paper's tag recomputes every number and figure the paper prints: every job and ticket run records the commit of `main` it ran at; code renders `code/REPRODUCE.md` and `reproduce.json` (per result, the commands that made the runs its findings cite, their inputs, outputs, time, and hardware), environment locks from the environment the jobs ran in, and `code/README.md` (keeping a part the owner writes); at the order, code re-runs at the tag every result whose code changed since its run and cuts a ticket only when its numbers moved. **The rule from code to Methods**, a Type-A check at each acceptance over the diff in `code/` by parsers with no tokens: every developed method the diff adds or changes is named by a `code` tag in a current Methods passage (plumbing excluded by code; anything else the worker calls not a method goes in `not_methods`, which the verifier judges); every used method the diff adds is named in a Methods passage through an alias table; every non-default parameter it sets, and every sensitive default left unset (an unseeded random state, default solver tolerances), has a one-sentence reason in the new result field `parameters`, where the worker also lists values the parsers cannot see, code fills each value and default, and the verifier's existing verdict judges the reasons. The signature pass runs in the project's own environment, a default marked "not checked" until it is installed. Parsers: Python by `ast` plus `inspect.signature`, MATLAB by tree-sitter-matlab in the tools venv with a documented-defaults table and backward slices, filling the code dossier's seam too; another language gets a Sonnet reading of the changed files at acceptance (grep-checked, about $0.40 per 1,000 lines) until its first project files an adapter as a harness ticket. Inherited code alone gets a Sonnet reading at setup (medium, per file where the parsers see developed code, items grep-checked, concerns as leads into the verifications; about $2.30 for PINF). **The rule from Methods to code** is no gate: a Methods method with no code behind it is listed among the outline's gaps, and the availability statement may not claim the repository reproduces it. At every render the inventory generates into Methods a parameter table (method, parameter, value, default, reason, a `code` tag; a reason editable like a passage), the software and its exact versions from the locks, and a proposed citation only for a package whose method the paper relies on and that publishes a preferred citation. A drawing that computes a number a finding cites also returns its Methods passage; at the order code copies the scripts behind every figure and every cited drawing number into `code/figures/`. Ports and reimplementations live in `code/` as the package's own code with one script per result under `code/repro/`; inherited code stays at its upstream path, changed only by a reproduction's edits.
- **Tools, packages, and environments** ([Asking for and installing software a project needs](https://github.com/Bernaljp/wayline/issues/188); [Installing software without root on this workstation](https://github.com/Bernaljp/wayline/issues/179)): four kinds. **The harness's tools** (pandoc, the embedding model, tree-sitter-matlab, matplotlib and seaborn, micromamba, uv) come with `wayline tools install` beside docling, no ask at any autonomy. **A project's tools** (Octave, R, Julia, or what a plotting setting needs) install after a yes. **A project's packages** go into its own environment with no ask, locked in `code/`. **Licensed software** (MATLAB and its toolboxes) is the owner's alone: the owner installs it and says where, code records it (`installer: owner`, version and toolboxes from `ver`) and runs one `matlab -batch "ver"` check job, a failure keeping the decision open. Routes, never root, every download checked against its published digest: micromamba from conda-forge for pandoc, Octave, R, and R's packages (its static binary at `~/.wayline/tools/bin/`, `MAMBA_ROOT_PREFIX` and `CONDA_PKGS_DIRS` under `~/.wayline/tools/mamba`, one prefix per tool at `~/.wayline/tools/envs/<tool>`), which settles pandoc's route; Julia from its tarball at `~/.wayline/tools/julia-<version>`; Python packages always through uv (the `python -m venv` fallback goes, since it fails here); the model from Hugging Face at a pinned revision into `~/.wayline/tools/models/`. Packages are per project (`<project>/.venv`, an R library with `renv.lock`, a Julia environment, Octave Forge in the shared prefix unless two projects disagree), gitignored, locked in `code/`. `~/.wayline/tools/tools.json` gains one entry per tool (absolute executable, version, required environment, route, lock or digest or revision, installed when, installer `harness`, `owner`, or `system`), merged one entry at a time; `wayline tools install` records LaTeX, poppler, LibreOffice, and git as `system` by absolute path and never changes them; `wayline tools show` prints the record. Code installs, never a session and never the owner from a printed command, through `wayline tools install <name>`, synchronous in a setup conversation and a job mid-run so the conductor never waits on a download. A ticket names its tools (`software: ["octave"]`, set by specify, the planner, or the critic) and is not launchable until they are recorded; a job spec names a tool (`"tool": "octave"`) and `wayline job add` writes its absolute executable and environment into `command` and `env`; a session calls `wayline tools run <name> -- <args>` for short calls; each job record carries the name, version, and lock digest of every tool it called. The ask is a decision ticket of the new class `software`, one per tool, pausing only the tickets that need it, stating the route, the download and disk sizes from a dry run, the tickets waiting, and the cost, with Install (recommended), Not now, or Go without; the owner's under `interactive` and `checkpoints`; under `autonomous` the setup question lists every tool the planned work needs, and afterward the decider answers, installing free software through these routes but never changing an installed tool or the tools venv and never licensed software. A failed install is retried once, then becomes the same decision with the error. A gap found mid-ticket (an installed tool lacking what the code needs) ends the worker `blocked` with it in `blocked_on`, and code opens the decision. Installing free software is not irreversible and not a global harness change; changing what is installed is the owner's word. **Environment**, `harness.json.environment`: `shared` (the default), `conda` (one prefix at `<project>/.wayline/env`), `venv`, or `container` (one Singularity image at `<project>/.wayline/env.sif`, built without root through a sandbox from `docker://` and micromamba, as measured; Docker only where the account reaches it). The owner moves a project at any time by saying so: code builds the new place from the locks, runs each tool's version check inside it, and only then switches; past results stand; MATLAB stays bound in from the host; the decider never sets it. Whatever the setting, the order writes an environment file and a Dockerfile into `code/` from the same locks.
- **Converting documents** ([Converting documents both ways with the tools on this machine](https://github.com/Bernaljp/wayline/issues/177)): pandoc (the conda-forge build) is the route both ways. In: a `.docx` keeps headings, every equation as LaTeX, tracked changes in accept mode, and comments with their anchors; a small standard-library reader beside it decodes Mendeley Cite citations into CSL-JSON and reads comment threads; a `.tex` goes through pandoc; a PDF only when no source exists, through `pdftotext -layout` with margin line numbers stripped, docling adding structure where installed; `.xlsx` by the standard library, one CSV per sheet; LibreOffice only to turn a `.doc` into a `.docx`. Out: pandoc gives LaTeX for a venue class, a PDF through `latexmk` (xelatex for Unicode), a `.docx` with native equations, and a Markdown copy; pandoc-crossref resolves equation and figure references; a Lua filter turns `ref` tags into citations and strips every other tag. Conversion is code at every autonomy.
- **The paper order and what it compiles** ([The paper order and what it compiles](https://github.com/Bernaljp/wayline/issues/192)): the **paper order** is the owner's, said in a conversation and confirmed by a card carrying a readiness list code builds at no cost (open objectives, the outline's gaps, the general report's last kill argument and its standing points, results changed since their last drawing, inherited claims unchecked or unverifiable, open contradictions, unresolved references, concerns for the order, the outline's link) and the cost (about $35 to $40 for six figures when the first build passes, about $10 more per failed build); nothing blocks the owner's order, an order with nothing verified included (the batch then asks whether to keep the unchecked inherited results as stated, the default, or leave them out, and `PAPER.md` says none was checked). `wayline paper` stays as the session's tool and the dashboard's Confirm runs it; no decision ticket. Under `autonomous`, one setup question (default yes, no venue) decides whether the decider judges the order: only at the stopping rule's own ends after the run-end gates and drawings, never after `budget_spent`, `stall_strict`, `stopped`, or `switched`; code checks first (no named objective open, the last kill argument passed or its scope-downs done, no main-text gap, every changed result drawn, "Do the inherited results hold?" answered at a start midway), and only then one decider session on `opus max` reads `REPORT.md`, `OBJECTIVES.md`, and `OUTLINE.md` and orders or writes why not. The order is a rest point: running tickets finish, nothing new launches, changed results are drawn, the paper is composed from that commit, and the run resumes afterward if it had not ended; it starts no research ticket, and a gate point that needs evidence is a proposed objective. Under `interactive` and `checkpoints` one batch is asked before any model writes: the **figure plan**, oversized figures, open contradictions (each with code's suggested side or "a typo, fix it"), unverifiable claims the owner might keep, unresolved references (hand over, drop, or drop the reference but keep the claim marked "to be resolved"), and the outline's open proposals, each with code's default and "take all defaults" as one answer; under `autonomous` the decider answers it and each choice is listed under "Decided for you". The order then runs code's steps (tag `paper-N` and push it, re-run stale results, copy figure and drawing scripts into `code/figures/`, the code-to-Methods check over all of `code/`), then one writer session (`opus xhigh`) composes the whole **paper** from the outline and the sections, each part its own field, and code writes `research/paper/`: `title.md`, `abstract.md`, `introduction.md`, `results.md`, `discussion.md`, `methods.md`, `supplement.md`, `front.md`, each heading with its outline id; `figures/F1/` and `S1/` with `caption.md`; `tables/T1.csv` with `T1.md`; `response/<critique>.md`; `references.json`; `alternatives/<part>-<n>.md`; and the build report `PAPER.md` (the commit and tag, each part with its version, the batch's answers, what was left out and why, the owner's passages whose wording changed, each gate with the points still standing, and the cost). Figures: code builds the plan from the outline, one figure per main-text result whose panels are every plot marked keep (or, with none marked, every plot the synthesis cites), with no panel cap; maybe-marked and other plots go to its supplementary figure, drop-marked never appear; a venue's display-item limit moves the last results in outline order to the supplement; the figure role starts from the planned plots (finish in the library each was drawn in, caption, checks with the five new ones, honesty verdict; two sessions), composes every planned panel (a Type-A check confirms each is present), never splits one result into small figures or drops a panel to simplify; a figure too large for one page is in the batch with a proposal to drop or split, and under `autonomous` it splits, never drops; a figure from nothing only on the owner's request or the venue's requirement. Tables chosen become numbered tables rendered from their CSV. Unverifiable claims are left out and listed unless the owner keeps one, stated as not verified with its reason; unchecked framing is built on, never copied; inherited title, abstract, and captions never reach the paper; a supplementary table renders each inherited result's verdict, route, narrowed wording, and reasons, and the writer adds one Methods paragraph naming the routes. ## Testing Decisions

**What a good test is.** A test exercises one seam from the outside and asserts on what a user or the next component can observe: the journal events written, the ticket statuses in `graph.json`, the files in the ledger, the exit codes, the HTTP responses. It never asserts on private functions or on the order of internal calls, never sleeps, never touches the network, the subscription, or the GPU, and runs under `python -m unittest` from the harness root. Live behavior that cannot be faked (a real `claude -p`, a real `systemd-run`, a real tunnel) is verified once per milestone by its first acceptance criterion and recorded in `docs/verification/`, not by the suite.

**Seams.** The four the brief and the map imply, plus two the four do not cover:

1. **The worker launcher** (decision 3): one `launch` and one `resume` function over a `LaunchRequest`, one real backend, and a fake backend for tests. The fake is scripted per test with the envelopes to return in order, including a `structured_output` (or none, or an invalid one), `permission_denials`, `rate_limit_events` with any utilization or `status: rejected`, an `api_error_status`, an exit code, a session id, and a patch to apply and commit in the worktree before returning, so that integration and conflicts are testable. Every model call in the harness goes through this seam, so the verifier, the consultant, the decider, the planner, the critic, the classifier, and the fixture judge are all faked here; no second model seam exists.
2. **The job runner** (decision 6): `launch`, `poll`, `kill`, `cleanup` over a `JobSpec`, with `systemd_run`, `setsid`, and `fake` backends. The fake advances jobs through scripted `JobState` sequences, writes scripted outputs and logs, and fakes host and GPU OOM so the ladder and the manifest are testable. Resource detection reads from a recorded snapshot in tests.
3. **The ledger** (decision 2): the only writer of `research/`. Tests build a ledger in a temporary project from fixtures, drive the code under test, and read the ledger back; the refusal rules (unmanifested provenance, a finding without a locator) are tested here directly.
4. **The conductor** (decision 5): tested by replaying a journal. A recorded journal plus a fixture ledger is the input; the assertion is the reconstructed view (statuses, attempts, session ids, pause, stall counter) and the events the next wave appends. The wave function is called directly; the sleep and the window wait live in the `run` verb. Idempotence is a test: replaying twice yields the same view. The M1 kill-and-resume demo has a recorded journal under `fixtures/conductor/` that the suite replays.
5. **The fetcher** (added; decision 9): one `fetch(url, headers) -> Response` behind which the scout, the arXiv source fetch, the plot index crawl, the guidelines build, and Unpaywall run, with a recording backend for tests (`fixtures/fetch/<host>/<request hash>.json`). Why a fifth seam: the four above cover models, hardware, the ledger, and control flow, but M3 and M7 talk to seven external services, and without one fetch seam their tests would either hit the network or fake `urllib` in five places.
6. **The tool runner** (added by decision 17; it already exists as the subprocess seam the PDF chain and `wayline tools install` share): one function that runs a program and returns its exit code and its two streams, and the `tools.json` record it resolves a tool's name through to an absolute executable and its environment, with a recorded runner for tests. Every recorded tool goes through it: pandoc, `latexmk`, tree-sitter-matlab, the embedding model, micromamba, uv, Singularity, `matlab -batch`, `gh`, the poppler tools, and the converters. Why a sixth seam: v1.1.0 calls about a dozen programs the machine may or may not have, two of them network writes (`gh repo create` and the push of the code repository), and without one runner their tests would either need the programs installed and the network reachable or fake `subprocess` module by module. The owner confirmed it on 2026-10-18. Plain `git` is not behind it: tests keep running real `git` against temporary repositories, `git subtree` included.

No other seam is introduced. The dashboard is tested through HTTP against a fixture ledger (seam 3); the guards through piped stdin (the 14 recorded cases plus the command cases); the frontmatter parser and the schema validator with round-trip and negative cases; the tick by calling its function with a fake heartbeat, a fixture journal, and a fake launcher and notifier; the absorb pipeline with a fixture inventory, the fake launcher returning scripted reader entries, and the coverage audit asserted; the figure checks against committed sample PDFs and PNGs; the provenance linter against a sample report with the classifier faked.

**Fable's weekly window** (decision 15) uses seams 1, 3, and 4 and adds none. The fake launcher is scripted with a Fable refusal (a rejected `rate_limit_event` of type `seven_day_overage_included`, `api_error_status: 429`, exit 1, the "reached your Fable limit" text) and with a subagent's failed task inside an allowed session, and the tests assert on each `LaunchRequest`'s model, effort, context cap, and agent models. The conductor is tested by replaying journals that hold the hold, each consent, fallback launches, verdicts, and decisions, and the ask with its superseded close and its timeout under a fake clock, asserting on the reconstructed view and the events the next wave appends, idempotence included. `wayline status` and `REPORT.md` are rendered from fixture journals. Prior art: the recorded refusal streams and `/usage` text in the research note on the branch `research/fable-weekly-window`.

## Out of Scope

Ruled beyond M0 to M7 by the brief (Section 14) and the map; each returns only as a fresh effort.

- The Claude Agent SDK and any API-key runtime (C1). Fixtures and workers never use `--bare`.
- A scheduler serving several projects at once (OPEN-3).
- Containers for worker sessions or experiment jobs (OPEN-5; reconsidered only if a live milestone shows a need). A project's environment may be one Singularity image for its tools and packages (decision 17); workers still run on the host.
- A GitHub Issues mirror of the ticket graph (after M5 at the earliest, optional, one-way).
- An external verifier backend (the `codex` CLI) and its invocation shape: verdicts are Claude-only unless the owner opts in per step (OPEN-6).
- Mirror trees or backends for other CLIs: the worker launcher leaves the seam, nothing else (Section 14).
- Submitting anything anywhere; the harness stops at a paper and its compilations the owner reads, and a response to a critique is never sent.
- A graphical interface beyond the local dashboard; `status` and `REPORT.md` remain the views that work without it.
- A native Telegram sender or any notification channel beyond `notify-send` and the detected `hermes send` (the notifier's fallthrough is the whole channel design).
- A model in the scheduling loop, a skill that calls a skill, a long-lived process holding a paper in context, a shared document edited by models, a wall-clock loop around a verdict, anything mutable shared between projects (Section 14).
- Quiet hours and a per-window worker budget (OPEN-8: none until a night is measured).
- Code dossiers and the code-to-Methods parsers for languages other than Python and MATLAB (decision 17: a Sonnet reading stands in until the first such project files an adapter).
- A Semantic Scholar key and the OpenAlex free key (the keyless chain works without them).
- Compressed internal notations or an embedding index for retrieval (OPEN-11: only through the evolve loop, only when they win the benchmark). Decision 17's local embedding model proposes repeated claims and result merges; it is no retrieval index.
- Falling back from Opus, Sonnet, or Haiku: they share the all-models week on this subscription, so a spent week leaves nothing to fall back to (Fable fallback map).
