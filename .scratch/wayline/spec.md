## Problem Statement

The owner is a computational researcher who works alone on a workstation (one NVIDIA RTX 3090 with 24 GB, 128 cores, 1 TB RAM, 11 TB disk, Ubuntu with systemd 255 and user lingering enabled) with a Claude Code Max subscription and no API keys. A research effort starts anywhere between a vague direction with a pile of references and a precise plan with half an implementation, sometimes with a quantitative goal. Carrying it to a report today means the owner sits in the loop at every step: reading papers, deciding what to try next, launching experiments, waiting on them, checking results, and typing prompts into skills that call other skills and skip steps silently. Nothing keeps working when the usage window closes or the terminal dies. Nothing forces full reading of the papers that matter. Nothing stops a session from acquitting its own work. Nothing traces a claim in a report back to the file it came from. Every project leaks into the next through shared skills and carried-over context, and when the owner sees what should have gone better there is no safe way to make the pipeline change itself. The subscription also counts Fable, the model that the hardest tickets, the planner, the decider, the writer, and the verifier of every Opus author run on, in a weekly window of its own apart from the all-models week; once that window is spent, every Fable request is refused until the weekly reset, days away, and a conductor that treats the refusal like a closed window for every model stops all of the night's work, not only Fable's.

## Solution

wayline is a harness repository and one command, `wayline`, that turns a research intent into `REPORT.md`, the stopping point, under the owner's subscription alone. Deterministic Python (standard library only) decides what runs, when, on which resources, and what counts as done; models decide only content, one ticket per fresh `claude -p` session in a conductor-owned git worktree, under `--permission-mode dontAsk`, a per-role tool restriction, and hooks that deny writes outside the ticket's touch set. Everything durable about a project is the ledger under `<project>/research/`, written only by the ledger module from structured results; the append-only journal is what the conductor replays to resume and what the report is built from. Experiments and analyses run as detached jobs under the user's systemd manager, pinned to assigned GPUs and cores, polled by code; no session waits. A recurrent tick relaunches the conductor after usage windows and answered decision tickets and reaches the owner's phone through Telegram. Type-A gates are judged by code; Type-B verdicts come from a fresh Claude session that carries none of the author's context, on a different model from the author whenever the model table's choice is available. When Fable's weekly window is spent, only Fable work is held: under the owner's fallback consent `auto` it runs on Opus at the same effort, marked as fallback; under `ask`, the default, the owner is asked; under `wait` it waits for the reset. Every claim in the report carries a provenance tag the linter resolves. The owner steers from a local dashboard reached through one SSH tunnel, answers decision tickets from it or from the command line, raises autonomy at any moment, and files feedback that the evolve loop turns into tested, tagged harness changes, local to the project first and promoted to the harness only by the owner. On request the report continues into a paper under a chosen venue's guidelines. The build is eight tracer bullets, M0 to M7, each demoable on its own exactly as BRIEF.md Section 16 states.

## Milestones and acceptance criteria

### M0 Skeleton

Demo when done: "`init` lays out a project; the conductor runs one trivial ticket through `claude -p` in a worktree with `dontAsk`, validates the structured result, runs a machine check, fast-forwards main, closes the ticket, journals it. Unattended, one command."

1. Carried verbatim from the closed prototype ticket 16 (Prototype: the M0 worker launch):

   > What is the exact launch that works end to end? Build a throwaway script that:
   >
   > 1. Creates a scratch git repo with one file and a `.claude/skills/<test-skill>/SKILL.md`, adds a worktree on a `ticket/1` branch.
   > 2. Launches `claude -p` from the worktree with `--agents` (role prompt, `model: sonnet`, a tool allowlist, `maxTurns`, `skills: [<test-skill>]`), `--agent worker`, `--effort low`, `--permission-mode dontAsk`, `--settings <file>` carrying a `PreToolUse` touch-set guard and a `Stop` guard, `--output-format stream-json --verbose --json-schema <result schema>` (per OPEN-1: parse the final `result` message for `structured_output` and record any `rate_limit_event`), `--fallback-model sonnet`, and `< /dev/null`. Restrict tools with `--disallowedTools` or `--tools`, never an agent `tools` allowlist, which removes the StructuredOutput tool (Headless worker launch facts).
   > 3. Asks the worker to write one file inside the touch set and attempt one write outside it (the guard must block the second), run a machine check, and commit.
   > 4. Validates the envelope, runs the machine check on the branch, fast-forwards main, removes the worktree.
   >
   > Record the exact command, the raw envelope, the hook stdin as seen, turns, duration, and every flag that behaved differently from the notes. The answer is the launch shape M0 implements. Keep the script under `.scratch/proto/worker-launch/` and mark it throwaway.

   The real `wayline init` plus `wayline run` on a one-ticket project stands in for the throwaway script; the recorded artifacts go to `docs/verification/m0.md`.
2. The harness repository is this directory, laid out per Implementation Decisions 1, importable as the package `wayline`, runnable as `bin/wayline` and `python -m wayline`, tagged `v0.0.0` before the first project pins it.
3. `wayline init <path>` lays out a project (Implementation Decisions 1): the CLAUDE.md block, `harness.json` with the pin and the policy defaults, the `research/` skeleton, symlinks from the harness `skills/` and `workflows/` into the project's `.claude/`, the `.gitignore` entries, `git init` when needed, an entry in `~/.wayline/projects.json`, and the active pointer. Running it twice changes nothing the second time.
4. A ticket file in the flat YAML subset (Implementation Decisions 2) round-trips through the in-house parser and serializer; `graph.json` is regenerated from `tickets/` by code and is the only thing the conductor schedules from.
5. The worker launcher exists behind the one-function interface of Implementation Decisions 3 with the `claude_cli` backend and the `fake` backend; the conductor's M0 path (launch, validate, accept in the worktree, integrate, accept on main, close, journal) passes in the test suite with the fake worker before it is run live.
6. The three guards live in `hooks/` with the settings template: `touch_set_guard.sh` and `stop_guard.sh` are the validated scripts from `research-notes/03-hooks/`; `command_guard.sh` is new and normalizes the spelling variants `permissions.deny` misses (absolute paths to `rm` and `git`, `bash -c` and `sh -c`, `env`, `xargs`, `find -delete`, `git -C <dir> push`, `sudo`, and a pipe into a shell). Each guard has piped-stdin tests covering the 14 recorded cases plus the command cases.
7. The live run re-verifies OPEN-5 as decided: `--permission-mode dontAsk` with `--permission-prompts none`, the role's `--allowedTools` and `--disallowedTools`, the `permissions.deny` first layer, and the hooks, including inside a `--agents` subagent (the trivial ticket asks the worker to delegate one read to an Agent-tool subagent; the hook stdin's `agent_id` and `agent_type` are recorded).
8. Skills reach the worker through `--add-dir` plus one `/skill-name` line per assigned skill at the top of the prompt. M0 records whether more than one `/skill-name` line expands; if only the first does, the conductor inlines the remaining skills' `SKILL.md` bodies under a heading in the prompt, and the record says which path is in use.
9. The journal event vocabulary and the envelope fields of Implementation Decisions 2 and 3 are implemented; `wayline status` prints the frontier, running tickets and jobs, open decision tickets, window status, goal progress, and the last ten events.
10. The launcher leaves the portability seam: one `launch` and one `resume` function over a `LaunchRequest`, one backend named `claude_cli`, and no other place in the harness that starts `claude`.

### M1 Frontier and windows

Demo when done: "A five-ticket graph with two independent branches and one touch-set conflict runs with two workers; the conflict serializes; the hook blocks an out-of-scope write; a killed conductor resumes from the journal; a simulated usage-limit error pauses; the tick relaunches after the reset. A read-only dashboard at a local address shows the tabs, the frontier, running tickets, and the journal tail."

1. Carried verbatim from the closed prototype ticket 29 (Prototype: the tick):

   > Does a recurrent job relaunch work after a closed window and after an answered decision? Build a throwaway script that:
   >
   > 1. Installs a user timer (per the research note's recommendation) firing every minute for the test, running `tick.sh`.
   > 2. `tick.sh` reads an active-project pointer file, checks a conductor heartbeat file (pid plus timestamp), and exits if the conductor is alive; otherwise reads a `window.json` (`{"closed_until": <epoch>}`) and a `answers/` directory, and relaunches a dummy conductor (a script that appends a journal line and exits) when the window is open and work remains or an answer appeared.
   > 3. Sends one `notify-send` from the timer's unit.
   > 4. Simulates a closed window, waits for the reset, and shows the relaunch in the journal.
   > 5. Uninstalls the timer cleanly.
   >
   > Record what worked. The answer is the tick's contract (files it reads, conditions, actions) that M1 implements. Keep it under `.scratch/proto/tick/`.

   The real `wayline tick` under `wayline-tick.timer` stands in for `tick.sh`; the pointer is `~/.wayline/active`, the heartbeat is `research/conductor.json`, the window and the answers are read from the journal (the `paused` and `decision` events), and the timer is installed at one-minute cadence for the test and reset to `*:0/15` afterwards. On this machine `notify-send` exits 1 (no notification service), so the criterion is met when the notifier attempts it and falls through to `hermes send`, journaled as `notified` with the channel. Records go to `docs/verification/m1.md`.
2. Carried verbatim from the closed prototype ticket 36 (Prototype: dashboard transport through the tunnel):

   > Which transport feels right from the laptop? Build a throwaway standard-library server with two endpoints over a fake journal that a background thread appends to every second: `/api/journal?since=<n>` polled every two seconds, and `/events` as server-sent events; one static page with project tabs and a journal tail that can switch transport with a query parameter. The owner opens it through `ssh -L` from the laptop and reacts: latency, dropped streams, CPU on the workstation, behavior when the laptop sleeps and wakes.
   >
   > The answer is the transport M1's read-only dashboard uses. Keep it under `.scratch/proto/dashboard/`.

   The real read-only dashboard stands in for the throwaway server: the journal tail polls `/api/projects/<id>/journal?since=<byte offset>` every 2 s by default and switches to the server-sent events endpoint with `?transport=sse`; the owner's reactions through `ssh -o ServerAliveInterval=30 -N -L` are recorded in `docs/verification/m1.md`, and polling stays the default unless the owner judges the logs view annoying (OPEN-20).
3. The frontier and the launchable subset are computed as Implementation Decisions 5 states; the five-ticket demo runs two workers, and the journal shows the conflicting ticket launched only after the ticket it conflicts with was integrated.
4. The touch-set guard blocks the out-of-touch-set write live: the envelope's `permission_denials` names it, the worker's result reports the path, and the journal carries both.
5. A conductor killed with SIGKILL mid-wave is resumed with `wayline run --resume`: journal replay reconstructs every status; a worker still alive at kill time is re-adopted by tailing its stream file; a worker that died is resumed by session id when `system/init` was seen and relaunched otherwise.

### 2. The ledger and the journal

- **The ledger module is the only code that writes under `research/`** (C3, seam 3). Every other module returns structured values and the ledger writes them: JSON and markdown by write-to-temp-then-rename; `journal.jsonl`, `findings.jsonl`, and `qa_log.md` by append. The one exception is the conductor's heartbeat `conductor.json`, rewritten in place under the lock, because its own `flock` is what keeps a second conductor off the project (decision 5) and a rename would move the locked inode out from under every later reader (ticket 09). Every write takes `fcntl.flock` on `research/.lock`, because the conductor, the tick, the dashboard, and the CLI verbs are separate processes that all write through this module.
- **The journal is the bus** (spec decision). Resume is the same replay from offset zero. The dashboard's journal tail uses the byte offset as its version (map ticket 08).

- **Ticket files** (BRIEF 8.2; format per OPEN-4, map ticket 15): `tickets/NN-slug.md` with a frontmatter in a restricted flat YAML subset written by code and parsed by the in-house parser, then a markdown body. The subset (spec decision): `key: scalar` (integer, boolean, `null`, bare or double-quoted string), `key: [a, b]` flow lists of scalars, `key: {k: v, ...}` flow maps of scalars, and one layer of block nesting whose children are `subkey: scalar`, `subkey: [..]`, or `- item` lines (this covers `acceptance`, `resources`, `goal_metric`, `budget`, and `outputs`). A `#` preceded by a space starts a comment outside quotes. No anchors, no multi-line scalars, no deeper nesting. The body carries `## Demo` and free prose; the ledger appends `## Result` after each attempt and `## Answer` on decision tickets. The fields are exactly BRIEF 8.2's: `id, title, kind, difficulty, status, blocked_by, blocking, human_only, touches, resources, role, skills, inputs, outputs, acceptance.machine, acceptance.quality, goal_metric, budget, context_pack, origin, proposed_by, demo`, plus `pinned_difficulty` (OPEN-12, map ticket 24: the human can pin) and `retry` (the footprint ladder of decision 6, experiment tickets only).
- **Ticket kinds** (BRIEF 8.1): `dossier, lit, code, docs, experiment, analysis, figure, writing, review, decision, harness`. **Status** (BRIEF 8.2): `open, running, done, accepted, failed, blocked, needs_human, parked`. Transitions: `open` to `running` on launch; `running` to `done` when acceptance passed on `main` (or, for experiment tickets, when every job exited 0 and the outputs parsed); `done` to `accepted` on a passing Type-B verdict; `running` to `failed`, `blocked`, or `needs_human` from the result or the escalation; `failed` back to `running` on the next attempt; `open` to `parked` when the planner cut it beyond the radius cap or the owner parked it; `rerun` sets `open` with a new attempt counter; a decision ticket goes `open` to `done` when answered.
- **`graph.json`** is regenerated from `tickets/` by code at the start of every wave (one `os.scandir` snapshot decides whether anything changed) and holds, per ticket, the scheduling fields only: `id, kind, status, difficulty, blocked_by, blocking, human_only, touches, resources, role, skills, attempt`. It is the only thing the conductor schedules from; the ticket file is the human view and the place a human pins a difficulty or answers a decision.
- **Schemas shipped** (BRIEF Appendix A plus the ones the map added): `ticket`, `result`, `dossier`, `dossier_entry`, `inventory`, `code_dossier`, `consultant_answer`, `decision`, `proposal`, `goal`, `change`, `registry_entry`, `journal_event`, `job`, `manifest`, `verdict`, `absorb_result`, `figure_request`, `figure_result`, `plot_index_entry`, `guidelines`, `fixture`, `policy`, `harness`, plus `claim_classes` and `report_prose` (added by ticket 40: the sentence classifier's answer and the writer's prose). They are JSON Schema documents restricted to the subset the in-house validator implements (spec decision, because the standard library has no validator): `type`, `required`, `properties`, `additionalProperties`, `enum`, `const`, `items`, `minItems`, `maxItems`, `minimum`, `maximum`, `pattern`, `oneOf` of object schemas, and `$ref` within the same file. Every structured result a model returns is re-validated in code; the CLI's own `--json-schema` validation is not trusted alone (map ticket 01: a `success` envelope can lack `structured_output`).

### 3. The worker launcher (seam 1)

- **Interface.** One function `launch(request) -> Envelope` and one `resume(request, session_id, message) -> Envelope` over a `LaunchRequest` with `role, model, effort, prompt, agent_json, allowed_tools, disallowed_tools, settings_path, add_dirs, cwd, env, schema_path, max_minutes`. `Envelope` carries `session_id, model, structured_output (or None), is_error, subtype, num_turns, duration_ms, duration_api_ms, usage, model_usage, permission_denials, api_error_status, rate_limit_events (list), exit_code, stream_path`. Backends: `claude_cli` (the only real one) and `fake` (tests). Nothing else in the harness starts `claude`; this is the portability seam for another subscription CLI (BRIEF Section 14), and M0 leaves it at that.
- **Every model call goes through it**: workers, the verifier, the consultant (from `wayline consult`), the decider, the planner, the critic, the synthesizer, the evolver, the absorb session, the sentence classifier, the fixture judge. The fake backend therefore fakes all of them.
- **Launch** (OPEN-1, map ticket 12; map tickets 01, 02, 03, 16, 17; BRIEF Appendix B). With `RUN = <project>/research/sessions/<ticket>/<attempt>`:

  ```bash
  git -C "$PROJECT" worktree add -b "ticket/$ID" ".worktrees/$ID" main
  cd "$PROJECT/.worktrees/$ID"
  TICKET_TOUCHES="<colon-separated touch set>" TICKET_ACCEPTANCE_FILE="$RUN/acceptance.json" \
  WAYLINE_PROJECT="$PROJECT" WAYLINE_TICKET="$ID" WAYLINE_RUN="$RUN" \
  claude -p "$(cat "$RUN/prompt.md")" \
    --agents "$(cat "$RUN/agent.json")" --agent "<role>" \
    --model "<alias by difficulty>" --effort "<by difficulty>" \
    --permission-mode dontAsk --permission-prompts none \
    --allowedTools <the role's allowed_tools> \
    --disallowedTools <the role's disallowed_tools> \
    --settings "$RUN/settings.json" \
    --add-dir "$HARNESS" --add-dir "$PROJECT" \
    --output-format stream-json --verbose \
    --json-schema "$(cat "$HARNESS/schemas/result.json")" \
    --fallback-model sonnet \
    < /dev/null > "$RUN/stream.jsonl" 2> "$RUN/stderr.txt"
  ```

  `agent.json` is `{"<role>": {"description": "...", "prompt": "<role system prompt>", "model": "<alias>", "effort": "<effort>", "maxTurns": <by budget>, "permissionMode": "dontAsk"}}` with no `tools` and no `skills` key (map ticket 01: `skills` in `--agents` did not inject when the agent runs as the main session). `--add-dir "$PROJECT"` is passed because a worktree cwd does not discover the main checkout's `.claude/` (map ticket 01); it also grants file access to the project root, which is harmless because the touch-set guard denies writes outside the touch set regardless of access. `--fallback-model` never fires on usage limits (map ticket 02); it covers overload only. `CLAUDE_CODE_RETRY_WATCHDOG` is left unset so workers fail fast and the conductor owns the wait. `< /dev/null` avoids the 3 s stdin wait. Worktrees branch from `main`; the conductor never fetches or pushes (spec decision: pushing is on the irreversible list, and a project may have no remote).
- **The prompt** is assembled by code in this order: one `/wayline-<skill>` line per assigned skill at the top (map ticket 01: this is what injects a skill; if M0 finds only the first expands, the remaining skills' bodies are inlined under a heading); the ticket restated (title, kind, demo, touch set, acceptance commands, budget); the context pack (each file's contents under a header with its locator, in the ticket's order, cut at the tier's cap with the cut noted); the role protocol from `prompts/`; the result schema and the instruction to return it through the structured output; the contract lines: "write only under the touch set; run `wayline accept` before you stop; commit on the ticket branch; never integrate, never close the ticket, never edit `research/`; ask the consultant with `wayline consult <slug> "<question>"`, at most five times".
- **The stream** is kept whole in `stream.jsonl`. The conductor parses `system/init` (`session_id`, `model`; journaled as `ticket_session`), every `rate_limit_event` (`rate_limit_info.status`, `resetsAt`, `rateLimitType`, `unifiedWindows.five_hour.utilization`, `unifiedWindows.seven_day.utilization`, `unifiedWindows.*.resetsAt`; the `unifiedWindows` block is observed, not documented, so its absence degrades to `status` and the `/usage` reading), and the final `result` message, which it copies to `result.json`. The validated object is `structured_output`; a `success` result without that key, or `subtype: error_max_structured_output_retries`, is an invalid result and triggers one resume with the error text (BRIEF 9.1). A `rateLimitType` of `seven_day_overage_included` is Fable's weekly window, which only a Fable request's own event carries; a subagent's failed task (`task_updated` with `status: failed` and `error: rate_limit`) inside an allowed session is parsed as that subagent's refusal, because the parent's `result` stays a success (decision 15).
- **Resume**: `claude -p "<message>" --resume <session_id>` with `--agents`, `--settings`, `--permission-mode`, `--permission-prompts`, `--allowedTools`, `--disallowedTools`, `--add-dir`, `--fallback-model`, `--output-format`, `--json-schema` passed again (map ticket 01: not restored); the `--agent` choice is restored; `--system-prompt-snapshot` stays at its default. A worker whose process died (exit 143, or the pid gone after a conductor restart) is resumed when `system/init` was seen and relaunched otherwise. After a conductor restart, a worker whose pid is still alive and whose environment still names its session directory (`WAYLINE_RUN`) is re-adopted by tailing its `stream.jsonl` for the final result, and so is a worker, alive or not, whose stream already holds that result; both are journaled `ticket_resumed` with `reason: readopted`. A dead one without a result is journaled with `reason: worker_died`, carrying the session id it is resumed by, or none when it is relaunched in the same attempt; while the run is paused or stopping, that resume or relaunch waits (ticket 09). A worker that exceeds `budget.max_minutes` is sent SIGTERM, journaled `ticket_resumed` with `reason: timeout`, resumed once with "you ran out of time; return the structured result now", and then escalated. A session a usage window refused before its first turn is never resumed, verdicts included: it is relaunched (decision 15).
- **Models** are passed as the CLI aliases `haiku`, `sonnet`, `opus`, `fable`; the resolved model name from `system/init` is what the journal records. A Fable launch that falls back (decision 15) is passed `opus` at the same effort, and every agent its `agent.json` defines on `fable` is launched on `opus` with it.
- **Nested launches** are fine (map ticket 01): tests, `wayline consult` from inside a worker, and the evolve loop all launch `claude -p` from inside a session.

### 4. Guards and permissions (OPEN-5, map ticket 17; OPEN-7, map ticket 19; map ticket 03)

- **Per launch** the conductor writes `settings.json` from `hooks/worker-settings.json` with `${CLAUDE_PROJECT_DIR}` replaced by the absolute harness path (hooks and settings load from the worktree cwd only, with no parent fallback). The shape, verified live on 2.1.268:

  ```json
  {"hooks": {"PreToolUse": [
      {"matcher": "Write|Edit|NotebookEdit", "hooks": [{"type": "command", "command": "<harness>/hooks/touch_set_guard.sh", "args": [], "timeout": 30}]},
      {"matcher": "Bash", "hooks": [{"type": "command", "command": "<harness>/hooks/command_guard.sh", "args": [], "timeout": 30}]}],
     "Stop": [{"hooks": [{"type": "command", "command": "<harness>/hooks/stop_guard.sh", "args": [], "timeout": 30}]}]},
   "permissions": {"deny": ["Bash(git push *)", "Bash(git push)", "Bash(git reset --hard *)", "Bash(rm -rf *)", "Bash(rm -fr *)", "Edit(//etc/**)", "Edit(~/.claude/**)"]}}
  ```

  `args: []` runs the script in exec form; the 30 s timeout matters because a timed-out `PreToolUse` hook does not block. Hooks from `--settings` apply in `-p` and inside subagents (`agent_id`, `agent_type` in the input); a `SubagentStop` matcher, if ever added, must accept `workflow-subagent`.
- **Touch-set guard**: `research-notes/03-hooks/touch_set_guard.sh` as validated (reads `tool_input.file_path` or `notebook_path`, resolves with `realpath -m` against `CLAUDE_PROJECT_DIR`, exits 2 with the path and the touch set on stderr, fails closed when `TICKET_TOUCHES` or the path is missing, directory entries match below, file entries match exactly, `jq` required). Touch sets are relative to the worktree root or absolute; an `experiments/ablation_bX/` prefix trick does not match `experiments/ablation_b/`.
- **Command guard** (new in M0): reads `tool_input.command`, normalizes it (strips leading `VAR=` assignments, `env`, `sudo`, `nice`, `xargs`, `sh -c`/`bash -c` wrappers, `$(...)` bodies, pipelines and `&&`/`;` segments, and absolute paths to `rm`, `git`, `find`, `chmod`), and exits 2 on: `git push` in any spelling including `git -C <dir> push`, `git reset --hard`, `git clean -f`, `git branch -D`, `git worktree remove`, `rm -r`/`rm -rf`/`rm -fr` outside the touch set, `find ... -delete`, `chmod -R`, `truncate`, `dd of=`, `curl`/`wget` with an upload flag (`-T`, `--upload-file`, `-d`, `--data`, `-F`, `--post-data`), `pip upload`, `twine`, `gh pr`, `gh release`, and any command whose target path resolves outside the worktree and `results/`. `permissions.deny` is the cheap first layer for the literal spellings; the guard is the second (map ticket 03: deny rules miss `/bin/rm`, `bash -c`, `git -C`).
- **Stop guard**: `research-notes/03-hooks/stop_guard.sh` as validated. The contract is settled here (an M0 open item in map ticket 03): the conductor exports `TICKET_ACCEPTANCE_FILE=$RUN/acceptance.json`; `wayline accept`, run by the worker inside the worktree, executes the ticket's `acceptance.machine` commands with `shell=True`, each under `policy.acceptance_timeout_s`, and writes that file (`ran_at`, `where`, `results: [{cmd, exit_code, seconds, tail}]`, `pass`); the guard blocks the stop once while the file is missing and always allows it when `stop_hook_active` is true. The conductor never trusts the worker's file: it reruns acceptance itself after the worker exits.
- **Tool restriction per role** (defaults in `wayline.json`, overridable per project): a `coder` gets `Read, Edit, Write, Glob, Grep, Agent, Bash(python *), Bash(python3 *), Bash(pytest*), Bash(ruff *), Bash(git add *), Bash(git commit *), Bash(git status*), Bash(git diff*), Bash(git log*), Bash(ls *), Bash(cat *), Bash(wayline accept*), Bash(wayline consult *)` as `allowed_tools` and `WebFetch, WebSearch, NotebookEdit` as `disallowed_tools`; an `experimenter` adds `Bash(wayline job *)` (the verb that writes a job file for the runner) and `Bash(nvidia-smi *)`; the `verifier`, `critic`, `consultant`, `reader`, and `decider` get `Read, Glob, Grep` only, with `Edit, Write, NotebookEdit, Bash, Agent, WebFetch, WebSearch` disallowed. No worker has network tools: fetching is the scout's job, in code (spec decision: network writes are irreversible, and reads are the scout's).
- **The irreversible list** (OPEN-7, map ticket 19): delete or overwrite data, force-push, push to shared branches, exceed the compute or usage budget, spend money, change the goal or the data, change the harness globally, any network write beyond fetching sources. Enforced by: the deny list and the command guard (git and deletion), the absence of network tools (network writes), the resource manager and the pacing thresholds (budgets), `human_only` on goal and data decisions, and the rule that a global harness change under autonomy `autonomous` is proposed, not applied. Default autonomy is `checkpoints`; `human_only` classes default to decisions that change the goal or the data, extendable at intake.
- Containers are deferred (map ticket 17); nothing in M0 to M7 needs one.

### 5. The conductor (seam 4)

- **Process.** `wayline run` is one process, foreground by default, or the transient unit `wayline-conductor` with `--detach` (a plain `systemd-run --user --unit=wayline-conductor -p WorkingDirectory=<harness> <python> -m wayline run --resume`, no `--collect`; the tick relaunches it the same way). The unit also loads `~/.wayline/env` with `EnvironmentFile=-` and carries the caller's `PATH` and `WAYLINE_*` variables, because a transient unit starts from the manager's environment, not the caller's, and the manager's `PATH` lacks `~/.local/bin` where `claude` lives (ticket 13). It writes the heartbeat `research/conductor.json` (`pid, started_at, last_wave_at, harness_tag`) every poll. Two conductors on one project are prevented by `flock` on `research/conductor.json`. `run` refuses to start when the harness checkout's tag (`git describe --tags --exact-match`) differs from `harness.json`'s `harness_tag`, or when `git status --porcelain` on `main` shows changes outside `research/`, and prints the command to fix each.
- **A wave** is one pass of the loop (BRIEF 9.1), and the loop wakes every `policy.poll_seconds` (60). Tests call the wave function directly; sleeping and the window wait live in the `run` verb around it, not inside it (spec decision, so that no test sleeps). The steps, in order:
  1. Read the journal tail since the last offset; apply `control`, `decision`, `feedback`, and `switched` events; regenerate `graph.json` if `tickets/` changed.
  2. Poll every job in `jobs/` (decision 6): exited jobs with parsed outputs close their tickets as done; OOM failures step the ladder; other failures fail the ticket.
  3. Poll every running worker: a final `result` message in its stream, or a dead pid, produces an outcome (below).
  4. Answered decision tickets: journal nothing new (the `decision` event already exists), mark them done, and unblock their subgraph.
  5. Admit proposals (below) and create the tickets the workers requested; create decision tickets from `decision_requests`; under autonomy `autonomous`, launch the decider for open decision tickets not marked `human_only`.
  6. Goal check: with `stop_when: goal_reached` and the best kept `progress` value at or beyond `target` in `direction`, journal `run_ended` with `goal_reached` and go to P6.
  7. Frontier: open tickets whose blockers are all `done` or `accepted` (a difficulty-5 blocker counts only when `accepted`; spec decision from BRIEF 8.4's "accepted only after it"), minus tickets blocked by an open decision ticket, minus everything when a `blocking: all` decision ticket is open. Launchable: the frontier minus tickets whose touch set intersects a running ticket's, minus tickets whose job resources are not free.
  8. Pacing: compute the action from the latest utilization (decision 5, pacing); when the action is `stop` or the run is paused, launch nothing that needs a model; while Fable's weekly window is held (decision 15), drop only the launches on Fable, which fall back or wait as the fallback consent says; subscription-free work (jobs, machine checks, index builds, report rendering) proceeds first.
  9. While launchable is non-empty, worker slots are free (`max_parallel_workers`), and the action allows it: pick by critical-path length (longest chain of dependents), then goal relevance (`goal_metric` present), then lower difficulty when the action is `cheap_only`, then difficulty, then id; allocate resources for job-bearing tickets; add the worktree; launch; journal `ticket_launched`.
  10. Stall check (below). Commit ledger changes to `main`. Write the heartbeat. If the frontier is empty, nothing is running, and no job is pending: P6 (verdicts on every claim), P7 (report), `run_ended` with `frontier_empty`.
- **Worker outcome** (BRIEF 9.1): validate the envelope and the result against `result.json` (invalid: resume once with the error, then treat as failed); run acceptance in the worktree (fail: resume once with the output, then escalate); integrate (below); the ledger writes the findings (refusing any whose provenance is unmanifested), sets `done`, journals `ticket_done`, removes the worktree; quality criteria and difficulty 3 to 5 queue a Type-B verdict (decision 11), whose pass sets `accepted`; `proposals` go to admission; `decision_requests` become decision tickets; `goal_progress` runs the keep-if-better protocol; `touched_outside_declared` non-empty or `blocked_on` set marks the ticket `blocked` with the path for the planner to re-cut; `needs_human` notifies. A `running` result (experiment tickets) records the job ids and leaves the ticket running for the job poller.
- **Integration protocol** (M1; spec decision on the details): one integration at a time under the ledger lock. In the worktree, `git rebase main`; on conflict, `git rebase --abort` and launch the integrator role once in the worktree with the conflicting paths as its touch set and the conflict markers as its context, then rebase again; a second conflict fails the ticket with `next: split`. The integrator runs `git rebase main` itself and resolves it, because a resolution committed on the old branch would meet the same conflict when the commit that conflicted is replayed; the conductor's second rebase is the check (ticket 08). Its session is not journaled as a `ticket_*` event, and it waits, like any model work, while the run holds launches. After a clean rebase, rerun acceptance (`where: rebased`); then `git -C "$PROJECT" merge --ff-only ticket/<id>` on `main`, rerun acceptance on `main` (`where: main`), journal `integrated` with the commit, delete the branch and the worktree. A kept-if-better decision that discards keeps the branch and skips the fast-forward.
- **Escalation** (BRIEF 8.4; OPEN-12, map ticket 24): on a failed attempt, resume the same session once with the failure output; then relaunch one difficulty tier up (new attempt, new session); then file a planner ticket to split it; then `needs_human`. A kind that fails twice at a tier raises that kind's default difficulty by one for the rest of the run (`difficulty_raised`), unless the ticket's `pinned_difficulty` is set. A failure on a launch that fell back (decision 15) counts toward the ticket's escalation and never toward `difficulty_raised`. Outcomes also feed the registry's outcome record for the skills involved.
- **Stall** (BRIEF 9.7; spec decision on counting): a settling wave is one that processed at least one worker or job outcome. The stall counter increments on each settling wave that produced no `ticket_done`, no `finding`, and no `progress` with `kept: true`, and resets on any of them. At 2, journal `stall` and file a replan ticket for the planner (it reads the journal and the failures) or, in radius `strict`, journal `run_ended` with `stall_strict` and render the report. The conductor journals `wave` (`number`, `outcomes`, `progressed`) at the end of every settling wave, which is what a restart rebuilds the counter from, and the count starts again after a `stall` (ticket 09).
- **Keep-if-better** (map ticket 39): for every ticket with `goal_metric`, a Type-A evaluation script named in `GOAL.json` (`eval_command`, receiving the held-out split and the ticket's outputs) computes the metric per seed; the change is kept (fast-forwarded) only if the mean improves in `direction` over the best kept value by more than one standard deviation across at least three seeds; otherwise `discarded` is journaled with the metric, the branch stays, and the findings enter `findings.jsonl` as negative results. Revival is only by a new ticket citing new evidence.
- **Proposals** (BRIEF 9.5; OPEN-13, map ticket 25): admitted when inside the radius (`strict` admits only tickets tracing to a spec claim; `moderate` adds follow-ups probing a claim's failure; `exploratory` adds new directions gated on a scout novelty check), not a duplicate (mechanical comparison first: same kind and normalized-title similarity above 0.8 or identical touch set and origin; then one `haiku --effort low` judgment when the similarity is between 0.6 and 0.8), under the per-wave cap (`strict` 0, `moderate` 3, `exploratory` 6), and with every `blocked_by` existing. Otherwise parked with the reason, listed in `REPORT.md` under "not pursued", never deleted; under `autonomous` the decider reconsiders parked proposals at the end of each wave.
- **Decision tickets** (BRIEF 6.6): created by the planner or from a worker's `decision_requests`, with the question, options, recommended answer, evidence, `blocking`, and `human_only`; `decision_opened` notifies. Answers arrive as `decision` events from `wayline answer`, the dashboard, an edit of the ticket's `## Answer` section (the tick and the conductor detect the edit and journal it), or an interactive session; the decider answers the rest under `autonomous`.
- **Pacing and pause** (OPEN-8, map ticket 20; map ticket 02): utilization comes from every worker's `rate_limit_event` and from `claude -p "/usage" --output-format json` at every tick and at every `run` start (parsed with the regexes `Current session: (\d+)% used · resets (.+?) \(` and `Current week \(all models\): (\d+)% used`, and Fable's weekly window with `Current week \(Fable\): (\d+)% used · resets (.+?) \(`, decision 15); the action is `stop` when either window is at or above `pacing.stop_at` (0.90), `cheap_only` at or above `pacing.cheap_at` (0.80), else `normal` (spec decision: the same thresholds apply to the weekly window, because a fan-out can exhaust the week before the session window resets). A hit limit is any of: a `rate_limit_event` with `status: rejected`, a `result` with `api_error_status: 429`, or a non-zero exit whose stderr or result text contains "hit your" or "reached your", and "limit"; the conductor journals `paused` with `resets_at` from the event or the message (else the next known window reset, else now plus five hours), lets running workers finish, keeps polling jobs, and continues at the reset; the tick relaunches it if it is not alive then. A refusal of Fable's weekly window holds only Fable work instead of pausing the run (decision 15). No quiet hours and no per-window worker budget until a night is measured.
- **Resume** is start: replay the journal from offset zero to rebuild statuses, attempts, session ids, pids, jobs, the pause, the hold on Fable and an open ask (decision 15), pacing, and the stall counter; reconcile with `tickets/` (a hand edit wins for `pinned_difficulty` and answers) and with `.worktrees/`; re-adopt live workers by pid and stream file; resume or relaunch dead ones. Idempotent: replaying twice yields the same view. A result journaled and never carried is carried from its stream, and the verdicts a done ticket earned and no conductor took are queued again. A `control` event carries its arguments in `args`: `stop` takes `drain` and, when `switch` wrote it, `switch_to`; `cancel` and `rerun` take `ticket`; `autonomy` takes `autonomy`; `pacing` takes `stop_at` and `cheap_at`; `model_fallback` takes `model_fallback`. The run that is running applies a `stop`: without `drain` it ends at its next wave and leaves the workers still running to finish, for the next run to re-adopt; with `drain` it launches nothing new and ends once they have returned. A run started after a `stop` is not stopped by it; whether the tick relaunches a stopped project is the tick's contract. A `cancel` or a `rerun` ends the ticket's running worker and waits for its `ticket_cancelled` or `ticket_rerun`, across restarts; a rerun of an answered decision ticket renames its `## Answer` heading to `## Superseded answer`, so that it can be answered again (ticket 09).
- **Termination**: `run_ended` when the frontier is empty and nothing is running and no job is pending, when the goal is reached under `stop_when: goal_reached`, on `control stop`, on `switched`, or on a strict stall. Then P6 and P7 run (decision 11) unless the reason was `switched`.
- **Context packs** (map "Not yet specified"; spec decision on the initial numbers): the pack is the ticket's `context_pack` list rendered in order under locator headers, cut at `policy.context_pack.max_chars[<tier>]` with the cut announced in the prompt; initial caps are in decision 14 and M1 records what was used and how the tickets fared.

### 6. Jobs and resources (seam 2; OPEN-15, map ticket 28; OPEN-8, map ticket 20; OPEN-14, map ticket 26; map ticket 05)

- **Interface.** `JobRunner.launch(spec) -> handle`, `poll(handle) -> JobState`, `kill(handle, hard=False)`, `cleanup(handle)`. Backends: `systemd_run` (default), `setsid` (chosen automatically when `systemctl --user show-environment` fails, that is, when no user manager is reachable), `fake` (tests). The resource manager and the conductor only ever see `JobState` (`running`, `exited`, `oom_host`, `oom_gpu`, `failed`, `killed`, `gone`).
- **Launch line** (map ticket 05, A1, with the unit prefix renamed for wayline and `RuntimeMaxSec` added from the ticket's `wallclock_minutes`, a spec decision so a runaway job frees its slot):

  ```
  systemd-run --user --unit=wayline-job-<id> --slice=wayline-jobs --remain-after-exit --expand-environment=no \
    -p CPUAffinity=<cores> -p MemoryMax=<bytes> -p MemorySwapMax=0 -p TimeoutStopSec=30 \
    -p RuntimeMaxSec=<wallclock seconds> -p WorkingDirectory=<abs project dir> \
    -p StandardOutput=append:<abs log path> -p StandardError=append:<same log path> \
    -E CUDA_VISIBLE_DEVICES=<ids> -E PYTHONUNBUFFERED=1 \
    <abs interpreter> <script> <args>
  ```

  Never `--collect` (it unloads a failed unit before the poller reads it). `AllowedCPUs` is unavailable to the user manager here; `CPUAffinity` is the pinning knob. `MemoryMax` comes from the ticket's `ram_gb`, `MemoryHigh` stays unset. The unit name is the job id and must be unique among loaded units.
- **Poll line and decoding** (map ticket 05, A2): `systemctl --user show wayline-job-<id>.service -p LoadState,ActiveState,SubState,Result,ExecMainCode,ExecMainStatus`. `active/exited, Result=success, ExecMainStatus=0` is exit 0; `failed, Result=exit-code, ExecMainCode=1, ExecMainStatus=N` is exit N; `failed, Result=oom-kill, ExecMainCode=2, ExecMainStatus=9` is a host memory kill; `Result=signal` with 9 and no `oom-kill` is a cancellation; `LoadState=not-found` never implies success (consult the job file and the log). `RuntimeMaxSec` expiry shows as `Result=timeout` and is `failed` with reason `wallclock`.
- **OOM rule** (map ticket 05, A3): `Result=oom-kill` is host RAM (empty log); `Result=exit-code` plus one of `CUDA out of memory`, `torch.OutOfMemoryError`, `torch.cuda.OutOfMemoryError`, `CUDA_ERROR_OUT_OF_MEMORY`, `cudaErrorMemoryAllocation`, `RESOURCE_EXHAUSTED`, `CUBLAS_STATUS_ALLOC_FAILED`, `CUDNN_STATUS_ALLOC_FAILED` in the last 64 KB of the log is GPU OOM; the signature list is one table in the resources module. Retry: host OOM first doubles `MemoryMax` up to the free RAM minus the reserve, then steps the ticket's `retry.host_oom` ladder; GPU OOM steps `retry.gpu_oom`; each step is a set of argument or environment overrides the experiment worker declared (for example `{"--batch-size": 16}`); an exhausted ladder fails the job and the ticket with the log tail.
- **Kill and cleanup** (map ticket 05, A4): `systemctl --user stop <unit>` (SIGTERM, SIGKILL after 30 s), `systemctl --user kill --signal=SIGKILL <unit>` when hard, `systemctl --user stop wayline-jobs.slice` for everything; `reset-failed` for failed units and `stop` for exited remain-after-exit units after the result is read; a nonzero exit from either cleanup is ignored.
- **Fallback** (map ticket 05, A5): `setsid nohup env CUDA_VISIBLE_DEVICES=<ids> taskset -c <cores> sh -c '<abs interpreter> <script> <args>; echo $? > <abs jobs dir>/<id>.exit' >> <abs log path> 2>&1 < /dev/null &` with the pid in `<id>.pid`; poll by the exit file and `kill -0`; kill with `kill -TERM -- -<pid>` then `-KILL`. It loses `MemoryMax`, the `oom-kill` signal, cgroup-wide kill, and manager-recorded status; the job file records `backend: setsid` so the report can say so.
- **Job file** `jobs/<id>.json` (schema `job`, M2 verifies): `id, ticket, array (group id or null), backend, unit, command (argv), cwd, env, devices: {gpu_uuids, gpu_indices, cores, ram_gb}, log, expected_outputs, retry: {host_oom: [...], gpu_oom: [...]}, attempts: [{n, started_at, ended_at, result, exit_code, oom, overrides}], status, wallclock_minutes`. GPUs are recorded by uuid because the index can change per boot; the index is resolved at launch.
- **Detection and slots** (map ticket 05, A8; OPEN-8): `nvidia-smi --query-gpu=index,uuid,memory.total,memory.used,memory.free,utilization.gpu,utilization.memory --format=csv,noheader,nounits`, `nvidia-smi --query-compute-apps=pid,used_memory --format=csv,noheader,nounits`, `/proc/loadavg` field 1 against `nproc`, `/proc/pressure/cpu`, `MemAvailable` from `/proc/meminfo`, `df -B1 --output=avail /home`. Reservation defaults for this machine: no GPU, 8 cores (0 to 7), 64 GB; `harness.json.reservations.processes` lists process names whose GPU memory and cores count as reserved. A GPU slot is free when `memory.free >= need + reserve`, `utilization.gpu < 20` for two consecutive samples, and no wayline job holds it (one GPU job at a time on this box; jobs take the GPU whole). A CPU slot is free when `loadavg1 + cores_needed <= nproc - reserved_cores` and the core allocator (a pool of the unreserved cores, ranges handed out and returned per job) can supply the request. RAM is free when `MemAvailable - reserved - sum(MemoryMax of running jobs) >= need`.
- **Sweeps** are job arrays: the experiment worker writes one job file per member with the same `array` id through `wayline job add`; the conductor launches as many members as fit each wave and the ticket closes when every member exited 0 and its outputs parse.
- **Artifacts** (OPEN-14, map ticket 26): `results/` is git-ignored; every expected output and every file a finding cites gets a `manifest.json` entry `{path, size, sha256, job, run_id, ticket, ts}` where `run_id` is `t<ticket>-a<attempt>` for the attempt that produced or registered it and `job` the job id when a job wrote it; the ledger refuses a finding whose provenance is not in the manifest. Files under about 1 MB may be committed; a heavier file may be when a ticket or the owner says it is necessary (`commit_threshold_bytes` in policy is a soft default).

  Install: `systemctl --user daemon-reload`, `systemctl --user enable --now wayline-tick.timer wayline-dashboard.service`. Uninstall (`init --uninstall-units`): `disable --now` both, `stop wayline-tick.service`, `clean --what=state wayline-tick.timer`, remove the three files, `daemon-reload`, `reset-failed` ignoring errors. Nothing touches the crontab. A transient timer is used only in tests (it dies with the manager). `WAYLINE_UNITS=none` keeps a process and its children off the user manager (`init` writes no unit, `run` starts no dashboard, `--detach` is refused); the test suite sets it (ticket 13).
- **Tick contract** (M1; the prototype's contract made real): under `flock -n ~/.wayline/tick.lock` (an already active unit is not restarted by the timer, the lock covers manual runs): read `~/.wayline/active`; exit if no project; run `claude auth status` and read `claudeAiOauth.expiresAt` and `refreshTokenExpiresAt` from `~/.claude/.credentials.json`, opening a decision ticket (`human_only`) when the login is within 3 days of expiry; read `claude -p "/usage"`, its Fable line included, and journal `pacing` on change; if the heartbeat pid is alive and `last_wave_at` is under `policy.heartbeat_stale_s` (300) old, exit; otherwise poll jobs, run the machine checks that are due, render `REPORT.md`, send due notifications, and relaunch the conductor as the `wayline-conductor` transient unit when work remains (open tickets, running jobs, or an unanswered verdict queue; a verdict queue that waits only on Fable counts once Fable's weekly window has reset, decision 15) and the window is open (the last `paused.resets_at` has passed, or the `/usage` reading is under the stop threshold), or when a `decision` event appeared after the last `run_ended` or `paused`. If the subscription lapses, nothing breaks: the tick keeps polling jobs and exits.
- **Login durability** (map ticket 02): the conductor and the tick run on the stored `/login` credential by default; `init` offers to write `~/.wayline/env` from `claude setup-token` (one-year, inference-only, outranks `/login`, so it is set only in the units' environment, never in the shell profile).
- **Notifier** (spec decision per map ticket 05's recommendation; the map's channel question): one function `notify(event, text)` that journals `notified` first, tries `notify-send -a wayline -u normal "<summary>" "<body>"`, then, on a nonzero exit and when `harness.json.notify.hermes_python` is set, `<hermes_python> -m hermes_cli.main send --to telegram --subject "[wayline]" "<text>"`, and never raises. The first `notified` is the claim, written before any channel runs with `channel`, `ok`, and `exit_code` null, so a channel that hangs or dies never makes the tick send the same notification again; a second `notified` records the channel whose exit code it carries (the last one that ran, `none` when none could run), `ok`, and `exit_code` (ticket 13). `init` detects `~/.hermes/hermes-agent/venv/bin/python` and records it; wayline does not depend on hermes and ships no Telegram sender of its own. Events: `decision_opened`, `ticket_needs_human`, `paused`, goal reached, `run_ended`, and login expiry.

### 8. The dashboard (OPEN-20, map ticket 37; OPEN-21, map ticket 38; map ticket 08)

- **Server**: `http.server.ThreadingHTTPServer` with a small path table; JSON endpoints that read the ledger of every project in `projects.json`; static files from `dashboard/`; no framework, no build step. Change detection is one `os.scandir` snapshot of `(st_mtime_ns, st_size)` per ledger directory inside the poll handler with a 1 s memo. `request_queue_size` is 16 when bound wider than localhost.
- **Transport**: polling. The journal tail reads `/api/projects/<id>/journal?since=<byte offset>` every 2 s and receives only the bytes appended; every other view polls its JSON every 5 s with `If-None-Match` and gets 304 when the snapshot is unchanged. The server-sent events alternative for the journal tail exists behind `?transport=sse` (unchunked `Connection: close` `text/event-stream`, `id:` set to the byte offset, `retry: 2000`, a `select()`-based dead-client check) and becomes the default for the logs view only if the owner judges the 2 s tail latency annoying through the tunnel.
- **Endpoints**: `GET /api/projects`; per project `overview`, `graph.svg` (server-side layered layout: longest path, two barycenter sweeps, straight edges, one link per node, status fills), `tickets`, `tickets/<id>`, `decisions`, `outputs`, `journal?since=`, `logs/<kind>/<id>?since=` (worker streams, job logs, the tick log), `download/<path>` (single files with `Accept-Ranges: bytes` and single-range 206 and 416; a directory streams as a zip through a chunked-encoding wrapper with `write` and `tell`, ZIP_DEFLATED, data descriptors, flat memory); `POST /api/projects/<id>/actions/<name>` for `answer`, `autonomy`, `pause`, `resume`, `switch`, `cancel`, `rerun`, `feedback`, `promote`, `paper`, `pacing`, `model_fallback`, `intake` (file drop), each calling the CLI function of decision 1 in-process and nothing else; no endpoint runs a shell.
- **Views**: overview (phase, autonomy, radius, goal progress, window status with Fable's weekly window and its hold line of decision 15, slots in use, running workers and jobs, last events); graph with the frontier highlighted and a page per ticket (frontmatter, context pack, result, findings, session and job logs); decisions (open decision tickets with options, evidence, and the answer form; the decision record from `DECISIONS.md`, decider decisions first); outputs (an index of `results/`, findings, figures, dossiers, `REPORT.md`, `paper/`, the docs site, every file downloadable, markdown and images rendered inline through `DOMPurify.sanitize(marked.parse(md))`, large artifacts streamed); logs; intake and feedback.
- **Exposure**: bind `127.0.0.1` and print `ssh -L <port>:127.0.0.1:<port> <workstation>` at start; `serve --bind 0.0.0.0` requires the random URL token on every request. Actions always require the token as a header (spec decision: a page open on the laptop could otherwise POST to the tunneled port; views on localhost need no token). The token lives in `~/.wayline/dashboard.json` and `serve` prints the URL that carries it.
- `wayline run` does not host the dashboard; it prints the address and starts `wayline-dashboard.service` if it is not active, so the dashboard outlives every conductor and the tick keeps it alive (BRIEF 9.9).

### 9. Dossiers, the scout, the absorb workflow, the consultant, the knowledge base (BRIEF 7; OPEN-16, map ticket 31; map ticket 04; map ticket 06; map ticket 41)

- **Levels and budgets.** L0: metadata, abstract, verified identifiers, a knowledge-base node, for every reference. L1: one `sonnet --effort medium` call per paper over an input capped at `policy.absorb.l1_max_chars` (40,000) holding the title, abstract, introduction, conclusion, figure captions, and results table headers, returning the L1 record (a short structured record, `relation_to_intent`, `deserves_l2_if`). L2: the full dossier, only on promotion, capped per phase at 3 papers in P1 and 2 each in P3 and P5; every 7.2 trigger promotes automatically inside the budget (named primary at intake; cited by a spec claim, baseline, or method to implement; named in a ticket's context pack; a consultant question L1 cannot answer; the planner or decider promotes) and a decision ticket is opened beyond it. Promotions and demotions are journaled with the trigger; the report lists papers not read in full and why. The numbers live in `policy.json` and are revised from M3's measurements.
- **The scout** (map ticket 06, Section 3) resolves through the fetch seam with `User-Agent: wayline/<tag> (mailto:<owner email from harness.json>)`: for a DOI, Crossref `works/{doi}?mailto=` (polite pool, 10 requests per second), then OpenAlex `works/doi:{doi}` (keyless budget about USD 0.10 per day; sparingly), then Unpaywall `v2/{doi}?email=` for the PDF location, then Europe PMC for biomedical DOIs; for a title, Crossref `works?query.bibliographic=` with `rows=3` and a title-similarity check in code, then OpenAlex `search=`, then Europe PMC `TITLE:`; for an arXiv id, the arXiv API `query?id_list=` at one request per 3 s; bioRxiv and medRxiv through `api.biorxiv.org/details/{server}/{doi}/na/json`. Semantic Scholar is not used keyless (429 on the first call). A reference that resolves nowhere is `existence: unresolved`, never `fabricated`. Every lookup is cached under `research/.cache/scout/` by request hash.
- **arXiv sources** (map ticket 06, Section 2): `https://export.arxiv.org/src/<id>[vN]` (always a gzipped tar; PDF-only submissions return a PDF), one request per 3 s, one connection, ETag cache forever, the source kept under `refs/<slug>/source/` and never published anywhere; the main file from `00README` or the `\documentclass` grep; `latexpand main.tex > flat.tex`, comments stripped, environments by regex (`equation`, `align`, `figure`, `table`, `algorithm`, `theorem` and its kin, `\label`, `\caption`, `\section`); exact equation and figure numbers from the `.aux` `\newlabel` lines after one `pdflatex` run when the source compiles, document-order counting honoring `\nonumber` and `\tag` otherwise; figures from `\includegraphics` targets, PDF figures rasterized with `pdftoppm`; `https://arxiv.org/html/<id>` as the second source when the tarball will not flatten.
- **Non-arXiv PDFs** (map ticket 06, Section 1): always `pdftotext -layout`, `pdfinfo`, `pdfimages -list`, and pdfplumber for the text layer, page count, raw images, word and character boxes, ruled tables; docling as the primary structural converter (typed items with page and bbox, figures and tables to PNG, `do_formula_enrichment` on the GPU); marker 2.0 (GPU, vLLM server) then MinerU `pipeline` as fallbacks; GROBID CRF for structured references and header metadata; nougat rejected; PyMuPDF optional only (AGPL). Converters live in the tools venv from `wayline tools install` and are called as subprocesses; when absent, the inventory records `converter: none` and the reader pass fills more.
- **Inventory** `refs/<slug>/inventory.json` (schema `inventory`; M3's first criterion records the reliable split): `page_count`, `text_layer`, `raw_images[]`, `sections[]` (title, level, page, bbox, numbering by regex), `figures[]` (image file, caption, page), `tables[]` (cells, caption), `equations[]` (latex, number, page; LaTeX from a converter is OCR-derived and marked so, numbers regex-recovered from adjacent `(N)` and confirmed by a reader), `algorithms[]`, `theorems[]` (regex on `^(Algorithm|Theorem|Lemma|Proposition|Definition|Corollary)\s+\d`, boundaries confirmed by a reader), `appendices[]`, `references[]` (GROBID `biblStruct`), `metadata`; every model-derived field carries `provenance: "<tool>-<version>"` and keeps page and bbox so a reader can look at the crop (`pdftoppm -r 150 -f P -l P`).
- **The absorb workflow** (map ticket 04; map ticket 12 (b); map "Not yet specified"): one `claude -p` session per L2 paper, cwd the project root, launched through the launcher with `--allowedTools Workflow Skill Read Glob Grep` (the narrower `Workflow(absorb)` and `Skill(absorb)` forms are tried first and recorded in M3), `--disallowedTools Edit Write NotebookEdit Bash WebFetch WebSearch`, `--agents` defining `reader` (sonnet, medium) and `synthesizer` (opus, high), and a prompt whose first line is `/absorb <path to the chunk manifest>`. Chunking is code: one chunk per section's text cut at `policy.absorb.chunk_max_chars` (30,000) with the inventory items located in it as its obligation list; every figure and table is its own chunk with the image file; equations, algorithms, and theorems ride with their section. `absorb.js` runs `pipeline` over chunks with `agent(prompt, {agentType: 'reader', schema: dossier_entry_list})` (up to 16 concurrent on this box), one entry per obligation item (`item_id, locator, kind, content` in exact form, `importance` 1 to 5, `relation_to_intent`, `oddities`; figure entries add `what_it_shows`, `supports_cited_claim`, `anything_odd`), then one `synthesizer` call over all entries for the prose sections (method, claims, results, assumptions, limitations, flaws found, reusable ideas, open questions, relation to intent), every sentence with a locator. The script returns `{entries, sections, failures}`; the conductor reads it from the run file found by `glob ~/.claude/projects/*/<session_id>/workflows/wf_*.json` and journals `absorbed`. Code merges entries into `entries.jsonl` and `dossier.json`, renders `dossier.md`, runs the coverage audit (Type-A: every inventory item has at least one entry), and queues the depth spot-check (Type-B, the critic, on the five most important items and every claimed flaw). Fallback: N `claude -p` reader launches through the launcher, one chunk each, with the coverage bookkeeping in the conductor; same function signature, selected by `policy.absorb.fanout: workflow | conductor`.
- **Code dossiers** (map ticket 06, Section 4): `git clone --filter=blob:none --no-checkout <url> && git checkout <sha>` (or `fetch --depth 1 origin <sha>`), recording `url, sha, author_date, nearest tag, submodules`; inventory with the standard library `ast` (functions, classes, `__all__`, public symbols, docstrings, line ranges), entry points from `pyproject.toml` through `tomllib` and from `setup.cfg`, configs, tests, scripts, and data requirements by glob and grep; a verified recipe: install into a fresh venv (`pkg @ git+<url>@<sha>`), run the smallest test or example, record the log, `verified: true` only if it ran; the API map records per module what is good, bad, risky, reusable, and how to call the pieces that matter. Other languages wait for the first non-Python dossier.
- **The consultant** (map ticket 41): one role definition, two entry points. From code, `wayline consult <slug> "<question>"` launches `claude -p "<question>" --agent consultant --add-dir <project>/research/refs/<slug> --disallowedTools Edit Write --json-schema consultant_answer.json` through the launcher (with the same `dontAsk`, `--permission-prompts none`, stream-json, and `NotebookEdit Bash Agent WebFetch WebSearch` removals as every read-only role); in a Workflow script, `agent(question, {agentType: 'consultant', schema})` whose result the script returns to code. The answer (`answer, locators[], confidence, not_in_source, promote_requested`) is validated and the ledger appends it to `refs/<slug>/qa_log.md` and journals `consulted`. `promote_requested: true` becomes a promotion inside the budget or a decision ticket beyond it. Workers call the CLI form only: `wayline consult` reads `WAYLINE_TICKET`, counts the ticket's `consulted` events, and refuses the sixth. High-value answers are folded into the dossier at the next absorb pass.
- **The knowledge base** (BRIEF 7.5; OPEN-11, map ticket 23): `research/kb/nodes/<id>.json` for papers, ideas, experiments, and claims; `edges.jsonl` with `extends, contradicts, tested_by, supports, refutes, uses, depends_on`; `query_pack.md` regenerated by code under `policy.kb.query_pack_max_chars` (20,000) for injection into planning and ideation. Dossiers hold depth; the knowledge base holds relations; no prose is duplicated between them. Structured records with locators are the representation; alternatives enter only through the evolve loop when they win the benchmark built from `qa_log.md` questions and journaled ticket outcomes (retrieval hit rate and first-time pass rate).

### 10. The front door: intake, position, grill, decider, spec, planner, registry (BRIEF 6; OPEN-2, map ticket 13; OPEN-12, map ticket 24)

- **Interactive skills** (OPEN-2): `wayline-intake`, `wayline-grill`, `wayline-plan`, `wayline-evolve`, `wayline-paper`, one per phase, each small and fixture-tested, mirrored by the CLI verbs. `init` symlinks them (and every other harness skill) into the project's `.claude/skills/`; `upgrade` refreshes the symlinks. A skill is `SKILL.md` (Claude Code skill frontmatter and body) plus `wayline.json` (`id, scope_kind, capability_summary, applicability_tags, cost_hint, fixtures[], sha256`); model-authored skills may take whatever form retrieves best but carry the same sidecar and a fixture.
- **Intake** (P0): writes `INTAKE.md` (intent, references, data, constraints, autonomy, radius, budgets, the fallback consent `model_fallback` of decision 15, `human_only` classes) and `GOAL.json` as `{metric, direction, target, dataset_or_split, held_out_split, eval_command, baseline: {value, source}, budget: {gpu_hours, wallclock, usage_windows}, stop_when}`; the goal is rejected unless `eval_command` is a script the harness can run on an artifact a ticket can produce. `intake --goal` adds or replaces a goal later.
- **Position** (P2 first half): the critic role, fresh, reads only the dossiers, `INTAKE.md`, and `GOAL.json` and writes `POSITION.md`: the closest-prior-work table (each row a scout-verified citation), the feasibility verdict, the goal feasibility with a revised target when needed, the hostile reviewer's case, and three directions ranked by distance from the intent under the radius.
- **The grill** (P2 second half): the design tree with a frontier of questions whose prerequisites are settled; each tier asks that whole frontier, numbered, each with a recommended answer; facts are looked up (installed tools, the dossiers, the scout) and decisions are asked; every answer lands in `DECISIONS.md` (`question, answer, rationale, decided-by, confidence, timestamp`) and vocabulary in `CONTEXT.md` as it is settled; the switch is raised by saying so or with `wayline switch --autonomy autonomous`, and lowered only by stopping the conductor and editing `harness.json`.
- **The decider**: `claude -p --effort max` on the decider role (fable), `decision.json` as the schema (`question, options, answer, rationale, confidence, decided_by, reversible, timestamp`), input `DECISIONS.md`, `POSITION.md`, `GOAL.json`, the L0 and L1 records, and the query pack; it resolves every open question, every decision ticket not `human_only`, and every parked proposal at the end of each wave, never anything on the irreversible list; the report lists its decisions first. While Fable's weekly window is spent it falls back as decision 15 says, and each `decision` it writes records its model.
- **Specify** (P3): `SPEC.md` with claims and anti-claims, methods, experiments per claim, baselines, data, metrics, success criteria, budgets, out of scope, risks, and seams; Type-A checks (every section present, every claim has at least one experiment id, every experiment names a claim, every metric names a script); one independent verdict (the verifier) that every claim has an experiment and every experiment defends a claim; one human confirmation under `checkpoints`.
- **Plan** (P4): the planner (fable, xhigh) reads `SPEC.md`, the query pack, and the journal and writes `tickets/` and `graph.json`; the librarian step reads `registry.json` and assigns `role` and `skills` to every ticket; the plan-time Type-A checks are a DAG, every ticket with `demo`, `acceptance.machine`, `touches`, `difficulty`, `context_pack`, `role`, `skills`, no machine criterion that passes at the base commit, a `docs` ticket after every `code` ticket that adds public API, and touch sets that are paths under the project; decision tickets are created wherever a choice remains; every assignment is journaled as `assigned`. Difficulty is the planner's by the 8.4 rubric; the conductor adjusts from outcomes; a human pins with `pinned_difficulty`.
- **Registry entry** (map "Not yet specified"; spec decision on the shape): `registry.json` is regenerated by `wayline registry build` and at every planner launch from both scopes; an entry is `{id, kind: skill | role, scope_kind: global | local, path, sha256, capability_summary, applicability_tags: {kinds[], data_types[], libraries[], venues[]}, cost_hint: small | medium | large, fixtures[], outcome: {assigned, passed_first_time, failed, last_used}}`, the outcome computed from `ticket_launched` and `ticket_done` or `ticket_failed` pairs in the journal. A model-authored skill is assignable only when its fixture passes; `claude plugin validate <path>` runs as a free structural pre-check covering every skill directory, once per scope root rather than once per skill, because the validator reads a skill only from the directory that holds `skills/` (ticket 27 measured it: run on a skill directory it reports only that the directory holds no plugin manifest), and its findings are notes on the entry rather than a veto, because the harness's launch path is what has to accept a skill.

### 11. Verification, provenance, and the report (C6, C8; OPEN-6, map ticket 18; map ticket 40; OPEN-10, map ticket 22)

- **Type-B verdicts are Claude-only** (map ticket 18, narrowing C6's chain by the owner's choice): a fresh session on the verifier role that carries none of the author's context (never the session that wrote the work, a resume of it, or a subagent inside it), at the verifier's own effort, for every difficulty 1 to 5; no external model and no human verdict unless the owner enables them per step (the external backend's invocation is out of this spec). The verifier has its own system prompt, none of the author's skills, receives paths (the worktree or `main` at a commit, the result artifact, the claim) rather than summaries, and a scope limit stating the one question it answers. Model table (spec decision; in `policy.json`): author `sonnet` gets verifier `opus high`; author `opus` gets `fable high`; author `fable` gets `opus max`. The table is the default choice, not the rule: a verdict on the author's own model from such a session is a verdict ([Verdicts while Fable is spent](https://github.com/Bernaljp/wayline/issues/93)), and while Fable's weekly window is spent a verdict whose table verifier is Fable follows decision 15. The verdict schema is `{pass, findings: [{text, locator, severity}], question_limit, session_id, model}` and every verdict is journaled.
- **What gets a verdict**: every done ticket with `acceptance.quality`; every difficulty 3 ticket (an independent read of the diff); every difficulty 4 and 5 ticket (an independent read of the result); the spec (claims versus experiments); the depth spot-check of every L2 dossier; every claim in `REPORT.md` and the paper by sampling (below); the figure honesty verdict; the docs read; the kill argument. Verdicts are queued after `done` and launched by the conductor like any model work, subject to pacing; `accepted` follows a pass; a fail journals findings and, for tickets, sets `failed` with `next: resume` carrying the findings as the failure output.
- **The kill argument** (BRIEF 3.2, 13.3; spec decision on shape): two threads, both the verifier role on different sessions: the first writes the single strongest rejection memo against the report or paper from the paths; the second adjudicates it point by point against the artifacts; the outcome is a verdict whose fail scopes claims down (a `writing` ticket) rather than blocking forever.
- **Provenance tags** (map ticket 40): every claim sentence in `REPORT.md` and the paper ends with one or more tags `{res:<run-id>/<artifact>#<locator>}` or `{ref:<slug>#<locator>}`; they render as citations or supplementary references. Sentences are classified (claim, definition, transition, method description) in batches by one `haiku --effort low` call per batch, cached under `research/.cache/claims.json` by sentence hash so a rebuild classifies only changed sentences. Negative results are claims and need a tag. The linter (Type-A) requires a tag on every claim and resolves every `res` tag against `manifest.json` and every `ref` tag against `kb/` and `refs/<slug>/`, failing the build otherwise. The verifier (Type-B) samples 10 percent of tagged claims, at least ten, plus every claim originating from a difficulty-5 ticket, and checks that the artifact or locator supports the sentence. Ticket 40 settled four readings: the linter reads prose only, so the listings code renders from the journal sit between `<!-- wayline:records -->` and `<!-- /wayline:records -->` and are neither classified nor linted; in `REPORT.md` the tags render as numbered footnote citations with a supplementary reference list, which the linter reads back to lint the file on disk; the 10 percent and the minimum of ten are taken of all tagged claims and drawn from those not originating from a difficulty-5 ticket, a claim originating from a ticket when one of its `res` tags names a run of it; and the classifier and the writer are the roles `classifier` and `writer`. `render_report` and `verify_claims` are what P7 and P6 call, `offline` whenever pacing or a closed window forbids model work (as the tick renders), and `wayline report [--verify]` runs them by hand; a session a usage window refuses is a note in the report, never resumed.
- **REPORT.md** (OPEN-10, map ticket 22; BRIEF 6.1 P7) is always the stopping point, rendered by code from the journal, `findings.jsonl`, `DECISIONS.md`, `GOAL.json`, and `graph.json`, with these sections in order: decider decisions (first, with rationale and confidence), open decision tickets and `needs_human` items, the goal trajectory (every kept `progress` value with its run id, discarded changes with their metrics), findings by claim (each sentence tagged), tickets closed with `done` versus `accepted`, judged on Opus while Fable was spent (every verdict and decider answer carrying `fallback_from`, decision 15), negative results, papers read at each level and promotions not read in full and why, "not pursued" (parked proposals, never deleted), proposed global harness changes (under `autonomous`), resources spent (windows, turns per closed ticket, GPU hours), and the run's events. The documentation site is part of done whenever a `code` ticket added public API. The paper is only on request.

### 12. The evolve loop (C10; BRIEF 12; OPEN-17, map ticket 33; map ticket 07; map "Not yet specified")

- **Intake**: `wayline evolve "<text>"`, the dashboard feedback form, or files in `research/feedback/`, each journaled as `feedback`; after every `run_ended` the evolver runs a retrospective over the journal (failures, escalations, stalls, rework, turns per closed ticket, skills whose outcome record is below the registry's median first-time pass rate).
- **Change records** (`change.json`): `{id, observed: {text, journal_events[]}, desired, mechanism: prompt | skill | role | policy | hook | code, scope_kind: local | global, risk: low | medium | high, fixture, status}`. The evolver session (fable, xhigh) writes them from the feedback and the retrospective; code files one `harness` ticket per record through the conductor, with the touch set of a local change being the project's `.claude/skills/<name>/`, `.claude/agents/<role>.md`, or `harness.json`, and the touch set of a global change being a path in the harness repository on the branch `evolve/<id>` checked out as a worktree of the harness repository.
- **Application**: a local change is used from the next wave (the registry is rebuilt at every planner launch and the conductor rereads `harness.json` every wave); a global change runs the harness tests and the whole fixture suite on its branch, and the owner merges it to the harness `main` and tags it (or, under `autonomous`, the report proposes it and nothing is applied).
- **Fixtures** (map ticket 07, the proposed format adopted by map ticket 33): layout `fixtures/<kind>/<slug>/` with `kind` in `prompt, role, skill, verifier, conductor`, holding `fixture.json`, `input/` (`prompt.md`, `agent.json`, `schema.json`, `context/` or `manifest.json` with a sha256 per file), `rubric.md`, `recorded/` (the seed envelope and optional stream trace), and `runs/` (written by the runner only). The record, trimmed to the decision-rich parts of the research note's example:

  ```json
  {"schema_version": 1, "id": "role/worker-smoke-test-ticket", "kind": "role",
   "subject": {"path": "roles/coder/agent.md", "sha256": "...", "also": ["schemas/result.json"]},
   "origin": {"project": "...", "ticket": 3, "session_id": "...", "journal_ts": "...", "change_record": null, "reason": "seed: first green M0 run"},
   "launch": {"model": "sonnet", "effort": "medium", "permission_mode": "dontAsk", "max_turns": 40, "output_format": "stream-json", "json_schema": "input/schema.json", "fallback_model": "sonnet"},
   "input": {"prompt": "input/prompt.md", "agent": "input/agent.json", "context_manifest": "input/context/manifest.json", "input_hash": "..."},
   "structural": [{"check": "schema_valid"}, {"check": "path_in", "path": "$.status", "values": ["done"]},
                  {"check": "path_equals", "path": "$.touched_outside_declared", "value": []},
                  {"check": "path_matches", "path": "$.findings[*].provenance", "regex": "^(results|tests)/.+#L\\d+$"},
                  {"check": "tool_used", "tool": "Skill", "arg": "wayline-sweep-runner"}],
   "judged": {"rubric": "rubric.md", "show_judge": ["$.summary", "$.outputs_written", "$.commands_run", "$.findings"],
              "judge": {"model": "haiku", "effort": "low", "tools": [], "votes": 1, "must_differ_from_subject_session": true},
              "sample_size": 3, "pass_rule": {"at_least": 2}, "strict": false},
   "baseline": {"recorded_at": "...", "subject_sha256": "...", "structural": "3/3", "judged": "3/3"},
   "quarantine": {"status": "active", "flake_limit": 2, "flakes": [], "stable_runs_to_restore": 3},
   "cost": {"per_subject_run": {"turns": 12, "input_tokens": 41000, "output_tokens": 3900}, "per_judge_run": {"turns": 1, "input_tokens": 2100, "output_tokens": 90}}}
  ```

  Structural checks (Type-A, free): `schema_valid` (always first; the runner re-validates), `path_equals`, `path_in`, `path_matches`, `path_contains_all`, `path_contains_any`, `path_count` (`min`, `max`), `path_absent_or_empty`, `file_exists`, `file_absent` (in the run's worktree), `tool_used`, `tool_not_used` (over the stream trace), and `python` (a function in `checks.py` beside the fixture); JSONPath over the validated result; must pass n of n. The judged layer (Type-B): a fresh `claude -p` with no tools, the rubric, and only the `show_judge` fields, answering `{"verdict": "pass" | "fail", "reason"}`; never the subject's session; passes at `at_least` of `sample_size` (2 of 3; `strict` forces n of n). Subject outputs are cached by the hash of (prompt, agent JSON, context manifest, schema, model, effort) and verdicts by (rubric, judge model, output), with a separate namespace per sample index; on a change only fixtures whose `subject.sha256` changed run, the full suite at most once per weekly window; `fixtures.max_turns_per_suite` skips remaining judged samples but still runs the free layer. Fixtures never use `--bare`.
- **Runner contract**: `wayline fixture run [--changed] [--suite]` prints per fixture `structural i/n`, `judged j/n`, the baseline, the delta, and the cost; exit 1 on any regression (a fixture that passed at its baseline now fails), exit 2 on a cost-ceiling stop with partial results. A flake is a run whose outcome differs from the previous run with `subject.sha256` and `input_hash` unchanged; the second flake quarantines (keeps running and reporting, no longer gates, listed in the retrospective, a change record opened to tighten it); `stable_runs_to_restore` consecutive identical outcomes or a rewrite restores it; the runner never deletes a fixture.
- **Recording**: `wayline fixture record --session <id> --kind <kind> --slug <slug>` resolves the session directory from the journal, copies the input pack and the envelope, proposes one `path_equals` per scalar and one `path_count` per array for the author to prune, runs the fixture n times to set the baseline, flags an unstable baseline, and links the fixture id into the change record and, for a skill, its registry sidecar. A fixture born from feedback encodes the desired behavior and must fail on the old subject before the change is accepted.
- **Versioning, pins, upgrade, rollback** (spec decision on mechanics): the harness repository is tagged `vMAJOR.MINOR.PATCH` on every global change; `harness.json.harness_tag` is the pin; `wayline run` refuses when the checkout is not at the pinned tag; `wayline upgrade [--to <tag>]` checks the harness repository out at the target tag (a detached checkout is fine), rewrites the pin, refreshes the skill and workflow symlinks, prints the `CHANGELOG.md` entries between the two tags, and journals `pinned` with `previous`; rollback is `upgrade --to <older tag>`. Global changes are on the irreversible list, so under `autonomous` they are proposed in `REPORT.md`, not applied.
- **Promotion** (`promote skill | role | policy <name>`): copies the local artifact and its fixtures into the harness on a branch `promote/<name>`, runs the tests and the full fixture suite, and once the owner integrates it into the harness `main`, tags; the evolver recommends promotion when a local skill's outcome record is good over several tickets; the decision is the owner's.

### 13. Figures, documentation, guidelines, paper (BRIEF 13; OPEN-18, map ticket 34; OPEN-19, map ticket 35; map tickets 09, 10, 11)

- **Plot index** (`figures/plot_index.json`): built by `wayline figures build-index` from python-graph-gallery (`/all-charts/`), r-graph-gallery (`/all-graphs.html`), Altair (`/gallery/index.html`), seaborn (`/examples/index.html`), and plotnine (`sitemap.xml`), through the fetch seam at one request per second with a descriptive User-Agent, storing metadata and locators only (no prose, no images; the Holtz galleries' license coverage of prose is unverified). Entry schema (map ticket 09, adopted by map ticket 34): `id, family (distribution | correlation | ranking | part_of_a_whole | evolution | flow | map | network | multi_dimensional), chart_type, data_shape: {n_variables, variable_types[], grouping, notes}, when_to_use, when_not_to_use, library_implementations: [{library, function_or_geom, snippet_locator: {source_url, anchor}}], gallery_links[], known_pitfalls[], source_site, source_license, last_verified, last_crawled`. Refresh: `wayline figures refresh` runs the link-liveness check monthly and the full re-crawl quarterly and on a version bump of seaborn, altair, plotnine, ggplot2, or matplotlib, diffing the index page URL lists (plotnine by sitemap `lastmod`). The matplotlib and TikZ `known_pitfalls` are seeded from the traps in the owner's `paper-figures` skill (Section 4 there), regenerated per library, never copied into a role prompt; `traps_hit` entries from figure results are folded into the index through the evolve loop. `figures/structure_index.json` holds the layout structures for framework figures (pipeline, funnel-and-fan, grid, before-and-after).
- **The figure role** (map ticket 11): doctrine kept from the skill (the two paths, the register rules for a framework figure, the honesty discipline, the verification loop as a checklist, the notes file); every human-author assumption replaced. Pipeline: classify the data shape in code; take up to `candidates.max` (5) candidates from the index by data shape, claim type, and the project's library from `figures/style.json`; render drafts (one worker session, or one per candidate under a Workflow script) reading each candidate's pitfalls first and recording `pitfalls_consulted`; a fresh `figure-critic` ranks them with scores (`claim_legibility, honesty, venue_fit, legibility_at_size`) and reasons; the pick is the human's under `interactive` and `checkpoints`, or the decider's rank 1 with `margin_low: true` flagged when the margin over rank 2 is below `figures.margin_threshold` (2); the worker applies the house style, caption, and notes; the 19 machine checks run (`fonts_embedded` by `pdffonts` with Type 42 fonts, `journal_width` by `pdfinfo`, `resolution`, `min_font_pt`, `max_words` for a graphical abstract, `forbidden_text` in the conceptual register by `pdftotext` plus a save-time artist assertion, `caption_panels`, `caption_lint`, `generator_clean` by `ruff`, `regenerates` in a clean environment with SSIM at or above 0.99, `palette` against `style.json` or a CVD-simulated distance, `one_ramp_per_quantity`, `required_vs_optional_line_style`, `selection_representativeness` within the declared tolerance, `schematic_disclosed`, `mixed_data_disclosed`, `crops` produced at 600 dpi, `text_overlap`, `provenance`); then the one Type-B honesty verdict ("does the figure assert something the data does not") by a fresh session on the crops, the full image, the claim, the caption, the spec, and the check report, with equation verification fanned out as sub-verdicts. Guided revisions enter at the styling step with `revision_of` and `change_requests[]`; a request that would make the figure assert something false is refused with the nearest honest alternative rendered as a new candidate, and only a human can mark a refusal `overridden`.
- **Figure schemas** (map ticket 11, Section 4, trimmed to the decision-rich fields): `figure_request/1` carries `ticket, figure_id, mode: unguided | guided, kind: result | framework | graphical_abstract, register: quantitative | conceptual (conceptual forced for the last two kinds), claim: {claim_id, text, claim_type, evidence[]}, data: [{path, sha256, run_id, shape}], style, target: {venue, width_mm, max_height_mm, min_font_pt, min_dpi, max_words, formats[], library}, candidates: {max, families, exclude_index_ids}, comparables[], forbidden_text: {gene_names, dataset_names[], allow_regex[]}, revision_of, change_requests[], budget`. `figure_result/1` carries `status: candidates_ranked | selected | verified | failed_checks | honesty_failed | refused | blocked, data_shape, candidates: [{rank, index_id, chart_type, library, generator, png, rendered, pitfalls_consulted[], score, critic_reasons}], critic, selected: {rank, by, margin, margin_low}, final: {generator, pdf, png, caption, notes, crops[], inputs: [{path, sha256, run_id}], output_sha256}, checks: [{id, type, pass, tool, detail}], honesty_verdict: {type: "B", verdict, session, model, findings[]}, schematic_elements[], selection_statistics[], findings_for_text[] (the unattended replacement for every "tell the author": each becomes a proposal), refusals: [{change_request, reason, alternative_candidate, overridden_by}], traps_hit: [{library, chart_type, description, fix, promote_to_index}], sessions[]`. `figures/style.json` (per project, from `figures/style.default.json`) is the color budget: the categorical set, one ramp per named quantity, the diverging pair, the single special hue, and the equation-parameter colors. Ticket 49 settled what the lists above leave open. `final.inputs[]` entries may carry `panels[]`, the panels an input is drawn in, which `mixed_data_disclosed` needs. Each `figure_result` status requires the block that justifies it. The style also holds `library`, `diverging.cmap`, and `cvd_min_delta_e`, the distance the palette check holds a new color to. `fonts_embedded` passes any embedded font that is not Type 3 (matplotlib reaches that with `pdf.fonttype` 42; pdfTeX's Type 1 fonts qualify too). The checks that need matplotlib read an artist report written at save time by `figures/checks/artists.py` in the project's environment. A generator marks what code cannot infer with a matplotlib `gid`: `panel:`, `quantity:`, `required:`, `optional:`, `connector:`, `container:`. Without such a report, as for a TikZ figure, those checks fail rather than pass unexamined.
- **Documentation** (R28; BRIEF 13.2): the documentarian role and the docs module build a Sphinx site in the project's own environment (the harness stays standard-library) with tutorials, how-to guides, reference, and explanation, an API reference generated from docstrings, executed examples, a figure gallery, and the Read the Docs configuration; machine checks: every public symbol (from the code dossier's `ast` inventory of the project's package) documented and present in the reference, every example runs, the build is warning-free, links resolve; one Type-B read for clarity and completeness against the package's purpose; theme and layout chosen once per project and recorded in `harness.json.docs`. The planner files the `docs` ticket after every `code` ticket that adds public API.
- **Guidelines** (map ticket 10, adopted by map ticket 35): `guidelines/<venue>/guidelines.json`, `source.md`, and `checklist/` (cached reporting-checklist forms only; manuscript templates are linked, never stored) for Nature, Nature Methods, Nature Communications, Cell, Cell Systems, PNAS, PLOS Computational Biology, eLife, Bioinformatics, Genome Biology, NeurIPS, ICML, ICLR, bioRxiv, and arXiv, from the URLs and fields the research note recorded, with Cell and Genome Biology retried at build time and their unverified fields marked. `guidelines.json`: `schema_version, venue, display_name, guidelines_url, date_checked, length_limits: {word_count, page_count, abstract_word_count, notes, excluded_sections[]}, required_structure[], structure_flexible, figure_spec: {max_count, formats[], min_dpi, max_dpi, color_mode[], max_file_size_mb, legend_max_words, notes}, reference_style: {style, max_count, citation}, reporting_checklists: [{name, required, study_types[], url, cached_as}], submission_steps[], template: {latex_or_word_no_login, url, notes, document_class}, license_of_summary_source: {statement, url}, verification: {fully_verified_fields[], unverified_fields[]}` (ticket 52 added `length_limits.excluded_sections`, `reference_style.citation` and `template.document_class`, because a word count "with the venue's exclusions", a style check and a template check cannot run off prose; `figure_spec.notes` mirrors `length_limits.notes`; `verification` names a whole field or, where the source confirmed only part of one, its sub-path). The seven mechanical writer checks, off `guidelines.json` alone: word or page count with the venue's exclusions, section presence (a warning where `structure_flexible`), figure count, format, DPI, color mode, size, and legend length, reference style and count, reporting-checklist presence by detected study type, template or document-class conformance, and the provenance cross-check shared with the linter's sentence pass.
- **Paper** (R26; BRIEF 13.3): `wayline paper --venue <slug>` after the report, or `wayline paper` and the decider picks the best-fitting venue from `guidelines/`; the writer role (fable, xhigh) drafts `research/paper/` from the findings and the knowledge base under C8; the linter and the seven checks run on every build; figures come from the figure role; the kill argument and one independent verdict gate the draft; the owner reads it; nothing is submitted by the harness. The guidelines repository grows through the evolve loop.

### 15. A spent Fable weekly window (the Fable fallback map, [Bernaljp/wayline #89](https://github.com/Bernaljp/wayline/issues/89))

The subscription counts Fable in a weekly window of its own, apart from the all-models week and resetting with it on this account. Opus, Sonnet, and Haiku share the all-models week, so Fable is the only model with anything to fall back to, and it falls back only to Opus. This decision covers the harness's own sessions; the owner's build sessions on this repository pick their model.

- **Reading the window** ([Fable's weekly window: what the harness can read before and at a refusal](https://github.com/Bernaljp/wayline/issues/90)): `claude -p "/usage"` prints `Current week (Fable): N% used · resets <time> (<zone>)` beside the all-models line, parsed with `Current week \(Fable\): (\d+)% used · resets (.+?) \(` and journaled as `pacing.fable`; it is read at `run` start, at every tick, and before any wave that would launch Fable work (the reading takes no turn and costs nothing). Only a Fable request's own `rate_limit_event` carries the window, as `rateLimitType: seven_day_overage_included`; other models' events never do. A refusal is any of: that event with `status: rejected`; a `result` with `is_error`, `api_error_status: 429`, and exit 1; the text "You've reached your Fable limit" (the text signal matches "reached your" beside "hit your"); a subagent's failed task with `error: rate_limit` in an allowed parent's stream, whose own `result` stays a success. No alias or effort escapes the window, `--fallback-model` does not fire on it, and paid overage is on the irreversible list and unavailable to this account.
- **The hold** ([Holding only Fable launches while Fable's weekly window is spent](https://github.com/Bernaljp/wayline/issues/94)): at a refusal, or when `pacing.fable` is at or above `pacing.stop_at` (`cheap_at` does not apply, since there is no cheaper Fable tier), the conductor journals `paused` with `model: fable` and `window: seven_day`; it journals `unpaused` with `model: fable` at the refusal's `resets_at`, or earlier when `/usage` reads Fable under `stop_at`. A `paused` without `model` stays the whole-run pause of decision 5, so a five-hour pause can start and end inside a hold. While the hold stands, launchable drops every launch whose model is Fable or that defines an agent on Fable (tickets, verdicts, the depth spot-check, and the planner, decider, writer, and evolver sessions), and everything else keeps launching; a done ticket any of whose verdicts needs Fable waits whole. Replay rebuilds the hold. A session refused before its first turn is relaunched, never resumed, by every launch path including the gates. A Fable session stopped mid-work waits and is resumed on Fable after the reset under `wait`, or under `ask` before the answer; under fallback it is relaunched as a fresh Opus session in the same attempt and worktree, its prompt saying that a stopped session left partial work there, because resuming a Fable transcript on Opus is unverified.
- **The fallback consent** ([Consent to fall back to Opus: values, default, and where setup records it](https://github.com/Bernaljp/wayline/issues/91)): `model_fallback` in `harness.json` is `auto` (fall back without asking), `ask` (open the ask below), or `wait` (never fall back). The intake asks it beside autonomy and budgets; one value covers the project. A project without the key behaves as `ask`, except for the timeout below, so a missing key stays distinct from an explicit `ask`. `wayline switch --fallback auto|ask|wait` writes `harness.json` first and then journals `control` with `command: model_fallback` and `args: {model_fallback: <value>}`, the way `switch --autonomy` changes autonomy; `project.set_model_fallback` is the function the dashboard's action calls; any value is accepted at any time.
- **What Fable work becomes on Opus** ([What Fable work becomes on Opus: effort, budget, and context cap](https://github.com/Bernaljp/wayline/issues/92)): the same effort (difficulty 4 becomes `opus xhigh`, difficulty 5 `opus max`, the planner, writer, and evolver `opus xhigh`, the decider `opus max`); difficulty and the turn and minute budget unchanged; the context pack cut at `context_pack.max_chars.opus` with the cut announced. A fallback attempt counts toward the ticket's escalation and never toward `difficulty_raised`; the tier up lands on the next tier's launch, which falls back like any launch. `ticket_launched` carries `fallback_from: fable` beside `model: opus`. No role is exempt, and every agent a launch defines on Fable (`--agents` entries, Workflow `agentType`s) is launched on Opus with it.
- **Verdicts while Fable is spent** ([Verdicts while Fable is spent](https://github.com/Bernaljp/wayline/issues/93)): a verdict whose table verifier is Fable is Fable work under the consent. Under fallback, a fresh Opus session at the table verifier's effort (`fable high` becomes `opus high`) takes it: ticket verdicts, claim sampling, both threads of the kill argument, the figure honesty verdict, and the depth spot-check, which never goes to Haiku. Under `wait`, or under `ask` before the answer, it waits, queued, and the ticket stays `done`. `verdict` carries `fallback_from`. The difficulty-5 rule of decision 5 stands. The tick counts a verdict queue that waits only on Fable as work once the window has reset.
- **Asking the owner** ([Asking the owner when Fable is spent and nobody is at the laptop](https://github.com/Bernaljp/wayline/issues/95)): under `ask`, one decision ticket per spent window, keyed by the window's `resets_at`, opened when the hold first drops a launch (a spent week with no Fable work waiting asks nothing); `human_only` under every autonomy, because the decider runs on Fable; `blocking: null`, because the hold already holds Fable work. `decision_opened` notifies with the reset, what is held, the recommended answer, and `wayline answer <id> "<option>"`. The options: `fall back` and `wait` for this window; `always fall back` and `always wait`, which also journal `control model_fallback` with `auto` or `wait`. The answer text is matched against the options trimmed and case-insensitively, and an answer matching none counts as `wait` for this window, with a notification saying so. The recommended answer is `wait` when the reset is under `policy.model_fallback.wait_under_hours` (12) away, `fall back` otherwise. At the first wave past the reset, or on a `control` event setting the consent to `auto` or `wait`, the conductor closes the ticket with a `decision` carrying `answer: superseded` and `decided_by: conductor`, and a late `wayline answer` is refused as for any answered ticket. When nobody answers: an explicit `ask` never times out; a project without the key under `autonomous` gets `fall back` for this window after `policy.model_fallback.ask_timeout_hours` (2), journaled as a `decision` with `decided_by: conductor` and a rationale naming the timeout; otherwise the ticket waits for an answer or the reset.
- **Judgments made by fallback** ([Re-taking judgments on Fable after the reset](https://github.com/Bernaljp/wayline/issues/96)): nothing is taken again after the reset. `decision` gains `model`, and `fallback_from` when the decider ran by fallback; `REPORT.md` lists every verdict and decider answer carrying `fallback_from` in its section "Judged on Opus while Fable was spent"; `wayline rerun <id>` re-asks a decision ticket on demand, answered on Fable once the window has reset.
- **What `wayline status` and the dashboard show** ([What wayline status and the dashboard show while Fable is spent](https://github.com/Bernaljp/wayline/issues/98)): the window line gains `fable <N>`. While the hold stands, a second line follows: `fable    held until <reset>   consent <auto|ask|wait|ask (unset)>   waiting <n>   fallen back <m>`, where `ask (unset)` names a project without the key, `waiting` counts the Fable launches the hold holds, and `fallen back` counts the `ticket_launched`, `verdict`, and `decision` events carrying `fallback_from` since the hold's `paused`. The ask is listed with the other open decision tickets, adding `falls back at <time> unless answered` when the timeout applies. The overview reads the same view, the decisions view answers the ask on its form, and the dashboard gains the `model_fallback` action; no view of its own.
- **Vocabulary the build adds.** `harness.json` gains `model_fallback`. The journal gains `pacing.fable`; `model` on `paused` and `unpaused` (`fable` for the hold, absent for the whole-run pause); `fallback_from` on `ticket_launched` and `verdict`; `model` and `fallback_from` on `decision`, whose `decided_by` gains `conductor` (the superseded close and the timeout); and the `control` command `model_fallback`, whose `args` carry `model_fallback`. The policy gains `model_fallback.wait_under_hours` (12; the ask recommends `wait` below it) and `model_fallback.ask_timeout_hours` (2; only for a project without the key, under `autonomous`). Each lands in the event table of decision 2 or the policy table of decision 14 in the same ticket as the code that writes or reads it, because the suite holds those tables and the code to each other.
- **Build order** ([Where the fallback work lands in the ticket graph](https://github.com/Bernaljp/wayline/issues/99)): the hold lands first, in M1, before the tick; the fallback, the verdicts, and the ask follow in M5; the M5 overnight demo forces a Fable fallback with `--simulate-limit fable:<seconds>` rather than waiting for a genuinely spent week.

## Testing Decisions

**What a good test is.** A test exercises one seam from the outside and asserts on what a user or the next component can observe: the journal events written, the ticket statuses in `graph.json`, the files in the ledger, the exit codes, the HTTP responses. It never asserts on private functions or on the order of internal calls, never sleeps, never touches the network, the subscription, or the GPU, and runs under `python -m unittest` from the harness root. Live behavior that cannot be faked (a real `claude -p`, a real `systemd-run`, a real tunnel) is verified once per milestone by its first acceptance criterion and recorded in `docs/verification/`, not by the suite.

**Seams.** The four the brief and the map imply, plus one the four do not cover:

1. **The worker launcher** (decision 3): one `launch` and one `resume` function over a `LaunchRequest`, one real backend, and a fake backend for tests. The fake is scripted per test with the envelopes to return in order, including a `structured_output` (or none, or an invalid one), `permission_denials`, `rate_limit_events` with any utilization or `status: rejected`, an `api_error_status`, an exit code, a session id, and a patch to apply and commit in the worktree before returning, so that integration and conflicts are testable. Every model call in the harness goes through this seam, so the verifier, the consultant, the decider, the planner, the critic, the classifier, and the fixture judge are all faked here; no second model seam exists.
2. **The job runner** (decision 6): `launch`, `poll`, `kill`, `cleanup` over a `JobSpec`, with `systemd_run`, `setsid`, and `fake` backends. The fake advances jobs through scripted `JobState` sequences, writes scripted outputs and logs, and fakes host and GPU OOM so the ladder and the manifest are testable. Resource detection reads from a recorded snapshot in tests.
3. **The ledger** (decision 2): the only writer of `research/`. Tests build a ledger in a temporary project from fixtures, drive the code under test, and read the ledger back; the refusal rules (unmanifested provenance, a finding without a locator) are tested here directly.
4. **The conductor** (decision 5): tested by replaying a journal. A recorded journal plus a fixture ledger is the input; the assertion is the reconstructed view (statuses, attempts, session ids, pause, stall counter) and the events the next wave appends. The wave function is called directly; the sleep and the window wait live in the `run` verb. Idempotence is a test: replaying twice yields the same view. The M1 kill-and-resume demo has a recorded journal under `fixtures/conductor/` that the suite replays.
5. **The fetcher** (added; decision 9): one `fetch(url, headers) -> Response` behind which the scout, the arXiv source fetch, the plot index crawl, the guidelines build, and Unpaywall run, with a recording backend for tests (`fixtures/fetch/<host>/<request hash>.json`). Why a fifth seam: the four above cover models, hardware, the ledger, and control flow, but M3 and M7 talk to seven external services, and without one fetch seam their tests would either hit the network or fake `urllib` in five places.

No other seam is introduced. The dashboard is tested through HTTP against a fixture ledger (seam 3); the guards through piped stdin (the 14 recorded cases plus the command cases); the frontmatter parser and the schema validator with round-trip and negative cases; the tick by calling its function with a fake heartbeat, a fixture journal, and a fake launcher and notifier; the absorb pipeline with a fixture inventory, the fake launcher returning scripted reader entries, and the coverage audit asserted; the figure checks against committed sample PDFs and PNGs; the provenance linter against a sample report with the classifier faked.

**Fable's weekly window** (decision 15) uses seams 1, 3, and 4 and adds none. The fake launcher is scripted with a Fable refusal (a rejected `rate_limit_event` of type `seven_day_overage_included`, `api_error_status: 429`, exit 1, the "reached your Fable limit" text) and with a subagent's failed task inside an allowed session, and the tests assert on each `LaunchRequest`'s model, effort, context cap, and agent models. The conductor is tested by replaying journals that hold the hold, each consent, fallback launches, verdicts, and decisions, and the ask with its superseded close and its timeout under a fake clock, asserting on the reconstructed view and the events the next wave appends, idempotence included. `wayline status` and `REPORT.md` are rendered from fixture journals. The Fable line of `/usage` and the refusal signals are unit-tested in the pacing module and `verifier_tier` in the gates. Prior art: the recorded refusal streams and `/usage` text in the research note on the branch `research/fable-weekly-window`.

**Modules tested and how.** `conductor` (seams 1, 2, 4), `worker` (seam 1: prompt assembly is asserted on the rendered prompt; stream parsing on recorded `stream.jsonl` files from map tickets 01 and 02, including the `rate_limit_event` and the `success` envelope without `structured_output`), `resources` (seam 2 and recorded readings), `tickets` and `frontmatter` (round trips), `ledger` (seam 3), `tick` (fixture journal and fakes), `dashboard` (HTTP over a fixture ledger, ETag 304s, byte-offset reads, zip integrity with `zipfile.testzip`, range 206 and 416, the token on actions), `gates` and `provenance` (fake launcher, sample reports), `dossier` and `scout` (seam 5, sample PDFs and a sample tarball in `fixtures/refs/`), `evolve` and the fixture runner (a fixture whose subject is a test prompt and a fake judge), `figures` (sample generators and the check functions), `guidelines` (seam 5), `registry` (a fixture skill tree). Model behavior (prompts, roles, skills, verifiers) is covered by the fixtures of decision 12, which cost windows and run on demand, not in the unit suite.

**Prior art.** The piped-stdin cases in `research-notes/03-hook-shape.md` Section 6 (14 cases with expected exit codes) are the pattern for the guard tests; the 76-line server, `scan.py`, and `dag.py` in `research-notes/08-dashboard-transport.md` are the pattern for the dashboard's transport, change detection, and SVG layout; the smoke launch records in `research-notes/01-headless-worker-launch.md` and `02-unattended-auth-and-usage-limits.md` supply the recorded envelopes; the R2 to R11 raw outputs in `research-notes/05-detached-jobs-tick-notifications.md` supply the recorded `systemctl show` readings for the fake job runner's `JobState` values.

## Out of Scope

Ruled beyond M0 to M7 by the brief (Section 14) and the map; each returns only as a fresh effort.

- The Claude Agent SDK and any API-key runtime (C1). Fixtures and workers never use `--bare`.
- A scheduler serving several projects at once (OPEN-3).
- Containers for worker sessions or experiment jobs (OPEN-5; reconsidered only if a live milestone shows a need).
- A GitHub Issues mirror of the ticket graph (after M5 at the earliest, optional, one-way).
- An external verifier backend (the `codex` CLI) and its invocation shape: verdicts are Claude-only unless the owner opts in per step (OPEN-6).
- Mirror trees or backends for other CLIs: the worker launcher leaves the seam, nothing else (Section 14).
- Submitting anything anywhere; the harness stops at a draft the owner reads.
- A graphical interface beyond the local dashboard; `status` and `REPORT.md` remain the views that work without it.
- A native Telegram sender or any notification channel beyond `notify-send` and the detected `hermes send` (the notifier's fallthrough is the whole channel design).
- A model in the scheduling loop, a skill that calls a skill, a long-lived process holding a paper in context, a shared document edited by models, a wall-clock loop around a verdict, anything mutable shared between projects (Section 14).
- Quiet hours and a per-window worker budget (OPEN-8: none until a night is measured).
- Non-Python code dossiers (universal-ctags or tree-sitter wait for the first one).
- A Semantic Scholar key and the OpenAlex free key (the keyless chain works without them).
- Compressed internal notations or an embedding index (OPEN-11: only through the evolve loop, only when they win the benchmark).
- Falling back from Opus, Sonnet, or Haiku: they share the all-models week on this subscription, so a spent week leaves nothing to fall back to (Fable fallback map).
- Paying for Fable overage: spending money is on the irreversible list, and this individual account cannot buy usage credits.
- Taking judgments again, or redoing tickets or integrated code, on Fable after the reset: judgments made by fallback are marked and listed, and `wayline rerun` re-asks a decision on demand.
- The owner's own build sessions on the harness repository: the owner picks their model.

## Further Notes

- **Glossary.** Terms are used as `CONTEXT.md` defines them. Two schema names predate the glossary and are kept as enum values only: the ticket kind `review` (a ticket whose deliverable is a Type-B verdict) and the `run_id` in provenance tags and the manifest (`t<ticket>-a<attempt>`, the attempt that produced an artifact; a job is never called a run). The Fable fallback map added **Fable's weekly window**, **Fallback**, and **Fallback consent**, and sharpened the **Type-B gate** to a fresh verifier session, never the session that wrote the work.
- **Paths and snippets.** This spec names ledger files, harness directories, commands, flags, unit files, and schema fields because in a harness whose ledger is files and whose control flow is a command line those are the interfaces; every quoted command and field was verified in the research notes on Claude Code 2.1.268 and systemd 255 on this machine on 2026-09-11 unless a decision says otherwise. Module names are the brief's; nothing here pins a line number.
- **Facts the milestones still verify live** (unverified in the notes, with the behavior the harness assumes and the fallback): whether more than one `/skill-name` line expands (M0; fallback: inline the bodies); whether hooks fire inside a `--agents` subagent (M0; documented yes); the `-p` envelope at a real usage limit (M1 simulates it; M5 meets a real one; the conductor accepts three signals); whether `Workflow(absorb)` and `Skill(absorb)` narrow allow rules work (M3; fallback: `Workflow` and `Skill`); the cwd-slug rule for the session directory (M3 uses a glob that needs no slug); the tunnel's buffering and sleep-and-wake behavior (M1's second criterion); docling's, marker's, and MinerU's install footprints and the NVIDIA Container Toolkit's presence (M3; the always-on layer needs none of them); Cell's and Genome Biology's guideline fields (M7 retries); the `/usage` Fable line at a partial percentage (seen only at 100 percent; assumed to share the other lines' shape), whether an allowed Fable session's `rate_limit_event` carries Fable's weekly window, and a Workflow `agent()` refused on Fable (decision 15 treats a failed task with `error: rate_limit` as the refusal; M1 and M5 verify).
- **Deviations from the brief the map decided** (all applied above): verifier verdicts are Claude-only; workers emit `stream-json`; tool restriction is `--disallowedTools` or `--tools`, never an agent `tools` allowlist; `systemd-run` never uses `--collect`; notifications reach the phone through Telegram via `hermes send` because `notify-send` has no notification service on this machine; `skills` in `--agents` is not used; worktrees need `--add-dir`; `--fallback-model` is overload-only; the Fable fallback map corrected research note 02, whose weekly limits are not all shared: Fable's weekly window is counted apart.
- **Reading order for an implementer**: this spec, then `CONTEXT.md`, then the research note a decision cites, then `BRIEF.md` for the rationale; the map's ticket files hold the owner's own words for every decision.
